# Package A: requests for the integration step

Changes package A needs in files it does not own, and places where the plan
and UnityPy 1.25.2 disagree (UnityPy wins; the plan should be fixed). Each
names what, why, and the exact text or signature.

## 1. Plan 2.4, F3: counts follow UnityPy, not "refused when negative"

**What.** The F3 row says "every size or count read from the file as an
`i32` is refused with an error when negative". F3 refuses only the header's
sizes when negative. Every count is read the way UnityPy's `helpers/Tpk.py`
reads it, and none sizes an allocation:

- `range(count)` counts read zero items when negative and raise nothing.
  These are the class list (`Tpk.py:236-237`), a class's entries (`:338-344`),
  the node buffer (`:396-397`), the string buffer (`:409-410`) and the
  common-string versions (`:419-420`).
- struct-format counts raise `struct.error` when negative. These are the
  blob's version list (`read_versions`, `:467-469`) and the common-string
  indices (`:421-423`).

**Why.** UnityPy, probed in the container: G7's synthetic set records
`count_{classes,entries,common,nodes,strings,versions,indices}_{-1,2147483647}`,
and `TpkProvider` matches every outcome.

**Text.** Replace "every size or count read from the file as an `i32` is
refused with an error when negative and never used to pre-allocate" with
"the header's sizes are refused when negative; every count is read as
`Tpk.py` reads it (a negative `range` count is zero items, a negative
struct-format count, the version list's and the common-string indices', is
an error), and none is used to pre-allocate".

## 2. `PARITY.md` (E): F3's safety divergences

**What.** E's `PARITY.md` should list where the fork returns an error and
UnityPy returns an answer, or never ends. All but the last are reachable only
from a TPK that no writer emits; the last is a compression the format allows:

- a walk deeper than `Limits::max_tree_depth` (UnityPy builds it);
- a walk past `TpkProvider::MAX_TREE_ROWS` (65,536) rows, counting rows still
  to walk;
- a node that lists itself or an ancestor (UnityPy's walk never ends);
- a string tail shorter than its varint length (UnityPy's `read_string`
  decodes it short, `Tpk.py:445-456`);
- a varint of more than 5 bytes (UnityPy reads on with no shift limit);
- an LZ4 `uncompressed_size` above 255 times the block plus 255, refused
  before the output is allocated;
- an LZMA TPK whose header `uncompressed_size` is negative (F3), or differs
  from what the stream decodes to. The second is rabex's own rule, which the
  fork keeps: it decodes to that size. UnityPy reads the field and ignores
  it for LZMA (`Tpk.py:186-187`); only LZ4 passes it to the decoder;
- a brotli TPK. The fork is built without rabex's `tpk-compression-brotli`
  feature, so this is an `UnsupportedCompression` error, where UnityPy
  decodes it (`:189-192`). Enabling the feature would add the `brotli`
  crate. UnityPy's own TPK is LZMA, and A did not enable it.

**Why.** The plan's F3 row names E as the owner of this list.

## 3. `NodeRow::meta_flag` cannot hold a TPK meta flag above `i32::MAX`

**What.** `unityrs_core::typetree::rows::NodeRow::meta_flag` is
`Option<i32>`, as a blob reads it (`TypeTreeNode.py:102`, `read_int`). A TPK
node stores it as a `u32` (`Tpk.py:361`, `Struct("<HHihbIH")`, the `I`), and
`generate_node` copies it unchanged (`:78`). `TpkProvider` keeps the bits
(`row.meta_flag.cast_signed()`), so a flag of 2^31 or more reads as negative
where UnityPy has a large positive int.

**Why.** No real TPK reaches this: the largest meta flag in UnityPy's own
TPK is 268,468,289. A synthetic one can.

**Signature.** Either `pub meta_flag: Option<i64>` on `NodeRow` (blob values
sign-extended, TPK values zero-extended), or keep `i32` and record this as a
divergence in item 2's list.

## 4. Where the TPK fixtures live, and what is committed

**What.**

  `crates/unityrs-core/tests/fixtures/<package>/`. G7's replay test is in
  `unityrs-tpk`, and core cannot depend on it. So `tools/fixtures/tpk.py`

  `crates/unityrs-tpk/tests/g7.rs` replays.

  committed)". The G7 row says the synthetic TPKs and UnityPy's outcomes are
  A's committed fixtures. A follows the G7 row: the synthetic outcomes are
  committed, and nothing from the image's TPK is (no digest either).

**Text.** In 7.2, replace "(G7's UnityPy side, nothing committed)" with
"(G7's UnityPy side; commits the synthetic set's outcomes under
`crates/unityrs-tpk/tests/fixtures/tpk/`, nothing from UnityPy's own TPK)".

## 5. Generated regions, not a generated file header

**What.** Plan 2.5 says "A generated file starts with `// @generated by
tools/gen/gen_tables.py from <source>; do not edit.`". `tables.rs`,
`classid.rs` and `typetree/commonstring.rs` mix scaffold code with tables.
The generator therefore rewrites only marked regions. Each region opens with
that line and closes with `// @generated end`, and `--check` compares the
whole file. A file's own first line is left alone.

**Text.** In 2.5, write "A generated table sits between `// @generated by
tools/gen/gen_tables.py from <source>; do not edit.` and `// @generated end`;
the rest of the file is hand-written."

## 7. The ledger names each commit by its subject, not its hash

**What.** The plan's ledger has "one row per patch with id, commit, …". A
hash changes on every rebase and on the integration merge. `UPSTREAM.md`
therefore names each commit by its subject (`rabex F<n>: …`), and
`fork-check.sh` checks that each row has exactly one commit with that
subject prefix and that every commit touching `src/` names a row.

**Text.** In 2.4, replace "commit" in the ledger's columns with "commit
subject (`rabex F<n>: `, which `fork-check.sh` matches one to one)".

## 8. Running `fork-check.sh` from a worktree in the dev container

**What.** For whoever documents `scripts/dev`, probably in `CLAUDE.md`. In
the container, a worktree's `.git` file names a host path, so git works
there only with `GIT_DIR=/work/.git/worktrees/<name>
GIT_WORK_TREE=/work/.wt/<name>`. In its first version, `fork-check.sh`
passed those variables on to its replay repository. Its `git init` then
wrote `core.worktree` into the main repository's config, and its `commit`
committed into the worktree's branch. Both were repaired.

Commit 1df4837 fixed this: the replay runs with `env -u GIT_DIR -u
GIT_WORK_TREE -u GIT_INDEX_FILE -u GIT_COMMON_DIR` and checks
`rev-parse --absolute-git-dir`. The same trap waits for any script that
creates a scratch repository while those variables are set.

**Text.** A note beside the `scripts/dev` instructions: "git in a worktree
needs `GIT_DIR`/`GIT_WORK_TREE`; a script that runs `git init` must unset
them for its own repository."

## 9. Un-ignore G7's tree test when B's `Tree::compile` lands

**What.** `crates/unityrs-tpk/tests/g7.rs` (A's file) has
