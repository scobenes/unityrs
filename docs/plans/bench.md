# Benchmark plan: unityrs against UnityPy

**Status:** proposed, 2026-11-19, revised after review rounds 1 and 2, with the owner's decisions (section 9). Nothing is built yet. The owner asked for the following:

> once we have a shippable version, i want you to create benchmark suite that can be run to compare unityrs and unitypy and put summary on the main readme, and then bigger breakdown on a benchmark file. also we should record the numbers so that they can be reran and part of the tests so we can catch any regressions

**What it delivers.** The plan has four parts:
1. A comparison suite. One command times unityrs and UnityPy 1.25.2 with UnityPyBoost on public fixtures.
2. A README summary.
3. `BENCHMARKS.md`, the full breakdown.
4. Recorded numbers that tests check. `benchmarks/wall.json` holds the published timings. `benchmarks/gate.json` holds instruction-count baselines, which a CI job re-measures to catch regressions.

**What it builds on.**
- The private corpus report (`tools/perf/`), which stays private and unchanged. From it the plan reuses `mem_peak.py`'s summed-PSS sampler and `bench_unitypy.stack_problem`'s check of the pinned oracle.
- The testkit's builders.
- The oracle pins (`tools/parity/requirements-oracle.txt`).
- The UnityPy-compatible wheel (`crates/unityrs-py`), including its `tools/extractor.py`.

**Citations.** UnityPy behaviour is cited by its `PARITY.md` row.

## 0. Decisions

| # | decision | why |
|---|---|---|
| 1 | **Two measurements.** The *comparison* (wall time, CPU, peak PSS, throughput, both tools) is published and never fails CI. The *gate* (callgrind instruction counts, unityrs only) fails CI. | Wall clock on shared runners is too noisy to gate on. Instruction counts are deterministic but mean nothing across languages. |
| 2 | **Public inputs only.** The fixtures are generated by `unityrs-bench gen` from the testkit's builders with fixed seeds (section 2). Editor-built fixtures may join later. The private corpus and UnityPy's own test samples, which are game bundles, are never inputs. | The repository is public, and every figure must be reproducible by anyone. |
| 3 | **Fixtures are generated, never committed.** `benchmarks/fixtures.json` holds each file's name, bytes and sha256, plus, for each fixture, its inventory: object counts, pixels and the expected output paths. A test regenerates the gate scale and compares it with the manifest. | The set is about 440 MB. |
| 4 | **A speedup is published only for paired work.** A row is paired when its `PARITY.md` row is Tier A for the timed operation (a texture's section 17 row), both tools complete it with zero failures, and both produce the same digest. Every README count and total is computed from paired rows. Unpaired rows appear in `BENCHMARKS.md`'s unityrs-only table, with a reason and no speedup. Examples are BC6H (UnityPy raises) and `anim-gltf`. | A faster wrong answer, or a run against a refusal, is not a speedup. |
| 5 | **The same Python script for both tools.** The headline column runs the unityrs wheel under the workload script UnityPy runs (`import unityrs as UnityPy`). The wheel is installed `--no-deps` into the oracle venv, as CI's `python-wheel` job does, so both share Python 3.11 and Pillow 9.5.0. The Rust library column (`unityrs-bench run`) is in `BENCHMARKS.md` only. There is no CLI column and no parallel row. | It is what a UnityPy user switches to, line for line. `unityrs extract` has no `-j`, so a parallel row would compare different work. |
| 6 | **The gate counts unityrs's own instructions.** It counts `Ir` in the bench binary's own object, inside the workload's scope (section 4.2), under valgrind 3.19.0 (Debian bookworm's deb, sha256-pinned) in `debian:bookworm` pinned by digest, on `ubuntu-24.04`. glibc's share (the allocator and `memcpy`) is recorded but not gated. | glibc's malloc varies by about 0.9% between identical runs, and unityrs's own code by under 0.001% (section 8). Pinning the hasher does not help, because hashing is not the source. |
| 7 | **Two-sided ±1% gate. The base branch sets the policy.** Outside ±1% in either direction, the job fails with "out of band: refresh the baseline". The job reads each workload's mode (`calibrating` or `enforcing`) and the tolerance from the **base branch's** `gate.json`, never the PR's. So a PR cannot loosen its own gate. A policy change is a reviewed edit that lands on its own first. | The owner's decision. |
| 8 | **The reference host is GitHub's `ubuntu-24.04` x86-64 runner** for both measurements. Emulated hosts (Rosetta's `VirtualApple`, QEMU) are refused for publishing. | The owner's decision. The owner's Mac container is emulated, and its guest CPU class differs (section 8). |
| 9 | **The documents are generated.** `bench.py render` writes the README section between `<!-- bench:begin -->` and `<!-- bench:end -->`, and all of `BENCHMARKS.md`, from the two JSON files. A test fails if they differ, and it tolerates a missing `gate.json` until BN-2. | Hand-edited numbers drift. |

## 1. Scope

**Paired categories:** load and parse, typetree read, texture decode by format, mesh export, audio (PCM16 and FADPCM), animation (clip typetree read) and whole extraction of a supported inventory (4.3).

**unityrs-only rows:** BC6H, `anim-gltf`, and anything unpaired in a run.

**Not covered:**
- Vorbis: its setup table is never committed.
- MPEG and Opus: unityrs does not decode them.
- Crunch: the existing builder (`tools/fixtures/texture_crunch.py`) makes only small streams, so crunch is a later unityrs-only row.
- PNG encoding: it would compare Pillow with Pillow.
- Parallel runs.
- Wall-clock gating.

## 2. Fixtures

`cargo run --release -p unityrs-bench -- gen --scale full|gate DIR` writes every file and `manifest.json`. All bytes come from the testkit's builders and `unityrs_testkit::Rng` (SplitMix64). The Unity version is 2022.3.62f1, and one object set is in the 2019.4 layout.

**Texture blocks are legal by construction.**
- DXT, BC4, BC5, EAC, ETC2, PVRTC and ATC accept any bit pattern, so they use seeded bytes.
- ETC1 (`ETC_RGB4`) uses seeded blocks whose differential base plus delta stays within 0..31. Outside that range the specification leaves the output undefined.
- BC7 uses seeded bytes with the mode byte set to modes 1, 5 and 6 at 40%, 30% and 30%. It never uses the reserved mode.
- BC6H (unityrs-only) uses only legal mode bits.
- **ASTC tiles oracle-checked legal blocks.** These are the encoder-made and crafted legal blocks recorded in `crates/unityrs-texture/tests/fixtures/astc.json` (`tools/fixtures/texture_astc.py`, astc-encoder-py 0.1.12), laid out in a fixed pattern. There is no ISE writer and no random ASTC bytes. A test checks every tiled block with the unityrs ASTC decoder's error status under the LDR profile (no block may set it). It also checks the mix of block modes against the stated proportions at both scales. Output colour is not used as the legality test, because the error colour differs by build (`PARITY.md` section 19.3).

**Sizes.** The full scale is the comparison. The gate scale shrinks each item's dimensions while keeping at least one item of every kind.

| fixture | full scale | ~MB | gate scale |
|---|---|---|---|
| `objects-lz4.bundle` | 20,000 objects of 10 classes with embedded trees, about 1.2 KB each decoded, LZ4HC at about 3:1 | 9 | 1,000 objects |
| `objects-lzma.bundle` | the same, one LZMA block | 6 | 1,000 objects |
| `objects-2019.assets` | the same, uncompressed, 2019.4 layout | 24 | 1,000 objects |
| `many-blocks.bundle` | one 64 MiB entry in 16 KiB LZ4 blocks; its digest is the entry bytes' sha256 | ≤ 67 | 1 MiB |
| `textures-<format>.bundle` | 1024x1024 mip 0: 4 each of RGBA32, RGB24 and ARGB4444 (36 MiB); 8 each of DXT1, BC4, ETC_RGB4, EAC_R and PVRTC_RGBA4 at 0.5 MiB; 8 each of DXT5, BC5, BC6H, BC7, ETC2_RGBA8, ATC_RGBA8 and ASTC 4x4 at 1 MiB; 8 of ASTC 8x8 at 0.125 MiB (77 MiB) | 113 | 2 per format at 128x128 |
| `meshes.bundle` | 32 meshes of 16,384 vertices at 48 B, with 16-bit indices (30 MB); 8 skinned meshes with 4 weights and 16 blend shapes over 25% of vertices (29 MB); 8 `m_CompressedMesh` meshes (2 MB) | 61 | 2, 1 and 1 of 1,024 vertices, 4 shapes |
| `audio-pcm.bundle` | 8 clips of 30 s stereo 48 kHz PCM16 (8 x 5.76 MB) | 46 | 2 clips of 1 s |
| `audio-adpcm.bundle` | the same tones as FADPCM, about 3.6:1 | 13 | 2 clips of 1 s |
| `anim.bundle` | 100 clips, 2 s at 60 fps over 60 bones, a third each dense, streamed and constant | 29 | 3 clips, 0.5 s, 16 bones |
| `extract-set/` | 20 bundles, each holding 6 textures of 512x512 (DXT1, DXT5, BC7, RGBA32, ETC2_RGBA8 and ASTC 6x6), 4 meshes of 4,096 vertices, 8 TextAssets of 16 KiB and 1 PCM16 clip of 5 s, all as container entries | 88 | 2 bundles, textures at 128x128 |

The full set is about 440 MB, counting `many-blocks` at its 64 MiB bound. It is cached under `$UNITYRS_BENCH_CACHE`, outside the checkout.

## 3. Metrics and aggregation

- **Conditions.** The page cache is warm (each input is read once before a round). Every run is a fresh process. The runs of both implementations are interleaved round by round, with 1 warm-up round and 7 measured rounds.
- **Per run.** The harness records wall time inside the timed scope (4.2), whole-process wall time, CPU time (`getrusage`), peak summed PSS (`mem_peak.py`), the completion status (`ok`, or the failure), the inventory counts processed, and the digest.
- **Aggregation.**
  - A workload's figure is the median of its 7 round times, with the min and max as the spread.
  - A category's figure (a README row) is the sum of its paired workloads' times in each round, then the median of those 7 round totals. The min and max of the round totals give its spread.
  - The speedup is the ratio of the two medians. Its range is min(UnityPy) / max(unityrs) to max(UnityPy) / min(unityrs), from the round totals.
- **Throughput** is source MB/s plus the row's own unit, computed from the inventory counts.

## 4. The harness

### 4.1 Files

```text
benchmarks/fixtures.json   # manifest and inventories
benchmarks/wall.json       # the published comparison
benchmarks/gate.json       # instruction-count baselines and per-workload mode
BENCHMARKS.md              # generated
crates/unityrs-bench/      # publish = false: gen, run, the Rust workloads, block tests
tools/bench/
  README.md                # file and test tables, checked by tests/test_readme.py
  bench.py                 # gen | run | gate | render | check
  workloads.json           # the workload table, read by both sides
  py_workloads.py          # one script, --impl unitypy|unityrs
  callgrind.py             # valgrind runs, scope checks, per-object sums
  results.py               # schemas, pairing, aggregation, rendering
  install_valgrind.sh      # the pinned deb, sha256-checked, no root
  tests/                   # standard library; its own exact minimum in CI
.github/workflows/bench-wall.yml   # workflow_dispatch only
```

### 4.2 Workloads and scopes

Each workload has three phases:
1. `setup`, which is neither timed nor counted;
2. the scope, the only part timed and counted, whose outputs are held in memory;
3. `digest`, which runs afterwards.

In Rust the scope is `#[inline(never)] fn run_<name>`. Callgrind counts only it (`--collect-atstart=no --toggle-collect='*unityrs_bench::work::run_<name>*'`). `callgrind.py` rejects a run in any of these cases:
- the scope was entered other than exactly once;
- its inclusive `Ir` is under 10,000;
- another `run_*` function was entered;
- collection was on outside the scope.

| category | setup | scope (what the timer contains) | digest |
|---|---|---|---|
| load and parse | file bytes in memory | load from bytes; list every file's object table | object table; `many-blocks`: the entry bytes' sha256 |
| typetree read | environment loaded | `parse_as_dict()` on every object | canonical JSON |
| texture decode | environment loaded | `obj.read().image.tobytes()` for each Texture2D: object read plus decode | sha256 of mode, size and bytes (below) |
| mesh export | environment loaded | `obj.read().export()` for each Mesh: object read plus OBJ text | OBJ text |
| audio | environment loaded | `obj.read().samples` for each AudioClip | WAV bytes for each sample |
| animation | environment loaded | `parse_as_dict()` on every AnimationClip | canonical JSON |
| extraction | none (4.3) | the whole process | the output tree (4.3) |

**Pixels.** A texture's digest covers the image in the mode UnityPy returns (`PARITY.md` section 17's mode column: RGB for RGB24, RGBA for most formats). That means `tobytes()` after UnityPy's flip, plus the mode name and the size. Nothing converts to RGBA inside the scope.

### 4.3 Whole extraction

UnityPy's extractor aborts or writes nothing in documented cases (`PARITY.md` section 19.2, "extractor crashes"), so the row extracts a supported inventory only:
- Texture2D in Tier A formats, written as PNG;
- Mesh, as OBJ;
- TextAsset;
- AudioClip, PCM16 to WAV;
- all as container entries.

Both sides run the same script: `python -c "import <impl>; <impl>.tools.extractor.extract_assets(src, dst)"`. That is UnityPy's `tools/extractor.py` against the wheel's. The timer runs from process launch to exit for both, so the import counts on both sides. The parent then checks four things:
- the exit status is 0;
- the output tree's relative paths equal the fixture's expected path list (unique by construction);
- no expected path is missing or extra;
- the two trees' sizes and sha256s are equal.

Only then is the row paired. The gate's Rust scope for this row is `run_extract`: load from in-memory bytes, then the extractor into a scratch directory opened in setup. Its file writes are system calls, which callgrind does not count.

### 4.4 The commands

```sh
scripts/dev python tools/bench/bench.py run --out DIR           # the full comparison
scripts/dev python tools/bench/bench.py run --out DIR --quick   # gate scale, 3 rounds
python tools/bench/bench.py render [--check]
python tools/bench/bench.py check --wall-run RUN_ID             # CI: wall.json equals that run's artifact
```

### 4.5 Results

`wall.json`:
- `schema_version`, `run_id` and `run_attempt` (the `bench-wall.yml` run), `commit`;
- the tool versions: unityrs, `rustc -vV`, UnityPy, the UnityPyBoost sha256, Pillow and Python;
- the machine: CPU model, cores, memory, kernel, runner image version and `emulated`;
- the fixture manifest's sha256;
- `workloads[]`, each with `name`, `impl`, `timer` (the scope label), `paired` with a reason if false, `parity_row`, and `runs[]` holding each round's times, PSS, status, inventory counts and digest.

`gate.json`:
- `schema_version`, `tolerance_pct` (1.0);
- `fingerprint`: the valgrind deb sha256, the container digest, `rustc -vV`, the target and the guest CPUID class;
- `workloads`: a map from each name to its `mode`, `ir_own`, `digest` and `calls`, with `ir_libc` beside them, informational only.

No field holds a host path or a user name.

## 5. CI

### 5.1 The gate

The gate is a `bench-gate` job in `ci.yml`. It has no path filter and always reports, so a required check can never sit pending. There is no merge queue and no up-to-date rule.

The job:
1. builds `unityrs-bench` (release, `--locked`, with the cargo cache keyed on `Cargo.lock`) inside the pinned container;
2. regenerates the gate fixtures and checks them against the manifest;
3. runs each workload once under callgrind with one thread, `env -i` and the fixtures at a fixed path;
4. compares each workload with the base branch's `gate.json` under the base branch's policy (decision 7);
5. writes a job summary with base, PR and measured counts for every workload, and uploads the measured `gate.json`.

**What fails.** An `enforcing` workload outside ±1%, with the "refresh the baseline" message. A digest change on an enforcing workload. A workload missing from the PR's `gate.json`. A scope check (4.2). A fingerprint mismatch. A `calibrating` workload only reports.

**A refresh.** A refresh is a PR that changes `gate.json` together with the regenerated `BENCHMARKS.md`. The new numbers come from the job's uploaded file. CI re-measures and requires the committed counts to agree with its own within 0.01%. That is ten times the noise section 8 measured, so a baseline from another merge state fails before merge. The job summary shows the delta against `main` for review.

Two PRs that both move counts can each pass and then leave `main` out of band. `main`'s own run then reports the drift, and the next refresh PR fixes it.

**Calibration.** A workload enters `gate.json` in `calibrating` mode. It is promoted to `enforcing` by a PR that changes only modes. That PR lists at least 10 `bench-gate` runs on `main`, on separate runners, with this exact workload set and fingerprint, whose own counts agree within 0.01%. A fingerprint change (container, valgrind, toolchain) puts every workload back to `calibrating` in the PR that makes it, and that PR is reviewed on its own.

**Budget.** The gate is measured before it is committed. Every PR that adds workloads states the job's measured time, for a cold cache and for a warm one. The gate step must stay under 10 minutes, and the job's timeout is twice the measured run. If a PR would exceed that, it shrinks its gate sizes before it merges.

### 5.2 The published numbers

`bench-wall.yml` runs on `workflow_dispatch` only, on `ubuntu-24.04`. It installs the oracle stack and the wheel exactly as CI's `python-wheel` job does, runs `bench.py run` at full scale, and uploads `wall.json`.

A PR that publishes commits that file and the rendered docs. CI's `check --wall-run` step downloads the named run's artifact (`run_id` and `run_attempt`) and requires the committed `wall.json` to be byte-equal to it. That is the only provenance check. There is no weekly job.

### 5.3 The Python suite

`tools/bench/tests` gets its own step, `scripts/unittest-suites tools/bench/tests=N`, with an exact minimum. It holds the following:
- `test_readme.py`, which checks that `tools/bench/README.md`'s tables list every file in the folder (`tools/parity/tests/test_readme.py` is hard-wired to its own folder);
- `test_docs.py`, which runs `render --check`, validates the schemas, refuses emulated runs and allows a missing `gate.json`;
- the pairing, aggregation and band math;
- the scope checks on recorded callgrind files.

## 8. Feasibility spike (2026-11-19)

The spike ran in `unityrs-dev`: x86-64 Debian 12 under Rosetta, with 10 cores and a guest CPU of `VirtualApple` (SSE4.2, no AVX). Nothing from it is committed.

| question | result |
|---|---|
| valgrind | Not in the container, and there is no root. Bookworm's `valgrind_3.19.0-1_amd64.deb` (sha256 checked against the bookworm index) works from a `dpkg -x` prefix with `VALGRIND_LIB` set, and callgrind runs. Ubuntu 24.04 ships 3.22.0 in `main`, but it has not been run on a runner yet. `perf stat` is unavailable: there is no PMU under Rosetta, and none reliably on hosted runners. |
| guest CPUID | Under valgrind the guest reads a built-in `Intel Core i5 670` (SSE4.2, no AVX), not the host. So counts depend on the host's capability class, and baselines come from the runners. |
| small and large scopes | `unityrs dump` of one 7-object bundle, scoped to `dump_on`: 2,399,110 in 3 of 3 runs. Whole process: a spread of 0.022%. 128 MiB of LZ4 decode, scoped to `BundleFile::entry_bytes`: 86,040,117 in 3 of 3 runs. |
| hash maps, 10 runs | `unityrs dump` of the testkit's 518 bundle and serialized seed files, which exercises `walk/dict.rs`, `value/builder.rs` and the environment registry. Scoped to `dump_on`, the total was 211.43 to 211.64 million over 11 runs, **a spread of 0.103%**. Interposing `getrandom` with fixed bytes, which pins every `RandomState` seed, still gave 0.092% over 6 runs. One thread does all the counted work (`--separate-threads`). **By object:** unityrs's own code was 186,657,811 to 186,659,198 (0.0007%), and libc's 24.77 to 24.99 million (0.9%), all of it in glibc malloc internals. So the hasher is not the source: the allocator varies with addresses, and ASLR cannot be disabled in the container. The plan therefore gates `ir_own` (decision 6), pins no hasher, and records libc beside it. BN-2 retries with ASLR off on the runner, using `setarch -R` under an unconfined seccomp profile. If libc then repeats exactly, BN-2 may gate the whole scope. |
| UnityPy under callgrind | It runs, about 52x slower than native. `import UnityPy` alone is 5.09 billion `Ir`, with a spread of 0.09% that dwarfs small workloads. UnityPy is wall clock only. |
