**What it builds on.**
- The core as merged in P1 (`docs/plans/core.md`), through the properties its section 4.1 lists. A need those properties do not cover is a request to the core, made through its integration rule, not an assumption.
- The batch engine, whose design is `docs/plans/batch.md` section 2: staging, sealed attempts and their admission, views, copy-out to the spool, the winners, the stop path and refusal. This plan states what it needs from the engine (sections 1.3, 1.8, 1.13) and does not design it.
- The contract, `docs/BATCH_SPEC.md`: the spec's fields, templates and keys, identity and order, the NGUI cutter, the spool, the manifest, the zip bytes, the exit codes and reasons. A requirement here that names a field, a rule or a code takes its exact form from there.

**What it delivers.** `unityrs batch JOB.json`: one job of N bundles plus their dependencies, decoded in parallel under explicit budgets, with textures, sprites and NGUI atlases written as PNG files and atlas JSON to a directory, zip archives or an S3-compatible store, and a run manifest that says what was written, what was skipped and why. A release job publishes the binary. The first production consumers run on this phase; the plan names none, and their own acceptance runs (L10) are theirs.

**How requirements are written.** Each is numbered (E1, E2, ...). Each names the level it is checked at (`docs/DESIGN.md` section 6) and, once the plan is reviewed, the test that checks it. Where UnityPy 1.25.2 has the behaviour, UnityPy (or the oracle stack, `docs/DESIGN.md` section 3) is the reference. Where it has none (the sinks, the manifest, the cutter's JSON), the reference is the rule written here. Requirements added in design round 1 take the next free numbers (E57 on) and sit in the section they belong to.

## 1. Requirements

### 1.1 The job spec and the CLI

- **E1.** A job is a JSON document with a `spec_version`. The binary refuses a version it does not know, before any work, with a named error. It also refuses a spec over its size cap (`docs/BATCH_SPEC.md` section 1), an unknown field at any level, and a spec its schema rejects (section 3, item 4). Version 1's fields, types, defaults, ranges and cross-field rules are `docs/BATCH_SPEC.md` section 1.
- **E2.** `unityrs batch JOB.json` runs one job. `unityrs --version` prints the crate version and the highest `spec_version` the binary reads, in one line (`docs/BATCH_SPEC.md` section 10). `unityrs batch --check JOB.json` validates a spec without running it and prints its memory bound (`docs/BATCH_SPEC.md` section 10; **provisional** until X12 measures `docs/plans/batch.md` 5.3's constants, and uncertified, said on stderr, on a host whose pages are not 4 KiB), and `unityrs batch --schema` prints the embedded schema (`docs/BATCH_SPEC.md` section 1). B7c executes the temporary local directory normal-run subset; unavailable capabilities remain 78 `usage` before mutation, while `--check` accepts the full schema.
- **E3.** Exit codes tell apart: complete, expected skips included (`docs/BATCH_SPEC.md` 9.3: an object that reads correctly, left without an output by version 1's fixed scope or by a rule about its own content or name); complete with other object-level skips; incomplete for a data or transport reason; a budget refusal; stopped; superseded; could not start; an internal error; a host failure; a bad spec. Every stop, whoever requested it, exits with `docs/plans/batch.md` 2.11's end code. Their values, their precedence and the mapping from each outcome to a code are `docs/BATCH_SPEC.md` section 9, fixed and never reused for another meaning. None is 1 or 2, which shells and argument parsers use.
- **E4.** Progress is NDJSON on stdout; its fields, types and phase values are `docs/BATCH_SPEC.md` section 10 (section 3, item 5). Its first line is written when the threads start (`docs/plans/batch.md` 2.11 step 7), and its lines are then at most 2 seconds apart until the exit, on `docs/BATCH_SPEC.md` section 10's terms (a pipe, a FIFO, a socket or a terminal that the caller keeps reading), so a caller that keeps reading such a stdout can treat 5 seconds of silence after the first line as a hung run. To a regular file the host's writeback can hold one line's write for minutes (measured, `docs/plans/batch.md` A11), so no spacing is promised there, and no path that ends the run by its deadline waits on that write (`docs/plans/batch.md` 2.11). The `exit` line names the reason that set the code, with its detail. Each line is a snapshot, and the last is an `exit` line, written through the progress thread, or by the main thread (or its writer thread) before that thread exists (`docs/plans/batch.md` 2.11); when it is missing, the exit status is authoritative. Producers never wait on stdout or stderr, but for the main thread's own two lines, which share one budget of at most 1 s: to a pipe, a FIFO or a terminal through a non-blocking description of its own, tried again while it is full, and to a socket, or when stdout cannot be opened again (`EACCES`, a pipe another uid created), through the writer thread, waited on for what is left of the budget, a line dropped when it is spent, and for a write to a regular file or a block device, a local filesystem call (`docs/plans/batch.md` A11), by the descriptor rules of `docs/plans/batch.md` 2.11, so a parent that stops reading either, or another writer of the same pipe, cannot delay the deadline or a signal. With a deadline, every line before the progress thread exists goes through a writer thread, whatever stdout and stderr are, which the main thread waits on for at most `min(1 s, the time left - 500 ms)`, so a held write cannot delay the deadline either; when that wait is not positive (the deadline less than 500 ms away, or past) no line is promised, and the exit status is the record (`docs/plans/batch.md` 2.11). Without one, the main thread writes its line itself: a failure before validation accepts a spec, a spec accepted with `deadline: null`, a 78 (a refused spec has no deadline, even when its `JOB.json` names one), and `--check`, which sets no deadline and does no work, so its `memory_bound` line is written whatever its spec's deadline says. The deadline holds only when no other process writes the engine's stdout or stderr: another writer of the same regular file, throttled while it holds the file's lock, can hold the engine's write where `_exit` cannot end it (`docs/plans/batch.md` 2.11, *What cannot be bounded*), so a caller that needs the deadline gives the engine a pipe, or a file of its own, for each, and sources no other process is writing (E45; `docs/BATCH_SPEC.md` section 10). A caller that changes uid before the engine starts loses stderr unless the engine can open it again (`docs/plans/batch.md` 2.11). Its format has a version of its own, `p` (`docs/BATCH_SPEC.md` section 10). B7c supplies the normal mailbox/writer, priority exit acknowledgment and live atomic budget samples; B9 still owns lifetime handling.
- **E5.** The budgets of section 1.13 are required fields; a spec without them is refused (E1's error). Version 1 has no autodetection.

Levels: L9 for the CLI's behaviour on synthetic specs.

### 1.2 Inputs and downloads

- **E6.** A bundle (an input or a dependency) is a local path or a URL, with an optional expected `size` and `sha256` (`docs/BATCH_SPEC.md` 1.2). Every bundle is staged into the spool before extraction, a local file by a copy and a URL by its download, and every read of it during the run reads the staged copy (`docs/plans/batch.md` 2.5). Its SHA-256 is computed while it stages and recorded in the manifest's `bundles` rows. A `size` or `sha256` that does not match the staged bytes fails the bundle (`integrity_mismatch`); a local path that is missing fails it (`source_missing`), one that is not a regular file fails it at once, without blocking (`source_not_regular`), and one written during its copy fails it (`source_changed`). Local sources are on local filesystems; network filesystems are out of scope in version 1. A bundle over `max_decoded_bytes` fails before its bytes are claimed (`limit(input_bytes, <M>)`), so no one bundle's staging can fill the spool (an input's outputs are bounded by `max_export_work`, E48). A change to a source after its copy changes nothing.
- **E7.** A URL takes headers, an idle timeout and a rate floor (no body byte for that long, or fewer than the floor's bytes in such a period, fails a try; there is no whole-request timeout, so a download slowed by its neighbours takes longer and fails only below the floor) and a retry policy: which statuses and errors retry, the backoff, `Retry-After`, the number of attempts, and redirects, exactly as `docs/BATCH_SPEC.md` 1.4 defines them, its try table giving each failed try's class, `detail` and retry. No retry starts when its backoff would pass the deadline less the grace (E45), and a stop abandons a request in flight. A redirect to another origin fails the download, so a header never reaches another host. A body is staged as sent (`Accept-Encoding: identity`), so `size`, `sha256` and `Content-Length` all describe the same bytes. A header value that carries a secret is given by reference to an environment variable, never in the spec (E42), read once at preflight and at most 16 KiB.
- **E8.** `download_concurrency` bounds parallel transfers: stages (downloads and local copies), and in the publish phase uploads.
- **E9.** A job declares its complete dependency graph: every bundle any input needs is in `inputs` or `dependencies`, with its own path or URL, and every `deps` id names one of them (`docs/BATCH_SPEC.md` 1.1). A name in an input's AssetBundle `m_Dependencies` that is not the id of a bundle of its view is never fetched or opened: it is reported (a `diagnostics` row with the input and the name, and the run's `undeclared_dependencies` count), and a read that reaches a CAB only it would hold is the object-level skip `outside_view` (E65). There is no discovery. A first consumer builds its graph from its own build manifest, spelling ids as `m_Dependencies` spells them (`docs/BATCH_SPEC.md` 4.1).
- **E10.** A download that fails after its retries fails the bundle: the input itself, or, for a dependency, every input whose view holds it (E13). Each failed try's class is `docs/BATCH_SPEC.md` 1.4's try table. The run is then `incomplete` (exit 4), and the reason is in the `transport` class, which a retry as is may clear (`docs/BATCH_SPEC.md` 9.3).

Levels: L9, against deterministic in-memory transports for parser boundaries and a loopback TLS test server (no external network or DNS, test roots through the test hook only) that serves, delays, stalls mid-body, fails by status (a 408 among them), truncates, resets before the status line or mid-body, sends a malformed head or chunk, connects slower than the idle timeout, fails its TLS handshake and sends `Retry-After` on command, and against local files rewritten during the run.

### 1.3 Dependencies and isolation

- **E11.** The spec carries a dependency graph: for each bundle, input or dependency, the ids it needs (`deps`). An input's **view** is the input itself and the closure of its list through the graph (`docs/BATCH_SPEC.md` 4.2). A spec with a view over `max_view_bundles` is refused at validation. Every member of a view must be an AssetBundle file; one that is not fails the inputs whose view holds it (`dependency_failed(<id>, not_a_bundle)`), since a staged file has no name the core could key a raw dependency by (`docs/plans/batch.md` 2.3).
- **E12.** Under `EnvOptions::batch()`, an input's `.resS` reads and its container read its own bundle's same-named CAB first (core plan section 9, Q12; `docs/plans/batch.md` 3.9). `EnvOptions::unitypy()` keeps UnityPy's one registry.
  - The rule lives in the engine until the core's `own_bundle_first` option (batch.md section 6, CR3) replaces it.
  - The resource candidates follow `docs/BATCH_SPEC.md` 4.3's own-chain procedure, then the registry.
  - A pointer reads the reading file's own bundle first (Tier A), then the input, then, among the other bundles of the view, the one whose id is greatest in bytewise order (`docs/BATCH_SPEC.md` 4.3). Every input is registered in its own attempt, with or without dependencies, and every nested container of a registered bundle is reached at its registration (`docs/plans/batch.md` 2.6 step 4), so a pointer between two containers of its bundle, or into a dependency's nested container, resolves as UnityPy's eager load resolves it.
- **E13.** "Needs" means "is in the view" (E11). A dependency that fails to stage, or whose bytes fail to open, fails exactly the inputs whose view holds it, a staging failure before their attempt (`docs/plans/batch.md` 3.10). A read that fails for a dependency's own bytes (a corrupt block or entry, found at read time) is an object-level skip of the input that read it, not a failed dependency; what a bundle's peek at an entry's first bytes meets, computed once per run, goes by `docs/plans/batch.md` 2.6 step 4's rule: a `Limit` there fails, before dispatch, every input whose view holds the bundle. A failure at staging or at a peek fails the input before dispatch, by `docs/plans/batch.md` 2.3's rule 1: the input's own bundle's staging failure as its own reason; else, in a view that did not stage whole, the member of least id among those that failed staging, the record committed when staging ends, before any peek, so no peek bears on it; else, in a view that staged whole, the input's own peek failure as its own reason, then the member of least id among those whose peek failed, the record committed when the peek pass ends. So neither the input's own steps nor the eviction cap can come first. A view member whose load in an attempt is refused or fails on its bytes fails the input with `dependency_failed(<id>, <reason>)` (of several failed members, the one of least id, `docs/plans/batch.md` 2.3), whose exit code follows the inner reason: 5 for a budget reason, 4 otherwise (`docs/BATCH_SPEC.md` 9.2). An I/O error reading a member's staged file is a host failure (exit 74).
- **E65.** A pointer or resource read whose CAB no bundle of the input's view holds is an object-level skip, `outside_view(cab)`. The skip and its reason are the same whether another bundle holds that CAB or none does.
- **E14.** Each attempt opens each bundle of its view at most once per residency in its own dependency cache, within `dep_cache_bytes`, and reopens it after eviction. Past `max_attempt_evictions` evictions the input fails (`limit(attempt_evictions, <value>)`). Any refusal of its dependency budget that the core returns after the view is registered, a reopen's or a read's, fails it too (`budget(dependency)`, exit 5; until CR7, `docs/BATCH_SPEC.md` 4.3's gaps aside): the core does not say which refusals are reopens. So an attempt makes at most its view's size plus the cap in opens, and `budget(dependency)` is never an object's skip. No dependency is shared between attempts, so a dependency that N inputs read is opened up to N times (`docs/plans/batch.md` 1 and 2.2). The manifest counts every eviction. `docs/DESIGN.md` section 4 says the same, and plans a shared pre-decoded cache for later.
- **E58.** An input's records (its outputs and their bytes, its skips, its failure) are a function of its staged bytes, the staged bytes of the bundles in its view, the spec's entries for those bundles, and the spec's other fields. They do not depend on `threads`, the order inputs run or finish in, what else is in flight, or which bundles outside its view failed or exist (`docs/plans/batch.md` 1 and 2.10). Three limits: a run-level failure (a host failure, every allocator refusal the counting allocator sees among them, the spool's cap, an engine bug) stops the run instead; a bundle that could not be staged fails its inputs with a transport reason, which depends on the network or the host; and, until the core's CR2, liblzma's allocation refused unseen, on a dependency's meter (which the core retries after eviction) or on any meter, outside `with_room` too (a direct read on a dependency's handle; not in a peek, whose budget never refuses, `docs/plans/batch.md` 2.6 step 4), after a budget refusal absorbed earlier in the same core call, can decide a record by the host's memory (batch.md A13). Its test is `docs/plans/batch.md` 2.10's, with the nightly's second run (section 5). B7c pins normalized manifests and output bytes across threads 1/2/8, publication concurrency, five spool block sizes, resume and 20 seeded input orders; ordered output/collision encodings also stay identical.

Levels: L1 (env) and L9, on testkit scenes.

### 1.4 Decoding

- **E15.** BC7, DXT1, DXT5, RGBA32 and RGB24 decode bit-exact, with UnityPy 1.25.2's output modes, for textures UnityPy neither unswizzles nor byte-swaps (`docs/BATCH_SPEC.md` section 3): `RGB` for RGB24, `RGBA` for the other four (`PARITY.md` section 17's rows for these five). Built: `unityrs-texture`'s `decode`, ports of Pillow 9.5.0's raw and BCn decoders as `parse_image_data` calls them, with its padding, crop and flip; `crates/unityrs-texture/tests/oracle.rs` replays the oracle's pixels and errors (`tools/fixtures/texture.py`). - **E18.** Every decoder runs under `catch_unwind`. A panic is an object-level skip, recorded in the manifest, never a crashed run.

Levels: L5 on checked-in fixtures for the five formats and every sprite path; L5 on the nightly private corpus.

### 1.5 Images

- **E19.** A PNG writer byte-equal to Pillow 9.5.0's at its defaults, for modes `L`, `LA`, `RGB` and `RGBA` (`docs/DESIGN.md` section 4's `unityrs-imageio` row, L5b). Its deflate is zlib 1.2.13, the version the oracle image's Pillow links and the reference for PNG bytes (`docs/DESIGN.md` section 3's zlib row): the build compiles a vendored zlib 1.2.13 statically, since `libz-sys`'s static build bundles its own newer version, and CI asserts that `zlibVersion()` is `1.2.13`; that no crate enables a C-zlib feature of flate2, whose `any_c_zlib` would take the core's gzip off zlib-rs (flate2 1.1.10, `src/ffi/mod.rs`), and no C zlib's `-sys` crate (`libz-sys`, zlib-ng's `libz-ng-sys` or `cloudflare-zlib-sys`) is in the resolve or `Cargo.lock`, so no C zlib but the vendored one is linked; and that the vendored archive defines no name an unprefixed zlib defines, so it links beside one. Pillow saves a PNG through `deflateInit2` at level 6 (its default, -1), windowBits 15, memLevel 9 and strategy `Z_FILTERED` (Pillow 9.5.0, `src/libImaging/ZipEncode.c`), and the engine calls it so, with `zalloc` and `zfree` that allocate through Rust's global allocator (`docs/plans/batch.md` 2.6 step 10). The compiled `deflate.c` is an altered source version derived in `OUT_DIR`: `build.rs` verifies the original non-FASTEST `longest_match` span's SHA-256 before replacing it with the equivalent faster `zlib-match/longest_match.c`, using memcpy word comparisons with a byte-loop fallback, at optimisation level 3; the vendored files stay unchanged. The `test-reference` feature compiles pristine `deflate.c` under separate prefixed names: `tests/zlib_match.rs` compares deflated bytes at Pillow's settings over synthetic inputs through multi-megabyte window slides, and the `zlib_match` fuzz target repeats that comparison; CI also forces the byte fallback. The deflate state (a constant: its five blocks, 407,600 bytes at glibc's `heap_cost`), the five rows the filter works in and the output (one allocation, `deflateBound` of the filtered rows plus the chunks' framing) are charged to the caller's charger before each is allocated (E59; the crate's `charge` module says how the engine charges them).

### 1.6 The NGUI atlas cutter

- **E21.** Sheet scope `own_files_by_name`: the material's main-texture name, then the atlas name, matched among the input's own Texture2D objects only. A PPtr may cross into a dependency to read a name, never to take its texture. `follow_pptr` is not in version 1, nor a fallback for an atlas stored without a typetree (`no_typetree`). How an atlas is recognised, which fields hold its sprites, the crop geometry and every tie rule are `docs/BATCH_SPEC.md` section 5, which is the specification item 3's reference is written from.
- **E22.** A caller-given list of name suffixes (`skip_name_suffixes`) skips reference atlases.
- **E23.** A crop past the sheet's edge is padded with zeros, as Pillow 9.5.0's `Image.crop` pads.
- **E24.** The atlas JSON is byte-equal to CPython 3.11's `json.dumps(value, indent=2)` (its defaults otherwise: ASCII escapes, the float `repr`, `NaN` written as `NaN`) of the object `docs/BATCH_SPEC.md` section 5 defines: keys `name`, `texture_width`, `texture_height`, `pixel_size`, `settings`, `sprite_count`, `sprites`, in that order, with typetree values written as read (pairs as arrays, f32 widened exactly, strings as UnityPy decodes them).
- **E25.** A value the layout cannot write (bytes) skips that atlas's JSON alone, recorded in the manifest. The crops stay.
- **E26.** Collisions are handled per unit: a sheet texture and every atlas of the input that cuts it, or one atlas when textures are not exported. The unit's winner also wins its sheet texture (`docs/DESIGN.md` section 4's `unityrs-export` row; `docs/BATCH_SPEC.md` 4.5). The outputs rows name each output's unit key, which links an atlas to its sheet.

Levels: L5 and L5b for the crops, L7 for the JSON, on testkit-built atlases (an NGUI-shaped MonoBehaviour typetree is synthetic) and the nightly corpus.

### 1.7 Output naming

- **E27.** Key templates per output kind come from the spec. A variable is written verbatim, and its `safe_` form through `safe()`. The grammar, the variables, their spelling and where each is allowed are `docs/BATCH_SPEC.md` 2.1. Version 1 has no container path: a scope decision, not an impossibility (the input's own container rows are readable); it can come in a later version as an optional variable.
- **E28.** `safe()` works per code point, an invalid UTF-8 byte counting as one: every code point outside `[A-Za-z0-9._-]` becomes `_`; then every leading and trailing `.` is stripped; then an empty result becomes `unnamed` (`docs/BATCH_SPEC.md` 2.2).
- **E29.** Inside one input, the first object of a given type and name, in object order (`docs/BATCH_SPEC.md` 4.4), takes the name, even when its decode then fails. A later one is skipped, `duplicate_name`. Keys are planned before any export: of two planned outputs of one input with one key, the first in (kind, object order) takes it, even when its export then fails, and the later one is `duplicate_key`; within an atlas its JSON comes before its sprites. An output skipped for one of the plan's reasons, which need no pixels (an unsupported format, an empty rectangle, a reference atlas; `docs/BATCH_SPEC.md` 4.4 step 2), is not planned and takes no key. An atlas JSON that `json.dumps` cannot write (`json_unwritable`, E25) is found at the export, and keeps its key.
- **E30.** Inside one atlas, of two sprites with one key, the later one wins.

Levels: L9.

### 1.8 Winners across inputs

- **E31.** When several inputs produce one key, the spec's `prefer` map, `{key: {input, md5}}`, decides:
  1. the candidate from the preferred input, if that input has a candidate for the key;
  2. otherwise the candidate with the preferred MD5 (for a unit, its unit key's output's MD5), and of several such the first by bytewise input id, not reported as a flip;
  3. otherwise the first candidate input in bytewise order of input id, reported in the manifest as a **flip** when the candidates' MD5s are not all equal.
- **E32.** A sheet's texture output and every atlas of the same input that cuts it, with their crops and JSONs, win as one unit; when textures are not exported, one atlas with its crops and JSON is a unit. The unit's `prefer` entry is its unit key's: the sheet's texture key, or the JSON key (`docs/BATCH_SPEC.md` 4.5). This is the cross-kind rule.
  - The exact steps are `docs/BATCH_SPEC.md` 4.5 and 4.6. A unit is made of outputs the input made, so its unit key is always an output's key: the sheet's texture, else each atlas's JSON. Units are decided first, per unit key.
  - Every key of a winning unit is then reserved: a plain candidate for it loses, reported with the rule `unit`.
  - When two winning units claim one key, the unit whose unit key is first in bytewise order keeps it. The other unit is withheld whole (`unit_conflict`). A unit with a key refused for `prefix_conflict` or `archive_conflict` is withheld whole too. So phase 6 never publishes a unit in part; an attempt-time skip of one output (`unwritable_key`, `duplicate_key`) drops that output only.
  - Each of these checks runs once, so phase 6 decides them in bounded memory (`docs/plans/batch.md` 2.9): a key a withheld unit claimed stays reserved.
- **E33.** "Pixels differ" means a different visible hash (E20). A collision whose candidates share a visible hash is reported, but not as a pixel difference.
- **E34.** The winners hold candidates until every input that can produce a key has run: a sink that holds output across jobs. `docs/plans/batch.md` 3.5's model allows it: candidates are copied out to the spool, and winners are decided after extraction, as a pure function of the committed records.
  B7b supplies numeric committed payload access, accounted positional outcomes,
  and eight bounded row streams. Its serial publication peak has a separate
  bound in `batch.md` 5.1; the phase-6 40 MiB audit is unchanged. The disk ledger
  in 2.9 includes outcomes under `6S + 2A`, with `A` at encoded key length.

- **E60.** All or nothing per input. An input that fails commits no candidate and competes for no key. Only its failure record reaches the manifest.
- **E61.** Withholding. A key whose `prefer` entry names an input that failed in this run is not published (`withheld`). Its rule-2 or rule-3 winner could otherwise overwrite what the next complete run publishes. A key with no such entry is published, even when a failed input might have won it by rule 3: a choice, since withholding every key a failed input could produce would withhold most of a run for one failure. A spec option `publish_incomplete` (default `true`) set to `false` publishes nothing when any input failed: every winner and every archive with a member is `withheld` (`publish_incomplete`), and neither resume nor verification runs (`docs/BATCH_SPEC.md` 7.3).

Levels: L9.

### 1.9 Sinks

- **E35.** Directory.
- **E36.** Zip archives, written to the job's one sink as one more object each: stored members. An archive names output kinds and, per kind, a member path template over the output's variables; every published output of those kinds is a member, in `/`-first order of path (bytewise, except that a `/` is less than any other byte; `docs/BATCH_SPEC.md` 1.7 and 4.7). So a caller needs no list of keys before the run. Membership is decided with the winners, never by how loose PUTs end. Members stream from the spool, never copied whole; no archive is written that would have no member. Their bytes are fixed by `docs/BATCH_SPEC.md` section 8, so an archive's MD5 is the same on every run with the same members. There is one spool for staged bundles, candidates, records, archive central-directory scratch and the manifest, with one size cap and one free-space reserve, checked before every claim (`docs/BATCH_SPEC.md` section 6). Only an archive's central-directory scratch is spooled: its complete ZIP bytes stream straight to the sink's temp/transport, so there is no complete-archive spool cache and no complete-ZIP spool allowance. Sink temps and outputs stay in `batch.md` 5.6's separate filesystem provisioning term.
- **E37.** Object store (S3-compatible):
  - credentials from the environment only (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_SESSION_TOKEN` when set); no fallback chain. The engine builds each client with `AmazonS3Builder::new()`, never `from_env()`, which reads every `AWS_*` setting (checksums, encryption, request-payer) and would add headers this requirement forbids, passes its own static credentials with `with_credentials`, which skips the fallback chain, and refuses to start without credentials;
  - path-style addressing available (bucket names with dots break virtual-hosted TLS), and plain HTTP allowed only for an `http` endpoint the spec names (the L9 test store). `endpoint` is the service's URL without the bucket, which the engine maps for each addressing mode, and preflight proves the bucket exists with a LIST (`docs/BATCH_SPEC.md` 1.6, 7.2);
  - Content-Type set on every PUT (`image/png`, `application/json`, `application/zip`, `application/x-ndjson`) and `User-Agent` (`unityrs/<version>`) on every request, and no other header the engine chooses: no metadata, ACL, cache-control or checksum header. Signing headers, the session token's header, `Content-Length`, and E38's `If-Match` and `If-None-Match` are the protocol's, and `Accept: */*` is the engine's HTTP service's (`docs/plans/batch.md` 2.5). A single PUT sets its Content-Type per request; `MultipartStore::create_multipart` takes no options, so a multipart upload takes its client's default, and the controller has one client per multipart Content-Type (`docs/plans/batch.md` 2.9);
  - the caller passes credentials valid until the deadline; a set `AWS_CREDENTIAL_EXPIRATION` before the deadline is refused at start, and a request refused with `ExpiredToken` fails with its own reason, `credentials_expired` (`docs/BATCH_SPEC.md` 1.6);
  - the engine's connector sends every request through the engine's own HTTP service, with the settings `docs/plans/batch.md` 2.5 and 2.9 list, which for a store follow no redirect (so every 3xx reaches `docs/BATCH_SPEC.md` 1.6's table); `object_store` applies the builder's client options only in its own connectors, so none is relied on but `with_default_content_type`, which `object_store` applies itself to a request that sets no Content-Type (`src/aws/client.rs`). Its `RetryConfig` retries nothing (`max_retries` 0): the engine makes each of the sink's `attempts` tries itself, so it sees and counts every try the store may still commit (`unsettled_tries`, `docs/BATCH_SPEC.md` 1.6, 7.3). `object_store`'s errors do not expose a try's status, so the engine's own HTTP connector records each try's status, `Retry-After` and the S3 error code its body names, and `docs/BATCH_SPEC.md` 1.6's table classifies it. A stop abandons a try in flight. Multipart uploads go through `MultipartStore` (`create_multipart`, `put_part`, `complete_multipart`, `abort_multipart`), whose upload ids the journal records. A `CompleteMultipartUpload` retried after a lost response that meets `NoSuchUpload` is checked with a HEAD: the expected ETag there means it completed;
  - files up to 16 MiB single-part, so the ETag is the MD5; larger ones multipart in 16 MiB parts, like archives, compared by their expected multipart ETag (E43). Under SSE-KMS or SSE-C the single-part ETag is not the MD5; the engine reports `etag_not_md5` instead of failing, and resume then re-PUTs;
  - archives multipart at 16 MiB parts; a failed or interrupted multipart upload is aborted, on SIGTERM too (E64);
  - the permissions it needs: `s3:ListBucket` on the bucket (the bucket proof, resume, verification), and `s3:GetObject`, `s3:PutObject` and `s3:AbortMultipartUpload` on the prefix;
  - keys written byte for byte as given, or refused with a named error, never rewritten. Section 3, item 1 names the refused classes. Empty segments, `.` and `..` segments, a leading or trailing `/`, control characters, keys that are not UTF-8 and keys over 1,024 bytes are refused. `%`, `#`, `~`, spaces and non-ASCII are written as given.
- **E62.** Directory-sink safety. Each file is written as a temp file beside its destination and renamed over it. An existing final symlink may be replaced by that rename without following it; an intermediate symlink is refused. Loose outputs initiate writeback with `sync_file_range(SYNC_FILE_RANGE_WRITE)` and rely on the final `syncfs`, without a per-output `fsync`. Heads use temp-file `fsync`, rename and directory `fsync` on the writing thread, and are acknowledged only after all three succeed. Every temp file, the head's included, is created by `unlinkat` of its name (`ENOENT` ignored), then opened `O_CREAT | O_EXCL | O_NOFOLLOW`, so a killed attempt's leftover neither fails a retry nor is followed. An `unlinkat` or a create refused by what lies at an output's temp name fails that output by the kind rule below; an error at the head's temp file is the head write's (the `running` write's: a hand-over 74, below). One `syncfs` of the output file system runs before the final manifest, so the manifest never claims a file a power cut could lose. Paths are opened beneath the root and within its mount: by `openat2` with `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS | RESOLVE_NO_XDEV`, unless preflight's probe of it on the root gives `ENOSYS` or `EPERM`; else segment by segment, intermediate segments `O_PATH | O_NOFOLLOW | O_DIRECTORY` and the last as its use needs (`O_RDONLY | O_DIRECTORY | O_NOFOLLOW` for a directory to `fsync`, `O_RDWR | O_CREAT | O_NOFOLLOW` for the lock, a temp file's create flags), each opened descriptor's `statx` (`AT_EMPTY_PATH`) `STATX_MNT_ID` compared with the root's, `RESOLVE_NO_XDEV`'s rule, a `stx_mask` without it counting as a crossing; a fallback that cannot so `statx` the root exits 69 (`mount_check_unavailable`). So neither a key nor a planted symlink can escape it, and the `syncfs` reaches every file. Preflight opens `<root>/_unityrs` and `<root>/_unityrs/<run_id>` by the same rule, made when absent (`docs/plans/batch.md` 2.1). A mount crossed beneath the root is, in phase 7, `host_io` (74), a run failure (but not, under resume, one at an output's destination itself, E43): it is the host's layout, not the input's, so records keep D, and the root's `syncfs` would not cover what lies past it; at preflight, exit 69 (`mount_crossing`); in the finisher, on a row file's or the head's path (a mount made during the run), a failed write of that file (`docs/BATCH_SPEC.md` 9.2: a 4). In phase 7, a file or directory planted at an output's own path or along its key's segments, a mount crossing aside, fails that output, `publish_failed` (4): an open refused with `ELOOP`, `ENOTDIR` or `EISDIR`, or a rename refused with `EISDIR`, `ENOTEMPTY`, `ENOTDIR` or `EBUSY` (a mount on the destination). A filesystem's own error there is the host's (74); in the finisher, a failed write is `docs/plans/batch.md` 2.11 step 3's. Any error of the `running` write, a mount crossing (made during the run) or `EBUSY` included, is `host_io` (74), handed to the finisher as a 69 is (`docs/plans/batch.md` 2.11). A segment over 255 bytes (`NAME_MAX`) is a refused key. A killed run can leave temp files (`.unityrs-tmp-*`). No key may have a segment starting with `.unityrs-tmp-` (`reserved_name`), so none is ever taken for an output, and the engine never walks the root for them: the caller may delete them while no run holds the root's lock (E38).
- **E64.** Each multipart upload's id is appended and synced to the spool's uploads journal after its create and before its first part, and removed only after a successful complete or abort (`docs/BATCH_SPEC.md` 6.1), so an id whose abort failed stays for the finisher and the next start. The finisher closes the journal and aborts every id in it (it starts no multipart upload itself: its row files are single PUTs), and the next run in the same spool, of any `run_id`, aborts the ids a killed one left for its own endpoint and bucket (`docs/BATCH_SPEC.md` 6.2); an id it cannot abort is left to the lifecycle rule with a warning, and never stops its start. The operator's runbook names the bucket's lifecycle rule for uploads left by a lost spool.

Levels: L9 against a local S3-compatible test server, with its request log as the evidence for headers, addressing and keys, and a fault-injecting store (one fault per row of `docs/BATCH_SPEC.md` 1.6's table, `SlowDown` and `Retry-After` among them, a hang, a conditional-write conflict, a lost complete response, ETags that are not MD5s, a folder marker under the prefix, a PUT held until after the attempt's last transfer, which verification must report).

### 1.10 The run manifest

- **E38.** The manifest's first write is status `running`. It carries the `run_id`, the attempt number from the spec's required `attempt` field (an integer the caller raises for each attempt), the binary's version, the `spec_version`, the start time and the deadline. No output is written before it.
  - Its location is fixed by the `run_id`: a small head, `_unityrs/<run_id>/manifest.json` under the sink's root, and per-attempt row files beside it (`docs/BATCH_SPEC.md` 7.1). So runs with different `run_id`s never fence each other.
  - Each head write is fenced on (`run_id`, `attempt`). An attempt that finds a head of its `run_id` with an attempt number above its own (or, in preflight, equal to it), in preflight or on a write's read-back, writes nothing more and exits 7 (`superseded`; `docs/plans/batch.md` 2.11's precedence). A head of a lower attempt that a read-back finds is an earlier attempt's late write: the attempt retries its write on it, at most 4 times (`docs/BATCH_SPEC.md` 7.2).
  - In an object store each head write is a conditional PUT (`If-None-Match: *`, then `If-Match`), and a failed precondition (`object_store`'s `Precondition` or `AlreadyExists`) is read back before it counts as superseded, so a lost response is not taken for a rival (`docs/BATCH_SPEC.md` 7.2). A `running` write that fails otherwise exits 69 having written at most a fenced `running` head, so under conditional fencing the caller retries with the next attempt number, at once.
  - A store without conditional writes needs `manifest_fencing: "none"`; the caller's duties below are then the only fence on the head too.
  - The directory sink fences with one lock for the whole output root (`_unityrs/lock`), so one process at a time writes a root, and a rename.
  - **Verification and the caller's duties.** No client can bound when a store commits a request it has received, so in an object store the engine bounds its own writes and, before the final head, LISTs what it published and checks each key's ETag: another writer's bytes make the key `failed` (`publish_mismatch`), and the head says whether the pass ran (`verified`). The caller keeps two duties: one attempt of a `run_id` at a time, with nothing else writing its keys; and before a retry, a wait of the store's longest commit time (15 minutes for S3) past the earlier attempt's end, or its deadline, unless that attempt ran with conditional fencing and either its final head shows a normal end with no unsettled try or it exited 69; with `manifest_fencing: "none"` the caller always waits (`docs/BATCH_SPEC.md` 7.2). The spec gives a `deadline` with an object store, so the caller always has an end to count from, unless the process is stopped or frozen across its hard exit, or killed while a file call holds a thread (`docs/BATCH_SPEC.md` 7.2).
  - The head is the record of the run: for every key it lists as `written` or `present`, the store held this attempt's bytes when verification listed them (for a key whose ETag is not an MD5, an object of their size, counted in `verified_by_size`), and holds them still if the caller kept its duties. A key it does not list so is not the run's output, whatever the store holds.
- **E39.** Its last write, by the finisher, replaces it with the final status: `complete`, `complete_with_skips` or `incomplete`. On a normal end it is written only after every publish was acknowledged and, in an object store, verified, and after E62's `syncfs` for a directory. On a stop it says what was reached, as `docs/BATCH_SPEC.md` 7.4 defines for each phase; a stop before the `running` write writes no head.
- **E40.** The manifest records:
  - **per bundle:** whether it staged, its reason and detail, its size and the SHA-256 of its staged bytes, and its peek's peak and decode work (`peek_peak`, `peek_work`) and failure's reason, if any (`peek`);
  - **per output:** key, kind, unit key, source input and SerializedFile, path id, MD5, visible hash, mode, size, and a status of `written`, `present` (resume found the same bytes), `not_written` (a stop came first), `withheld`, `failed` or `unwritable_key`;
  - **per collision:** one row per candidate (key, input, MD5, visible hash), the winner and the rule that chose it, flips marked;
  - **per input:** status, failure reason and detail, its Input and Dependency peaks, its evictions, its export work, timings, object-level skips;
  - **per archive:** status, MD5, ETag and size, and each member's path, key, source input and MD5, or why it was left out;
  - **`run`** (`docs/BATCH_SPEC.md` 7.3's `run` row): `same_named_cabs`, `undeclared_dependencies`, `nested_containers`, evictions, the peaks of the inputs' and dependencies' budgets, the most decode work of one meter (`decode_work_peak`), the most export work of one input (`export_work_peak`), the most of any bundle's peek peak and peek work (`peek_peak`, `peek_work_peak`), the spool's peak, the sum of the inputs' spooled parts (`spooled_parts`, `docs/plans/batch.md` 2.6 step 10), peak RSS (`VmHWM`), the bound batch.md section 5 computes for the spec, the budgets as read;
  - **the head:** the stop reason and its detail, whether verification ran to its end and how many keys it checked by size alone, how many tries the store may still commit (`unsettled_tries`), each warning's count (`docs/BATCH_SPEC.md` 9.3), and the SHA-256 of `JOB.json` as read (`spec_sha256`).
  - Every field, row file and reason code is `docs/BATCH_SPEC.md` sections 7 and 9.3. A limit refusal's reason names the limit and its configured value, never the amount asked for.
- **E41.** In an object store, Content-Type `application/json`.
- **E42.** No credential the engine holds appears in the manifest, the progress stream, stderr or any error message. That covers a URL's query string and userinfo, and every header value. A URL is never printed with its query string, and an HTTP client's error is printed without its URL. stderr's writer masks every secret the engine holds (`docs/plans/batch.md` 2.11). A credential's text the caller writes into an id is the caller's, and is printed as given in the manifest; stderr masks it where it is a secret the engine holds.

Levels: L9, with a test that runs every sink with known credentials, signed URLs and secret headers, and searches every byte the run wrote or printed for them.

### 1.11 Resume and idempotence

- **E43.** A re-run with resume LISTs the output root once, at phase 7's start, and skips a PUT whose key already holds the same MD5 (an archive's, or a file's over 16 MiB: its expected multipart ETag at 16 MiB parts, which for an archive takes a first pass over its bytes), marking it `present`. The LIST is merged with the sorted winners one page at a time, so its memory does not grow with the store (`docs/plans/batch.md` 2.9). A LIST that fails, for example on a foreign key `object_store` cannot parse (section 3, item 1), degrades resume to "PUT everything" with the warning `resume_list_failed`; it does not fail the run. In a directory, resume opens the destination's parent beneath the root (E62), then `statx`es the last component from it with `AT_SYMLINK_NOFOLLOW`, so a crossing is located, and hashes the destination, opened from the parent, only when that shows a regular file of the output's size on the root's mount; anything else, a symlink among them, is not `present`, as are a mount crossing at the destination itself, whose transfer then meets E62's `EBUSY` (4), and one resume cannot open or hash, short of an I/O error (`EIO`, 74). B7c wires the directory resume procedure into normal CLI execution; store LIST execution remains B11's.
  B7b's library seam implements directory whole-file resume through the same
  admission envelope as transfer, with a miss transferred before the next key.
  It does not reuse extraction or spool artifacts. Concurrent scheduling and
  normal finishing are integration work; archive execution remains unavailable.

- **E44.** Every input is still read and decoded, so winners, archives and the manifest cover the whole job. There is no partial ("narrowed") re-run.

Levels: L9: a run killed at each progress line, then resumed, writes the same keys and bytes under the root, `_unityrs/` and `.unityrs-tmp-*` entries aside, as an uninterrupted run, and leaves no open multipart upload.

### 1.12 Lifetime

- **E45.** A wall-clock `deadline` in the spec is the time by which the process has exited. The engine converts it once to a `CLOCK_BOOTTIME` instant and starts stopping at the deadline less `shutdown_grace_ms` (default 20 s, at least 10 s, since phase 1 holds a stop until validation ends, `docs/BATCH_SPEC.md` 1.1). Every stop, from a signal, the deadline, the parent, stdin or a run-level failure inside the run (a leak, a host I/O error, an allocator refusal, a full spool, an engine bug), takes one path: every request in flight is abandoned, and the finisher aborts open uploads, writes the manifest the phase allows, and exits with the final code (`docs/plans/batch.md` 2.11), without joining its threads; a watchdog calls `_exit` with the end code before the deadline whatever is unfinished (`docs/plans/batch.md` 2.11). Only a stop or freeze of the process across it (`docs/BATCH_SPEC.md` 7.2), a filesystem call that never returns (batch.md A11), a wait on a file's lock that another, throttled process holds (below), a directory sink's final `syncfs` and, on ext4 in `data=ordered` or `data=journal` mode, the head's temp-file and directory `fsync`s and the uploads journal's syncs, which last as long as the unflushed data on their filesystem takes to write, and, each unverified, on ext4 in `data=ordered` mode a metadata call (a rename, a create, an unlink) or a buffered write's timestamp update (its jbd2 handle) waiting on a journal commit that waits on that data, a write to a page under writeback on a device that needs stable pages, an unlink's final `iput` waiting for the file's writeback, and a truncate waiting for its pages' writeback, can hold the process past it, leaving the head `running` (batch.md 2.11, *What cannot be bounded*). Dirty-page throttling, which can hold a buffered write for minutes while the host is over its global dirty limit or the memory cgroup over its own, on any filesystem (batch.md A11), can also leave the head `running`: it can hold the controller's writes the hand-over waits for (a directory sink's `running` head, written at preflight, whose throttled write, landing in the last seconds before `T_hard`, leaves the head's try no time; its commits under the commit lock; phase 7's outcome writes and `present` writes; the outcomes files' zero-writes), the uploads journal's writes, whose mutex the finisher takes, and the finisher's row-file and head writes, costing the head its try, but not the process past the deadline, since `_exit` ends a write the engine's own throttle holds. The controller's moved writes (every failure record's file, which the controller then renames, a metadata call; every phase-6 write: its sort runs, merges, row files, winners file, decision file, member lists and `P`), and a store archive's central-directory writes, per-permit chunk writes, run on its blocking pool, so a stop does not wait for them, and the finisher gives up the uploads journal's lock at the deadline less its head's reserve, leaving the aborts to the next start (batch.md 2.11, W10). What can hold the process past the deadline is another process's throttled write, in two ways (batch.md 2.11, *What cannot be bounded*, A11): a write to a file the engine writes, which holds that file's lock where `_exit` cannot end the engine's write, so a caller that needs the deadline gives the engine a stdout and a stderr no other process writes; and a write to a source the engine reads, whose read waits on the same lock on XFS, so the caller also gives it sources no other process is writing. A spec that validation refuses has no deadline, even when its `JOB.json` names one, and neither has `--check`: their lines are the main thread's own (E4). With a deadline, a start that ends less than 500 ms before it promises no line, only its exit status (batch.md 2.11).
- **E46.** The process exits when its parent dies (Linux `PR_SET_PDEATHSIG`, set by the binary itself) and, when the spec asks, when stdin reaches EOF, for a stdin that only the engine reads, a pipe, a FIFO, a socket or a terminal (`docs/BATCH_SPEC.md` 1.1). When the spec gives `parent_pid`, the binary compares `getppid()` with it right after setting the signal and stops at once when they differ, which closes the race of a parent that died first; without `parent_pid` there is no start check. Callers are told that Linux sends the signal when the *thread* that forked the child exits: a caller that spawns from a pool thread that may exit should use the stdin rule.
- **E47.** SIGTERM, SIGINT and SIGHUP stop the run (E45), but a SIGINT or SIGHUP the caller left ignored stays ignored (`docs/plans/batch.md` 2.11 step 4): abort open multipart uploads, write the manifest `docs/BATCH_SPEC.md` 7.4 gives for the phase reached (none before the `running` write was sent), and exit with the final code (`docs/plans/batch.md` 2.11: 6, unless a 7 or a more severe code), until the hard deadline, which leaves the head `running` when the final write has not landed. A stop the controller sees at phase 7's end, after the transfers drain or after verification, makes the end a stop; a signal after the controller's last check changes only the finisher's try budget (`docs/plans/batch.md` 2.11). The hard deadline and a second signal exit with the final code once it is stored, else with the stop's code (`docs/plans/batch.md` 2.11), and a final head write in flight may still land. A second SIGTERM, SIGINT or SIGHUP exits at once; a stop for another reason (stdin's EOF, the deadline, a run failure) followed by one signal still writes the manifest. Every engine exit resets Linux TCP sockets in place with `connect(AF_UNSPEC)`, preserving their descriptions and readiness registrations; disconnect reports `EPOLLHUP`. Zero linger is set before connect. macOS shutdown is non-normative (`docs/plans/batch.md` 2.11). From `docs/plans/batch.md` 2.11's step 4, a SIGABRT, the engine's or the caller's, ends the process with 134 after the engine resets its connections, as a PID namespace's init too (`docs/BATCH_SPEC.md` 9.1). B7c implements normal finishing only; mandatory process stop/lifetime acceptance remains B9's.
- **E63.** Before the manifest's first write, a preflight runs in a fixed order (`docs/plans/batch.md` 2.1). Before it starts its threads (`docs/plans/batch.md` 2.11 step 6), it checks the deadline (E45), reads each header variable once, checks `RLIMIT_AS` and `RLIMIT_DATA` against the floor `docs/plans/batch.md` 2.7 derives from the memory bound, refuses `vm.overcommit_memory` 2, a `vm.max_map_count` below the bound's need, and a bound above the smaller of `MemTotal` and the cgroup's limit (its ancestors' included, `docs/plans/batch.md` 2.7), raises `RLIMIT_NOFILE` and `RLIMIT_FSIZE` to their hard limits and checks them, and checks the engine's thread count against `RLIMIT_NPROC` and the cgroup's `pids.max` (`docs/plans/batch.md` 2.7). Then it reads the credentials and starts the spool (`docs/BATCH_SPEC.md` 6.2): it checks that the spool directory is dedicated to unityrs (empty, or holding only its marker, lock and runs) and apart from a directory sink's root, takes a non-blocking `flock` on its lock file, which is never deleted, so two attempts never share a spool, aborts the uploads its old journals name, deletes only its own `runs/`, then checks the free space against the reserve. It refuses a spool on tmpfs or ramfs, whose bytes would be memory, and a directory sink on a Linux kernel older than 5.8, whose `syncfs` reports no writeback error. It takes the output root's lock (directory sink), or proves the bucket exists with a LIST (object store), and reads the stored manifest head for fencing. A preflight failure exits 69 with nothing published or deleted that the engine did not create; a head that supersedes this attempt exits 7. A missing or mismatched bundle is not a preflight failure: it fails at staging, and only the inputs that need it (E6, E13).

Levels: L9.

### 1.13 Budgets

- **E48.** `threads`, `download_concurrency`, `max_inflight_uncompressed_bytes`, `max_decoded_bytes`, `dep_cache_bytes`, the spool directory, the spool size and the spool's free-space reserve are required (E5). Each has one meaning (`docs/plans/batch.md` 2.2):
  - `max_decoded_bytes` (`M`) is every meter's `max_input_memory` and `max_input_bytes`, an input's and each dependency's alike, and each attempt's Input budget; the engine sets every meter's `max_decode_work` to four times it, the core's default ratio;
  - `dep_cache_bytes` (`D`) is each attempt's Dependency budget and the bound of its private dependency cache, registry included;
  - `max_inflight_uncompressed_bytes` (`I`) bounds the slots of the attempts in flight (`M + D` each), and is the working set of the winners' sort, the resume merge and the transfers' buffers;
  - `download_concurrency` bounds transfers (E8);
  - `max_attempt_evictions` (optional) bounds one attempt's dependency evictions, and so its work (E14);
  - `max_export_work` (optional) bounds one attempt's export work (`docs/plans/batch.md` 2.6 step 10: the pixel bytes it writes, and the files and member records it spools, counted whatever the host's block size), so the limit is a function of the bytes and the spec; and so it bounds its export time and its share of the spool: past it the input fails, `limit(export_work, <value>)`. A spool sized by `docs/plans/batch.md` 5.6 leaves room for it. Its default, 2 x `M`, covers the measured texture path's largest input about 6 times, and is provisional until the atlas path is measured, the sprite path's work, measured, far below it (`docs/BATCH_SPEC.md` 1.1, `docs/plans/batch.md` 5.6 and section 8). A Sprite's render counts only its image as export work: its intermediates are bounded by `M_X`'s charges and its decode work (`docs/plans/batch.md` 2.6 step 10's exception).

  A spec is refused unless `M <= D`, `M + D <= I` and `I >= 64 MiB`. Every field, required or optional, and its default is `docs/BATCH_SPEC.md` section 1.
- **E49.** How the budgets bound memory is `docs/plans/batch.md` section 5: `max_inflight_uncompressed_bytes` plus constants the spec fixes, with the spool bounded on disk by its size and reserve.
- **E59.** Every buffer the engine allocates in proportion to an input or an output (pixels, masks, a sprite's mesh arrays and the affine path's buffers, PNG rows and output, atlas JSON, the attempt's records of its AssetBundle object, its record buffer, zlib's deflate state) is charged to the job's meter, or to the phase budget of `docs/plans/batch.md` 2.9, before it is allocated, at `heap_cost`: the core's rule (core plan 3.15) applied to engine code. A job exports one sheet at a time: a sheet's buffers and an atlas crop's are bounded by its largest sheet, and a Sprite's render, whose image can be larger than its sheet (a crop past the sheet is padded), by `M_X`'s charges and its decode work (`docs/plans/batch.md` 2.6 step 10).
- **E57.** On glibc, the binary sets `M_MMAP_THRESHOLD` to 128 KiB and `M_ARENA_MAX` to `threads + 2` at start, so RSS follows the charged heap (`docs/plans/batch.md` 5.4), and reports peak RSS.

## 3. Section 3's items, settled in design round 1 (for review)

Each item gives the recommendation and its reason. None is decided until this plan's review rounds end.

### Item 1. Verbatim keys and `object_store`

**Recommendation.** Keep `object_store` (0.12). Write a key only when `Path::parse(key)` gives back exactly `key`, the key is non-empty, valid UTF-8 and at most 1,024 bytes. Refuse any other key with `KeyRefused { key, rule }`, never rewriting it. `Path::from` and `from_iter` are never used.

**What `object_store` does**: 0.12.5's, as read in design round 1 and checked against the crate's source in design round 5, and each point below rechecked against 0.14.2's source, the version the engine pins, in B11a's review fold (what remains assumed is the store's side, `docs/plans/batch.md` A15):
- **`Path::parse`** (`src/path/mod.rs`, `src/path/parts.rs`):
  - strips one leading and one trailing `/`, silently, which is a rewrite;
  - refuses an empty segment, a segment that is `.` or `..`, and any ASCII control character (`PathPart::parse`);
  - keeps `%`, `#`, `~`, spaces, non-ASCII and other punctuation verbatim.
- **`Path::from` and `from_iter`** drop empty segments, percent-encode `%`, `#`, `~` and other reserved characters, and turn `.` and `..` into `%2E` and `%2E%2E`. Those are rewrites.
- **On the wire**, the S3 client percent-encodes the key once, every byte outside `A-Za-z0-9-._~/` (`STRICT_PATH_ENCODE_SET`, `src/aws/mod.rs`, used in `src/aws/client.rs`), and the store decodes it once. So the stored key is the `Path`'s string, byte for byte.
- **`Path` is a `String`**, so a key that is not UTF-8 cannot be expressed.
- **LIST** reads each page's body whole and parses every key it returns with `Path::parse` (`src/client/s3.rs`). One foreign key under the root that it refuses fails the whole listing (E43's degradation). `PaginatedListStore::list_paginated` takes a page size (`max_keys`), which the engine sets to 1,000 (`docs/plans/batch.md` 2.9).
- **Credentials.** Without explicit ones, the builder falls back to web identity, the container and pod providers and instance metadata (`src/aws/builder.rs`), and `from_env` reads every `AWS_*` variable, so the engine uses neither (E37).
- **Content-Type.** A single PUT's attributes set it; otherwise the client's extension map, empty unless configured, then its default (`ClientOptions::get_content_type`). `create_multipart` takes no attributes, so a multipart upload gets the client's default (E37).
- **Errors.** `object_store`'s retry error type is private to the crate, so a try's status is not visible from outside; the engine reads it through its own `HttpConnector` (`AmazonS3Builder::with_http_connector`, E37).

**Refused classes** (the `rule` of the error), each with an L9 test that reads the test server's request log:
- `empty`;
- `leading_slash`, `trailing_slash`;
- `empty_segment`;
- `dot_segment`, a segment that is `.` or `..`;
- `control_char`;
- `not_utf8`;
- `too_long`, over 1,024 bytes, S3's own limit.

**What each choice cannot write.**
- `object_store` cannot write any of the first six rules, `empty` to `control_char`.
- A hand-written SigV4 client over `reqwest` could add empty segments, slashes at the ends and control characters (the last needing `encoding-type=url` on LIST), but not dot segments. The `url` crate, which every `reqwest`-based client builds on, removes `.`, `..` and their `%2e` forms as dot segments, per the WHATWG URL standard (`url` 2.5.8, `src/parser.rs`).
- No client can write the last two, since S3 refuses them.
- A second HTTP stack, with our own signing, multipart, retries and credentials, is not worth keys no template should produce.

**Where a refusal lands.**
- A template's literal parts are checked at validation (`docs/BATCH_SPEC.md` 2.1's literal checks): a bad spec (exit 78).
- A key built from a verbatim name is checked when its output is made. The output is an object-level skip (`unwritable_key`), named in the manifest.
- `safe()` never makes a shape refused by its characters: it maps `/` and control characters to `_` and strips dots at the ends. A long name can still make a segment over 255 bytes or a key over 1,024, which is `unwritable_key`.
- The same rules hold for every sink: `segment_too_long` (`NAME_MAX`), `reserved_prefix`, `prefix_conflict` (a key that is also a parent directory of another key the decision would publish, `docs/BATCH_SPEC.md` 4.6's `P`, or of an archive's key, which a directory cannot hold) and `archive_conflict` (a key equal to an archive's key or under it) are refused everywhere, the last two decided in phase 6 so it does not depend on publish order (`docs/BATCH_SPEC.md` 2.3 and 4.6). Zip member paths take the rules too (but the reserved prefix and name), where they also block escapes from the archive's root. So a key is writable in one sink exactly when it is writable in all of them.

**Reason.** It keeps the one S3 client DESIGN names, and every key it writes is byte-exact. The keys it cannot write, no client could write through `url`, or S3 itself refuses.

### Item 3. The cutter's reference

**Recommendation.** E21 to E26 are the specification. The reference is `tools/parity/ngui_cutter.py`, written from E21 to E26 (not ported from the Rust, and by someone other than the Rust's author), and reviewed with this plan.
- It reads through UnityPy 1.25.2, crops with Pillow 9.5.0's `Image.crop` (whose zero padding is E23's definition), writes PNG with Pillow's `save`, and writes JSON with CPython 3.11's `json.dumps(value, indent=2)` (E24's definition). So every byte it compares comes from the oracle stack.
- The only logic of its own is selection: the sheet scope, the reference-atlas pattern, per-atlas collisions and the unit winner. That is small enough to review by reading. Its own tests use testkit atlases with hand-computed expectations.
- Its outputs on the testkit atlases are recorded as fixtures, so CI compares against recordings and needs no oracle image. The nightly runs it live.

### Item 4. The spec schema and its versioning

**Recommendation.**
- **The schema.** A JSON Schema (2020-12) per version, `docs/batch/spec-v<N>.schema.json`, written by hand from `docs/BATCH_SPEC.md` section 1's tables and embedded in the binary, which prints it (`unityrs batch --schema`). Validation is the parser's alone: no JSON Schema crate is a dependency of the binary. It states each field's type, range and presence, which a schema can express, a byte cap only as a `maxLength` of as many code points, which is looser; the byte caps and the cross-field rules (unique ids across two arrays, `M <= D`, view sizes, templates, literal keys, archive ancestry, the spool against the sink) it cannot.
- **Its tests.** Every per-field fixture spec, valid and invalid, runs through both the schema, with a 2020-12 validator that is a test dependency only, and the Rust parser, and they must agree. Every byte-cap and cross-field fixture runs through the parser alone and names the rule it breaks. A duplicate member in any object is refused by the parser's own deserializer, which sees what a schema cannot. The intentional differences, each a fixture of its own (`crates/unityrs-batch/tests/cases.rs`) that the validator accepts and the parser refuses:
  - numbers: an integer field takes only an integer token, where JSON Schema's `integer` holds any number whose value is one: `2.0`, `-0`, `1e-400` (which reads as 0) and `9007199254740991.1` (which reads as 2^53 - 1) are `type` to the parser (`BATCH_SPEC.md`'s conventions). Where both refuse, as for `spec_version`'s `2.0` (`type` to the parser, over the schema's `maximum`), it is no difference;
  - `format` is an annotation in 2020-12, so a date-time's form, the leap second's placement (RFC 3339 5.7), a URL's scheme and userinfo, its host's 253-byte cap as written and its cap as serialized, and an endpoint's query, fragment and path, are the parser's. A URL's ASCII form and its cap as written are the schema's too (a `pattern` and a `maxLength`), and both refuse past them;
  - `maxLength` counts code points, the parser bytes, so a byte cap is looser past ASCII;
  - `headers`' 64 KiB total of names and literal values, and its names compared case-insensitively for repeats (`duplicate_header`, a cross-field rule);
  - a lone surrogate escape (`"\ud800"`), which JSON's grammar admits and no UTF-8 string holds: `syntax` to the parser. A validator that reads strings as UTF-16 accepts it; this one, reading through `serde_json`, cannot read it either;
  - a number past a double's range, which the parser cannot read (`syntax`), and the depth limit of 128 levels (`syntax`), which a validator need not have;
  - the cross-field rules (`BATCH_SPEC.md` 1.1), the views' work budget among them.

  Every `pattern` is written for ECMA-262: none uses `.`, which stops at a line terminator, and a sink prefix's "any characters" is `[\s\S]`.
- **`spec_version`** is an integer, from 1. A binary reads every version from 1 to its highest, and `--version` prints the highest (E2).
- **Strict.** Unknown fields are refused at every level (`additionalProperties: false`, `deny_unknown_fields`). A misspelt budget that is silently ignored is an outage.
- **Adding a field means a new version.** In it, the field is optional, with a default that reproduces the previous version's behaviour exactly. A removal, a rename, a new required field or a changed meaning also needs a new version, and the old number keeps its old meaning.
- **Golden specs per version** (`tests/specs/v<N>/`) run in CI against every later binary, with their outputs and manifests pinned under the normalised comparison (section 5). B7c adds 22 synthetic v1 cases and a Linux CLI harness, with complete normalized heads and all eight row families. Expectations use pinned synthetic oracle recordings, independent one-pixel PNG bytes and rule assertions; no engine-output blessing command, corpus bytes or TPK-derived fixture is used.
- **Pinned consumers.** A consumer pinned to an older binary keeps writing its version, and newer binaries read it the same way. A newer field sent to an older binary is refused before any work (E1), which is the safe failure.
- **No secret is a spec field** (E7, E42), except what a signed URL carries in its query string; E42 keeps that out of every output. The manifest carries the `spec_version` it was produced under; the progress stream's `p` is its own (`docs/BATCH_SPEC.md` section 10).

**Reason.** A hand-written schema is the document consumers read. The agreement test keeps it equal to the parser, and the golden specs keep old versions working.

### Item 5. Exit code values and the progress schema

**Exit codes:** `docs/BATCH_SPEC.md` section 9: 0, 3, 4, 5, 6, 7, 69, 70, 74 and 78, their precedence, the mapping from every outcome class to a code (a budget-caused skip or failure is 5, a depth or count limit is a data reason), and the codes of `--check` and of a second signal.
- **Reason.** "Stopped", "superseded", "could not start" and "host failure" are acted on differently from a data failure, so each has its own code. The values follow `sysexits.h` where one fits. Codes 1, 2 and 64-68 are never used, so a shell or argument-parser error is never mistaken for a run's verdict.

**Progress, version 1** (NDJSON on stdout): every field, its type, the `phase` values and the `exit` line are `docs/BATCH_SPEC.md` section 10. Each line is a whole snapshot, not an event.
- **Rate.** A progress thread writes a line at least every 2 s, on `docs/BATCH_SPEC.md` section 10's terms, from a one-slot mailbox that producers overwrite. So a parent that stops reading stdout stalls only that thread, and an `EPIPE` stops progress but not the run. stderr is written only through one writer, which never blocks on a pipe, a FIFO, a character device or a socket (`docs/plans/batch.md` 2.11) and drops and counts (`stderr_dropped`) a line it cannot write and the lifecycle thread's line to a regular file or a block device, whose writes writeback can hold for minutes (`docs/plans/batch.md` A11); no thread that must end by the deadline waits on such a write (`docs/plans/batch.md` 2.11, *A held stdout*), and the panic hook writes nothing.
- **The last line** is `exit`. A killed process has none.
- **Reasons** are the fixed codes of `docs/BATCH_SPEC.md` 9.3.
- **No secret.** No URL query string, userinfo or header value appears in any field (E42).
- **Reason.** Per-input outcomes are in the manifest, so a dropped snapshot loses nothing, and a snapshot writer can never block the run.

### Item 6. The sprite affine path's tolerance

**Measured (E17, 2026-11-11): exact, so the row is Tier A.** Step 1's port (`crates/unityrs-texture/src/sprite/affine.rs`) is OpenBLAS 0.3.31's `dgesv` path for a 6 x 6 system as numpy 2.4.6's wheel runs it on the Haswell kernel: `getrf_single` hands the whole matrix to `getf2`, then `getrs` (`laswp`, `trsv` lower unit and upper), over `ddot`, `dgemv_n`, `idamax`, `dscal` and `daxpy`. The wheel's disassembly shows one fused multiply-add on that path, `vfmadd231pd` in `dgemv_kernel_4x2` (the kernels are built with `-mavx2` and no `-mfma`), which the port writes as `f64::mul_add`; Pillow 9.5.0's `_imaging` has no FMA and no AVX instruction. Its one fused multiply-add computes `y + (-1) * t`, OpenBLAS's `alpha` being -1 on that call (`getf2`'s update), which is exact, so the fused and the unfused forms round alike on every input and no system tells them apart; the port keeps `mul_add` as the kernel's order all the same. Before the port was written, a Python model of it matched `numpy.linalg.solve` under `OPENBLAS_CORETYPE=Haswell` in every bit of all 46,378 solutions of 50,000 random integer systems of `copy_triangle`'s shape (destination sides of 3 to 4,096, a shared coordinate in one of seven), and agreed on the 3,622 singular ones; the same probe on the wheel's default kernel differed on 15,702, so it tells the kernels apart. That figure is the model's. The shipped `affine::solve` is held to numpy's bits by `crates/unityrs-texture/tests/sprite_solve.rs`, on 2,000 seeded systems of that shape (`tools/fixtures/sprite_solve.py`), 116 of them singular, whose solutions `tools/fixtures/sprite.py` records as hex under the pin (`tests/fixtures/sprite_solve.json`), and by the oracle fixture's 40 cases that call `solve` (`tools/fixtures/sprite.py`: the scale, fixed-point and floating-point paths, each asserted as Pillow takes it, shears, fractions, collinear corners that solve and copy, seeded fans, singular systems, corners at the ends of numpy's conversion): 33 render, pixel for pixel; 3 raise numpy's `UFuncTypeError` for a corner it cannot convert and 1 an `IndexError` after its first copy, as UnityPy raises them; and 3 meet a zero pivot, whose Tier C images match. All 152 cases match. No corpus sprite reaches the affine path, so step 2's share has no corpus distribution to be set from, and is not needed. The measurement, the corpus's included, ran in `unityrs-dev` under Rosetta on an Apple host, which reports `fma` but no `avx2`, so it is not the reference host: it runs the Haswell kernels with the pin, which `tools/parity/oracle_env.py` confirms there, and since no corpus sprite reaches the solve, the corpus's answer does not depend on the kernel. CI's sprite step, which fails on any host without `avx2` and `fma`, checks both fixtures on the reference host. What was built of the pin: CI sets `OPENBLAS_CORETYPE=Haswell` in the sprite step's env, not the job's, since that step alone solves; `scripts/dev` forwards a pin the host set, else sets it where the CPU has `avx2` and `fma`; `tools/parity/oracle_env.py --core` reads the core the bundled OpenBLAS runs (its `get_corename`, which threadpoolctl reads), fails where a pin is set and the core is not Haswell, and reports where the host could take the pin and has none; `sprite.py` checks it before it records, and skips `sprite_solve.json` unpinned. No nightly workflow exists yet (open, below).

**Recommendation in two steps.**
1. **Measure exactness first.** UnityPy's `SpriteHelper.copy_triangle` builds a 6 x 6 system and solves it with `numpy.linalg.solve` (`UnityPy/export/SpriteHelper.py`), then samples with Pillow 9.5.0's nearest-neighbour affine transform.
   - The reference is numpy as the oracle runs it: numpy 2.4.6 linked to OpenBLAS 0.3.31 built with `DYNAMIC_ARCH`, whose `dgesv` is OpenBLAS's own factorisation, with kernels chosen by the host CPU at run time. A probe of 200,000 random integer triangles found 43 % whose solution differs in at least one coefficient bit from a reference-LAPACK-order solve. So the oracle runs that solve pin one kernel, `OPENBLAS_CORETYPE=Haswell`, the reference host's (x86-64 with `avx2` and `fma`), set in the process environment before the interpreter starts, never from Python after numpy is imported. As built: CI's sprite step sets it in its env, the one parity step that solves, and fails on a host without `avx2` and `fma`; `scripts/dev` forwards a pin the host set, else sets it where the CPU has both; `tools/parity/oracle_env.py --core` reads the core the bundled OpenBLAS runs and fails where a pin is set and the core is not Haswell, and `sprite.py` runs that check before it records. A run elsewhere without the pin, such as `scripts/dev` under Rosetta, which reports `fma` but no `avx2`, reports the affine-path comparisons as skipped; under Rosetta the pin runs the Haswell kernels too, where `oracle_env.py` confirms the core, and that is where this item's measurement, the corpus's included, ran (Measured, above). X2's CI step and X14 run on the reference host and fail on any other; X14's nightly, which is to set the pin as CI's step does, is not built (open, below). The pinned core and the reference host are in `docs/DESIGN.md` section 3's oracle table and `PARITY.md` section 1's numpy row.
   - Port the solve in the order of OpenBLAS 0.3.31's Haswell kernels as built in numpy 2.4.6's wheel, derived by disassembly, in f64, each fused multiply-add they do written as `f64::mul_add` (correctly rounded on every host) and no other contraction; and Pillow's coefficient arithmetic and sampling in each path Pillow takes, with no contraction: its manylinux x86-64 wheel is built for the baseline ISA, which has no FMA, as step 1 confirms by disassembly (no `vfmadd*` instruction in `_imaging`). So D holds and the Tier A check can match: the pin fixes the reference's bits, and X2's CI run compares against them. Compare on the testkit sprites and the corpus. Only if every pixel matches is the row Tier A.
   - UnityPy's numpy-free solver is not the reference: the oracle has numpy and never runs it (its `PARITY.md` row says so).
2. **If it is not exact, use an edge-band metric.** Where a one-ulp difference in the matrix moves a sample, a pixel takes a neighbouring texel, so its channels can differ by up to 255. A per-channel absolute-difference metric is therefore the wrong shape: every real disagreement would fail it. A share of differing pixels alone would hide a wrong triangle. So both must hold:
   - every pixel whose visible RGBA (E20's clearing) differs lies within 1 px (Chebyshev) of an edge of the sprite mesh's triangles, rasterised on the output grid;
   - the differing pixels are at most a share of the sprite's visible pixels. The share is set from the corpus's measured distribution (its maximum, with the headroom stated) and written into the `PARITY.md` row before E17's test is written.

A sprite outside the metric fails its test and is listed, never passed silently. The nightly compares such sprites by the metric, not by their visible hash.

**Reason.** Exactness would remove the row, but it is not likely: the reference's coefficients follow its BLAS kernel's order, which the port must match bit for bit. The edge band has the shape a sampling miss has, and step 2 is the plan of record unless step 1's measurement shows every pixel equal.
