# P1 plan: unityrs-core

**Status:** the plan for P1's core, ready for parallel work. The interfaces in section 3 are committed as compiling stubs on this branch (`crates/unityrs-core`, `crates/unityrs-testkit`, `crates/unityrs-dump`). The stub files are the contract: where this text and a stub's signature differ, the stub wins and this text is fixed.

**What it delivers.** A library that reads Unity bundles, serialized files and typetrees exactly as UnityPy 1.25.2 with UnityPyBoost reads them, shaped for a batch engine and Python bindings. It ends at a gate: the canonical dump of the whole private corpus and of UnityPy's samples, at L0-L3, differs from the oracle's in zero records, with no shim.

**How it was chosen.** Three candidate designs were written against the same brief: parity first, performance first, and fork economy first. Each was scored, and their factual claims were checked against rabex 0.2.1's source and UnityPy 1.25.2's (the wheel, and the UnityPyBoost C++ in its sdist). This plan starts from the parity-first design and takes from the other two what survived that check (section 0).

**Citations.** UnityPy paths are relative to the installed `UnityPy/` package of 1.25.2; UnityPyBoost paths are `UnityPyBoost/…` in the 1.25.2 sdist; rabex paths are `src/…` of the 0.2.1 crate. Every rule the core ports cites its line. Repository paths are relative to the repository root.

**Reading order for a package agent.** Sections 0 and 1, your package in section 7, the API sections it lists, section 6 (what "done" is measured by), then the stub files you own.

## 0. Decisions at a glance

1. **The core is a port of UnityPy's read and write rules, line by line, on raw bytes. This is an architecture choice, not a finding that rabex cannot be fixed.** Every format path (detection, bundles, SerializedFile, typetree nodes, both readers, the writer, the Environment) is written from the UnityPy function it mirrors, with a `// UnityPy <file>:<line>` comment on each rule. The P0 spike showed rabex fixable: with one header shim its dump of the corpus game and UnityPy's samples equals the oracle's in all 403,076 records (`docs/spikes/rabex.md` section 3), and the spike lists what a fork would change (its "Recommendation": `serde_typetree`'s read and write rules, panics into errors, allocation bounds, the metadata gates, a `(class, version)` cache key, liblzma, the writer, licence and provenance). The port is chosen because P1's other requirements are easier to meet in code shaped for them than by reshaping rabex's types: the API of section 3 (lazy files sharing `Bytes`, one meter per input, owned self-describing values the bindings convert); facts kept as read (raw bytes where rabex has strict UTF-8 `String`s, "absent" where it fills defaults, UnityPy's level jumps, which its recursive node trees refuse, and UnityPy's version arithmetic); and a zero-difference gate where every rule traces to a UnityPy line. rabex stays vendored for what the core does not replace (decision 2).
2. **rabex stays vendored, as its own crate, pristine plus a ledger** (`crates/unityrs-rabex`, library name `rabex`). The first commit is the unmodified crates.io source; every later commit is one numbered patch with its class and reason in `UPSTREAM.md`; `scripts/fork-check.sh` proves the crate equals the pristine source plus the ledger. Code the core supersedes (serde_typetree, rabex's object lookup and read paths) stays in the fork **verbatim and fenced**: no unityrs crate may call it. In P1 the fork supplies the TPK parser to `unityrs-tpk`; in P3 the UnityCN decryptor and the builders. This keeps re-vendoring and upstream offers cheap without letting rabex's types into the core. `docs/DESIGN.md` section 4 records the result: the core is a port of UnityPy's rules (Q1, decided).
3. **Buffers are `bytes::Bytes`, shared, never copied.** The input, each decoded block run, every bundle entry, every `SerializedFile`, every `TypelessData` value, every `vector<UInt8>` value and every string read from a file (`RawStr` is a `Bytes`: metadata strings, node names, `Value::Str`) are slices of one allocation. A decoded buffer carries the charge that paid for its whole capacity, and a decoder is charged before its output grows (3.15), so the books show exactly what is alive.
4. **Containers are lazy; the dump forces UnityPy's eager order.** A bundle reads its header, blocks-info and directory at open and decodes no data block. There is one layout, UnityPy's: the `b"".join` of every block's actual output. An entry's offset in it depends on the actual length of every block before it, so a lazy read first learns those lengths (a block not yet decoded is decoded with its output discarded, its length kept), then decodes the blocks it overlaps into a cached run (a block that two reads' spans share is decoded once per span, and every decode is charged to the input's meter and counted as decode work, 3.6). A lazy read that succeeds therefore returns exactly the bytes of the eager read, on every bundle, malformed ones included, and a block that fails before or inside the read fails it as it fails the eager load; a block that fails only after the read fails `load_all` and not the read, the one way a lazy read differs (3.13's difference (c)). `BundleFile::load_all` is UnityPy's load (every directory entry parsed, a failing entry fails the bundle).
5. **Typetrees compile once per type into a flat table** (kind, shape, align, dict key, minimum size per node), `Arc`-shared by every object of the type, as UnityPyBoost precomputes per node. The walker never compares strings.
6. **`Value` is UnityPy's dict model, owned and self-describing.** Float width, packed primitive runs, tuple versus list, bytes versus str, invalid UTF-8 and dict order live in the value. Dict keys are node ids into the node lists a `Parsed` carries: the root's list, then one per ref-type tree a `ReferencedObject` read through. That last part fixes a flaw in the fork-first design, whose keys could only name the root tree.
7. **Two readers and one writer, each a port of its own UnityPy code.** UnityPyBoost's reader for `byte_size > 0`, UnityPy's pure-Python reader for `byte_size == 0`, and UnityPy's pure-Python writer (UnityPyBoost has no writer), whose per-element alignment does not mirror the reader. No serde in the walker.
8. **UnityPy mode is the default everywhere.** That covers the float32 signalling-NaN quieting, the writer's alignment, the eager AssetBundle read at load, and no version fallback. `FloatMode::Lossless` and `WriteRules::MirrorReader` are opt-in and listed in `PARITY.md`.
9. **The common-string table is the 112 strings UnityPy 1.25.2's blob parser resolves**, not the 108 of its MIT enum. Corpus blobs use two of the four extra offsets, so the 108-entry table (the performance-first design's choice) fails L1. rabex's 113th string stays out.
10. **No TPK in the core or the repository.** The core defines a provider chain keyed by `(class, packed version, script)`; `unityrs-tpk` loads a TPK from a path and implements it.
11. **No panics on untrusted input, bounded work, nothing global.** Clippy denies `unwrap`, `expect`, `panic`, `todo`, `unimplemented`, `unreachable` and indexing in the core (outside tests). Everything the core allocates in proportion to an input-chosen size is charged to the input's one meter before it is allocated, so one input holds at most `Limits::max_input_memory` plus a stated constant, however many files it holds and however often it is read (3.15); every input-chosen count grows a table only as the bytes behind it are read, never sizes an allocation; arithmetic on input integers is widened or checked, as Python's integers never overflow (positions are signed `i128`); and no step is worse than linear in its input. The core spawns no threads and never waits (a source scan checks both, 4.1). No lock is held across user code but a budget's, whose contract forbids it to block or call the core, and no lazy value is computed while its cell is locked (3.16). Every public type is `Send + Sync`, checked at compile time, and a test fails when a public type is added without the check.
12. **The canonical dump lives in `unityrs-dump`, on the public API only.** The core takes on no JSON, sha256 or gzip. If the dump needs a fact the API does not expose, the API is incomplete.
13. **Five work packages run in parallel after this scaffold** (section 7): A the fork, tables, TPK and licences; B the typetree compiler, readers and writer; C streams, versions, detection, codecs and files; D providers, objects, the container and the Environment; E the dump, the CLI and the gate.

## 3. The API

### 3.1 Principles

- **As read.** Every field UnityPy keeps is exposed as read: `Option` where UnityPy has no attribute, raw bytes where UnityPy keeps a surrogate-escaped `str`, the stored integer width. The dump is written from the public API, so a missing fact is a missing accessor.
- **Handles.** Files are `Arc`s of immutable parsed data (`File`, `Arc<BundleFile>`, `Arc<SerializedFile>`); an `ObjectRef` is an `Arc` on its file and the index of its row, which it reads from the file's table on demand, so a handle copies nothing and a caller may keep or clone millions of them without duplicating the table the parse charged (`object::tests`). Everything lazily computed sits in a `OnceLock` filled only through `once::get_or_publish`: the value is computed with no lock held and then published by a move. Two threads that ask at once may both compute it; the first to publish wins, and the other's value and its charges are dropped (3.16). A fallible value goes through `once::get_or_publish_result`, which publishes the value or an error the input decides, and never a **transient** one (`CellError::is_transient`: a budget or meter refusal, an I/O failure, a provider's failure). A refusal depends on what else is held at that moment (two threads computing one value at once can cause it), so keeping it would fail every later ask of a shared dependency for the handle's life; it is returned unpublished, and the next ask computes again. A kept error is charged to the input's meter for the heap it owns (`CellError::heap_bytes`, `once::KeptError`). A compute has no side effect but its charges: what follows from a value (registering a nested container's entries) is done from the published value.
- **Context.** One `Arc<FileContext>` per load carries version policy, float mode, writer rules, providers, codecs, decryptor, budget and limits into every file of the load. The load also makes the input's meter (3.15), which every parse is passed and every file keeps (`File::meter()`).
- **Errors, not panics.** Every fallible call returns `Result<_, Error>` or a narrower error with a structural kind; the dump never parses message text.

### 3.2 Strings

- `RawStr` (`raw.rs`, scaffold): the bytes UnityPy decoded with `surrogateescape`, kept as bytes, and a `Bytes`: a string read from a file is a zero-copy slice of the file's buffer (`RawStr::from_shared`), a common string is static, and only strings the core computes allocate, each charged to the input's meter as it is made (`RawStr::charged`: `heap_cost` of the bytes plus the owner record): the decimal string of an unknown common-string offset (3.8), `pystr`'s `py_lower`, `simplify_name` and `clean_external_path`, which take the meter, and a resource candidate's whole name (`env::Candidate::joined`, `RawStr::charged_concat`). A lookup by a name an input chose (`Registry::get`, `Environment::get_cab`, `find_file`) takes the name as a `RawStr` and the meter of the file that chose it, so the lowered key it builds is charged while the lookup runs, and a name already in its simplified form is not copied. `to_str()` gives `Some` only for valid UTF-8 (a surrogate code point's three-byte encoding is invalid, as in Python). `Display` escapes. Metadata strings, node names, node types, container paths and `Value::Str` are all `RawStr`, so a typetree row that names a long local string costs a handle, however many rows name it.
- `pystr.rs` (D): `py_lower` is `str.lower()` on a surrogate-escaped string: valid UTF-8 runs lower with full case mapping (final sigma included) using Rust's tables except where `tables::lower_exception` gives Python 3.11's answer; invalid bytes pass through. `ntpath_basename` (after `splitdrive`: a drive letter or UNC prefix is dropped), `ntpath_splitext` (leading dots are not an extension), `simplify_name` (`basename(name).lower()`, `environment.py:357-363`) and `clean_external_path` (`classes/PPtr.py:68-73`).

### 3.3 The stream reader

`stream.rs` (C) is the memoryview `EndianBinaryReader` (`streams/EndianBinaryReader.py:230-285`) over a slice with its own cursor. **The position is signed (`i128`)**, as a Python `Position` is an unbounded integer that UnityPy moves with plain arithmetic: it goes negative or past the end, and the reads after it follow Python's rules, which the scaffold implements once as free functions and an oracle fixture pins (`tests/fixtures/scaffold/reader.json`, written by `tools/fixtures/scaffold.py`, replayed by `tests/scaffold_fixtures.rs`):
- `read(n)` is `py_read`: a Python slice, negative indexes from the end, a reversed range empty; the position moves by `n` whatever the slice held (size -1 sets it to the end, so `read(-1)` at 12 of 10 bytes leaves 10);
- every fixed-width read of 2, 4 or 8 bytes is `struct.unpack_from(view, Position)` (`:340-343`), `py_unpack_from`: a negative offset counts from the end and must leave the whole read before the end; the position moves only on success;
- a one-byte read (`read_u8`, `read_i8`, `read_bool`) is `unpack(fmt, read(1))` (`:91-95`): the `py_read` slice must hold one byte, and the position has moved even when it raises (at -1, `view[-1:0]` is empty);
- `align(n)` is `py_align`, Python's floor modulo from the start of the slice, with no bounds check (-7 aligns to -4);
- `read_string_to_null` is `py_string_to_null` (`:275-284`; the oracle feeds UnityPy bytes, `tools/parity/unitypy_dump.py:100`, `:446`): `re.search` clamps both bounds of the `STRING_TO_NULL_WINDOW = 32_767`-byte window into the buffer, so a negative start searches from 0; found, the string runs to the NUL, which is consumed, and the position is the absolute index after it; not found, it raises when `pos + 32_767 >= len` and otherwise returns `read(32_767)`, a slice from the position that may hold a NUL or nothing;
- a read UnityPy refuses returns `Error::OutOfBounds { what, pos, need, have }` (its `struct.error`/`EOFError`); `read_bytes` returns a borrowed slice; nothing pre-allocates from a length.

The positions that go negative, each a named test of its owner: `parse_blob` with a negative `node_count` or `stringbuffer_size` (3.8); a `SerializedFile` below format 9 whose `metadata_size` exceeds `file_size` (`SerializedFile.py:266`); blocks-info at the end with `compressedSize > Length`, read at `Length - compressedSize` (`BundleFile.py:135`, so `view[L-c : L]`); the pure-Python reader after a negative `TypelessData` length (3.10); a format-22 `byte_start + data_offset` below 0 or above `i64::MAX` (`ObjectInfo::byte_start` is `i128`).

**Counts.** UnityPy builds every metadata table with `range(count)` (`SerializedFile.py:282-308`, `BundleFile.py:145-165`), so a **negative count is zero records, not an error**, and a huge count fails only when the bytes run out. Parsers therefore grow tables record by record, reserving at most `min(count, remaining / min_record_bytes)` and never more than the input's meter still allows, so a table's length is bounded by the bytes that back it. `read_i32_array` is the exception: its `struct` format rejects a negative count (`EndianBinaryReader.py:258-264`), and it checks `4 * count <= remaining` before allocating. The bytes bound a table's length but not its memory, since a record can be one input byte (an external below format 5 is a lone NUL) and its parsed form far larger, so every table is a `limits::MeteredVec` on the input's meter: its capacity is charged before each growth (3.15), and a growth the meter refuses stops the parse with `LimitKind::InputMemory`. Two `SerializedFile`s of one input, or one entry parsed twice, charge the same meter.

### 3.4 Versions

`version.rs` (C) ports `helpers/UnityVersion.py`.
- `UnityVersion::parse(&RawStr)` matches `^(\d+)\.(\d+)\.(\d+)(.)?(\d+)?(.*)$` with Python's `re` (`\d` is any `Nd` digit via `tables::nd_digit`, DOTALL). The type character lowers to `a` 0, `b` 1, `c` 2, `f` 3, `p` 4, `x` 5, anything else 255; none at all is `f`. `packed` is `major<<48 | minor<<32 | build<<16 | type<<8 | number` as an **unbounded OR**: `Packed::Small(u128)` while it fits, `Packed::Big` beyond. Equality, hashing and ordering are on `packed`, as Python's `int` (two raw strings may pack equal). `raw()` keeps the string **without a copy**: `parse` and both chains take the file's own `RawStr` (a slice of its buffer, the parent bundle's `version_engine`, or the policy's fallback) and keep a clone, a reference count, and so does `VersionError::NoMatch`; a version string can be 32,767 bytes (`read_string_to_null`'s window, with the pattern's DOTALL `(.*)$`) and every parse of an entry keeps its own version, so a copy would be an uncharged allocation per parse (`version::tests::the_chains_take_the_files_string_so_a_version_keeps_it_uncopied`). The one heap a version owns is a `Packed::Big`'s limbs (`UnityVersion::heap_bytes`), which the file that keeps the version charges with its handle (3.15).
- **Python's digit limit.** Each group goes through Python 3.11's `int()`, which refuses a string of more than 4,300 digits (`sys.get_int_max_str_digits()`, `version::PY_INT_MAX_STR_DIGITS`; leading zeros and non-ASCII `Nd` digits count). `from_str` then raises `ValueError`, as for a string that does not match, so a group of 4,301 digits is `VersionError::NoMatch` in both chains (probe: 4,300 digits parse in every group, 4,301 raise). A 4,300-digit major, minor or build parses, but its packed integer has more than 4,300 digits and the oracle's `json.dumps` then raises, so no oracle dump can hold one (`docs/CANONICAL_DUMP.md` section 7); the core reports the exact integer.
- **From a TPK** (scaffold, implemented): `UnityVersion::from_packed(u64)` is UnityPy's `UnityVersion(int)` (`helpers/Tpk.py:464`), with an empty `raw()`, and `packed_u64` returns a packed value that fits; with the ordering this is what `unityrs-tpk` needs to pick an entry (`Tpk.py:472-481`) before C lands.
- **Chain 1, the bundle** (`files/BundleFile.py:523-536`), `resolve_bundle(engine: &RawStr, policy)`: the engine string; when it does not parse or its 16-bit major is 0, the fallback; no fallback is `VersionError::NoFallback`. It decides `flags_class` (`:113-121`) and `uses_block_alignment` (format 7 and up, or 2019.4.15 ≤ engine < 2020 at format 6; `:129-131`).
- **Chain 2, the SerializedFile** (`files/SerializedFile.py:351-360`), `resolve_serialized(own: &RawStr, parent_engine: Option<&RawStr>, policy)`: its own string (format 7 and up); when empty or `0.0.0`, the parent bundle's raw engine string (a `WebFile` parent gives none); when still empty or `0.0.0`, the fallback; then `parse`, which fails on whatever string that chain produced if it does not match.
- `VersionPolicy { fallback, force_bundle, force_serialized }`: `fallback` is UnityPy's `config.FALLBACK_UNITY_VERSION` (default `None`, as UnityPy); the two forces are unityrs options for broken headers and are reported in `ResolvedVersion::source`.

### 3.5 Detection and `parse_file`

`detect.rs` (C): `check_file_type(data, limits)` implements CANONICAL_DUMP section 4.2's eight rules in order (`helpers/ImportHelper.py:44-125`), including: a 20-byte file with no NUL raises; the U+00FA signature as UTF-8 bytes; zip only when byte 4 is NUL; gzip must inflate in full, every member, CRC and size checked, trailing zero bytes allowed, bounded by `Limits::max_inflate` (the spike's detector inflated only 20 bytes; that is wrong for rule 7). The full inflate is UnityPy's, not a unityrs policy, though `ImportHelper.py:77-83` asks for only 20 bytes: it reads them through a streaming `EndianBinaryReader` whose `read_string_to_null` tests `Position != Length` on every byte (`EndianBinaryReader.py:136-144`), and that `Length` is `seek(0, 2)` on the `GzipFile` (`:303-308`), which decompresses to the end of the last member. The oracle raises `BadGzipFile` on a bad CRC, `zlib.error` on a corrupt second member and `EOFError` on a truncated stream, each after a valid `UnityWebData` prefix. Detection inflates into a fixed scratch buffer of at most 64 KiB and keeps only the first 20 bytes and the stream's length, so it charges nothing (the scratch is part of 3.15's constant); brotli at offset 0x20; the SerializedFile header read big-endian whatever its endian byte says. `parsed_as(ty, name, is_entry)` is `parse_file`'s naming rule (`ImportHelper.py:127-156`): an `AssetsFile` named `*.resS`, `*.resource`, `*.config`, `*.xml` or `*.dat` (case-sensitive) stays raw; a zip is `Zip` only for an input.

`files::parse_file(name, data, ty, parent, meter, ctx)` (C) builds the `File` the type and name rule say, charging everything it keeps to `meter`, the input's. A container entry that is itself a container parses one level deeper (`Parent::depth`), refused past `Limits::max_container_depth` (`LimitKind::ContainerDepth`). P1 refuses `WebFile` (`Unsupported::WebFile`).

### 3.6 Bundles and codecs

`files/bundle.rs` (C) ports `files/BundleFile.py`, lazily:
- `BundleFile::open` reads the header, blocks-info and directory only. `header()` exposes every field the dump's L1 writes (signature, format, both version strings raw, the resolved engine version, `data_flags`, `flags_class`, `block_alignment`, `encrypted`, `hash`/`crc` for the web/raw layout). `uncompressed_size()`, the sum of the **declared** block sizes, is known before any decode (for a caller that plans with it, 4.1); the actual decoded total can differ (LZMA ignores the declared size, LZ4 may decode short, a stored block yields its stored bytes, a truncated block yields what is there), and the limits and the budget follow the actual bytes (below).
- The rules, each with a test: the extra byte after the data flags only for non-UnityFS signatures (`BundleFile.py:104-106`; rabex reads it for UnityFS); the flag set by engine version (`:113-121`); the decryptor check **before** the 16-byte alignment (`:123-124`, then `:129-131`); blocks-info at the end read at `len - compressed` (`:134-137`); padding at the start only under the new flags with 0x200 (`:170-171`); a truncated block read short and decoded as it is, its actual length being the dump's `compressed`.
- **One layout: UnityPy's joined data.** UnityPy always decodes every block and reads entries from `b"".join` of their **actual** outputs (`:173-186`); there is no declared layout to fall back from. Block `b` starts at the sum of the actual lengths of blocks `0..b`, so an entry's bytes depend on every block before it, not only on the blocks it overlaps. The bundle keeps one `OnceLock<u64>` per block for its actual length. A length is known at open for a stored block (its bytes read) and otherwise only by running the block's codec.
- **Lazy reads.** Before `entry_bytes(i)` or `entry_range` returns bytes ending at joined offset `X`, every block that starts below `X` has a known length: a block still unmeasured that lies wholly before the read is decoded with its output discarded (a reused scratch buffer, its length kept), and the blocks the read overlaps are decoded into a run cached in `runs` (a run is `Bytes` carrying its charge; see **Runs** below for a block two spans share). A measuring decode is charged while it runs and returns its charge after. A read whose bounds depend on the total length (a negative offset, a size of -1, a stop past the end) measures every block. Every entry is a zero-copy slice of its run. `entry(i)` parses once per handle, computed outside its cell and then published (3.1). There is no switch of layout after bytes were served, so a lazy read that succeeds returns exactly the slice of `load_all`'s joined data on every bundle, malformed ones included, and a block that fails before or inside the read fails it as it fails `load_all`; a block that fails only *after* the read fails `load_all` and not the read (3.13's difference (c)). **Block outcomes are kept**, failures included: each block's cell holds its actual length or the error its decode gave, so a failing block is decoded once and every later read that needs it fails at once, as UnityPy fails once; a refusal that depends on what else is held (the meter, the budget) is not kept (3.1). On a well-formed bundle read in directory order the measuring costs nothing (the earlier runs are already cached); reading a later entry first costs one discarded decode of the blocks before it.
- **Entry slicing.** An entry is `reader.Position = offset; reader.read(size)` on the joined data (`files/File.py:78-81`), and the memoryview `read` is a Python slice (`EndianBinaryReader.py:248-255`): size 0 is empty, size -1 reads to the end, any other size is `data[offset : offset + size]` with negative indexes counting from the end and a reversed range empty. `stream::py_read` implements that arithmetic once (in `i128`, so no `i64` offset can overflow), and the bundle, `parse_blob` and the pure-Python reader use it.
- **Eager.** `load_all()` decodes every block in order and parses **every directory entry** in directory order, a path repeated in the directory included (its earlier entry is parsed and can fail, though the `files` dict keeps the later one), and returns the first error, which is UnityPy's behaviour (a failing entry fails the bundle).
- **Codecs** (`codec.rs`, C): **None** returns the stored bytes, as a zero-copy slice of the input; **LZMA** (`helpers/CompressionHelper.py:17-44`) is a raw LZMA1 decode of the 5 property bytes plus the rest, **run to the end of the input, the declared size ignored**, capped by `Limits::max_block_output` (fewer than 5 input bytes is `struct.error`); **LZ4/LZ4HC** (`:83-94`) is `lz4.block.decompress(data, uncompressed_size)`: the declared size is a **maximum**, a shorter output is accepted, a longer one raises (the performance-first design's "must equal" is wrong), and an empty input raises whatever the declared size; **LZHAM** and unknown ids raise (`:234-235`, `BundleFile.py:515-521`; `CompressionFlags` is an `IntFlag`, so any id constructs and the map lookup is what raises). `Codecs` is a 64-slot registry (the flags' low six bits) that a user may extend; only canonical ids name a slot (`Codec::Other(5..=63)`; `Other(1)` is not LZMA, and `set` hands a non-canonical value back); `BlockDecryptor` runs before decode (UnityCN: P3).
- **LZ4 acceptance is liblz4 1.9.4's** (`LZ4_decompress_safe` under python-lz4 4.4.4), not `lz4_flex`'s. They disagree both ways: liblz4's end-of-block conditions (a literal run ending within the last 12 bytes of the declared size or the last 8 bytes of input must be the last sequence and end exactly at the end of input; a match must end at least 5 bytes before the declared size; the length-extension guards) refuse blocks `lz4_flex` decodes, and liblz4 decodes a match at offset 0 (a run of zeros) that `lz4_flex` refuses. The oracle fixture `tests/fixtures/scaffold/lz4_blocks.json` (813 blocks around liblz4's end-of-block conditions, each decoded at up to 11 declared sizes around its real output, with liblz4's verdict and output; `tools/fixtures/scaffold.py` builds them) is the codec's acceptance test, and `tests/scaffold_fixtures.rs` pins that `lz4_flex` alone fails it. C checks the sequence stream against these conditions before (or while) `lz4_flex` decodes, and handles offset 0 itself; the dependency list stays as it is.
- **A codec writes into a `DecodeBuf`** (`budget.rs`, scaffold, implemented): `BlockCodec::decode(input: &Bytes, uncompressed, out: &mut DecodeBuf)` either appends its output (`extend_from_slice`, or `grow_zeroed` then `truncate`) and returns `Ok(None)`, or leaves `out` empty and returns `Ok(Some(slice))`, a zero-copy slice of its input, which the caller checks against the same cap. A `DecodeBuf` is made on the input's meter (`DecodeBuf::new(meter, initial, cap, kind)` charges its first allocation before making it) and holds one segment per block: `begin_block(cap, kind)` starts the next block of a run, so each block is capped at `max_block_output` (`LimitKind::BlockOutput`) on its own. Every growth first checks the segment's cap, then charges the new capacity to the meter (which books it with the budget), and only then grows; capacity doubles while the meter allows it and otherwise grows to exactly what is needed, so a budget that fits the output is not refused for the doubling. A dropped `DecodeBuf` returns its charge, and `into_bytes` hands the charge to the `Bytes` (the owner record charged too). So an LZMA block declared at 1 byte that decodes towards 1 GiB is refused at the first growth the meter or the budget does not allow, before the bytes exist (`tests/decode_alloc.rs` watches the heap with a counting allocator: a refused 64 MiB growth allocates nothing, on a budget refusal, on a meter refusal and in `new`).
- **Limits on actual bytes.** `max_block_output` caps each block's actual output (blocks-info's included); the input's meter caps everything decoded, at its actual length, whichever decode made it: a first decode, a measuring decode, a re-decode of a block two spans share, a re-decode after the handle was evicted and opened again (3.13). There is no separate declared-total limit: the meter sees the actual bytes as they grow, and `uncompressed_size()` is the declared total a caller may plan with. Blocks-info's rows grow with its bytes (3.3).
- **Decode work.** Memory returns when a run drops; work does not. Every byte a block decode is granted room for (first, measuring, repeated, a decode that fails after it wrote) also counts toward the input's decode work (`Limits::max_decode_work`, default 32 GiB, `LimitKind::DecodeWork`), which is not returned while the input is open, so reads that decode, drop and decode again (thousands of blocks that each decode to the block cap, measured and dropped by a lazy read of the last entry; a block that fails after it wrote) stop at that bound instead of running without end under a meter that never fills (`budget::tests::a_decode_repeated_for_every_read_stops_at_the_work_bound`, `limits::tests::decode_work_is_counted_and_never_returned`). A `DecodeBuf` checks the bound before a growth and counts the growth only once the meter and the budget granted it, so a refused growth decodes nothing and counts nothing: a transient refusal never uses the allowance up, and the same read succeeds once there is room (`budget::tests::a_refused_growth_counts_no_work_and_the_read_succeeds_once_there_is_room`). The count is the meter's, shared by every file of the input; the Environment restarts it when it opens an evicted dependency again (`Meter::restart_decode_work`, 3.13), so the bound is per open, and eviction churn costs work in proportion to the reads that cause it (`limits::tests::decode_work_starts_again_only_when_the_meter_is_restarted`). The default is four times `max_input_memory` because a lazy read of a bundle whose entries do not overlap decodes a block at most four times (measured; decoded for the entries wholly inside it; decoded again for each of the two entries that straddle its edges, **Runs** below), where UnityPy decodes it once.
- **Budget.** The meter books every charge with `ctx.budget` under its `Reservation` (`Input` for what the caller loads, `Dependency` for what the Environment loads to resolve a pointer or resource), so a refusal names the pool that refused (`ChargeError::Budget`, `Error::Budget`) apart from the input's own bound (`ChargeError::Limit`, `LimitKind::InputMemory`).
- **Runs.** A run covers the blocks one read overlaps, contiguous, and is cached by its block span. A read whose span a cached run covers slices it; any other read decodes its own span into a new run, so a block shared by two spans (a straddling read) is decoded twice and charged twice. `load_all` decodes every block into one run, so under `Eager` the runs hold exactly the joined data. `entry_range` (a `.resS` read) is a read like any other: it measures, serves from a covering cached run, and otherwise decodes its span into a run it caches, so N ranges in one block decode it once. A hostile directory whose spans nest or overlap makes lazy reads decode the same blocks again and again; each run is charged, so it stops with `InputMemory` at the meter's limit (3.13's difference (d)), where `Eager`'s one run fits. A run is decoded with no lock held and then published into the run table under its mutex; that growth is charged, so the one caller code that runs under the mutex is the budget, whose contract forbids it to block or call the core (3.16). E's perf report counts re-decoded bytes and the peak of cached runs (R2, R3).
- **Parents.** An entry's `Parent` carries the container's name, kind and nesting depth and, for a bundle, a `Weak` handle on it (the bundle is built with `Arc::new_cyclic`), which `PPtr.deref` scans for siblings (3.13). The meter is not in the `Parent`: `parse_file` is passed it, and each file keeps it (`File::meter()`).

### 3.8 Typetree nodes

- `typetree/rows.rs` (scaffold): `NodeRow` is one node as stored (`m_Level`, `m_Type`, `m_Name`, `m_ByteSize`, `m_Version`, `m_TypeFlags`, `m_VariableCount`, `m_Index`, `m_MetaFlag`, `m_RefTypeHash`, each `Option` where the format may lack it). `NodeList::from_rows(MeteredVec<NodeRow>)` is UnityPy's stack rule (`helpers/TypeTreeNode.py:156-188`): a row nests under the nearest earlier row of lower level, so level jumps are kept as UnityPy keeps them; rows after a later top-level row are dropped, but are still processed for errors. It builds its child tables by counting (no allocation per row), each a `MeteredVec` on the rows' meter, and keeps their charges with the rows'. Implemented and tested.
- `typetree/parse.rs` (C): `parse_old(r, data, format, meter, limits)` (`TypeTreeNode.py:78-109`, iterative, `Limits::max_tree_depth`) and `parse_blob(r, data, format, meter, limits)` (`:112-154`, `:331-347`), each returning a `MeteredVec<NodeRow>`: `m_Version` is read as `i16` where UnityPy reads it so; a string offset with the high bit set is looked up in `COMMON_STRINGS` and, when absent, becomes its decimal string (`:130`), charged to the meter (`RawStr::charged`, 3.2); a local offset reads to NUL within the buffer, as a zero-copy slice of it. The node area and the string buffer are `reader.read(n)` (`:116-117`), so a negative `node_count` or `stringbuffer_size` is a Python slice that moves the position back (`stream::py_read`, 3.3), not an error. **The rows are a `MeteredVec` on the input's meter**, grown with the rows read, never sized from `node_count`, so a row table whose decoded bytes compress well (a block of repeated rows) stops at the meter's limit (`InputMemory`), not at a row count.
- `typetree/tree.rs` (B): `Tree::compile(Arc<NodeList>, &Limits)` precomputes per node what UnityPyBoost precomputes (`UnityPyBoost/TypeTreeHelper.cpp:1215-1216`): `Kind` from `m_Type` by exact match (`:1075-1103`) with the `PPtr<` prefix first (`:1105-1128`); `Shape` (what the walker does); `align` (`m_MetaFlag & 0x4000`); `key` (the first sibling with the same name) and `slot` (that key's ordinal among its parent's distinct names), so the dict collapse is O(1); `min_size` (the fewest bytes a successful read consumes, to bound pre-allocation and zero-size loops); `dup_names` and `has_registry` flags. `Shape::Vector` is only for a node whose kind the reader's switch does not handle itself (`Unknown`, `PPtr`, `Array`, `ReferencedObjectData`, `ManagedReferencesRegistry`) and whose first child's kind is `Array` (R9). Malformed shapes compile to `BadPair`/`BadVector` and fail only when UnityPyBoost's reader reaches them (a `pair` run reaches its element once its length is read, even at length 0, R10); the pure-Python reader and the writer read and write a `pair` of three or more children through its first two and an `Array` of three or more through `m_Children[1]` (3.10), so those shapes are not errors there. `Tree::compile` charges its tables to the list's meter (`TreeError::Charge`); compilation fails otherwise only on depth.

### 3.9 Values

`value.rs` (scaffold) is the contract between the readers, the writer, the dump and (P3) Python:

| UnityPy | `Value` |
|---|---|
| `int` | `Int(i64)`, or `UInt(u64)` above `i64::MAX` |
| `bool` | `Bool` |
| `float` from a `float` node | `F32(bits)` |
| `float` from a `double` node | `F64(bits)` |
| `str` | `Str(RawStr)` |
| `bytes` (`TypelessData`) | `Bytes` (zero-copy) |
| `list` read as one primitive run | `Prims(PrimArray)`; `vector<UInt8>`/`char` is zero-copy `Bytes` |
| any other `list` | `List` |
| `tuple` (`pair`; the pure-Python path's aligned primitive arrays) | `Tuple` |
| `dict` | `Dict(Map)`: `(NodeId, Value)` entries in insertion order; `insert` is `PyDict_SetItem` (a repeated key keeps its first position and takes the last value) |

`Parsed { lists, value, bytes_read, charge }` is the self-describing unit, and carries the charge for every allocation its value holds, its `lists` table included (3.15), so a value a caller keeps counts against its input for as long as it lives. **The value cannot leave its charge**: `Parsed::value` is private (`value()` borrows it), and `Parsed`, `Value`, `Map` and `PrimArray` are not `Clone`; `value.rs`'s `compile_fail` doctests pin each, every snippet written so it can fail only one way (it names the missing item bare, or asks for a `Clone` bound), because stable rustdoc does not check a `compile_fail` test's error code. **The reader builds values only through `ValueBuilder`** (scaffold, implemented): `ValueBuilder::new(meter, root)` starts the charged `lists` table; `list_index` adds a ref-type tree's list once per distinct `Arc`; `vec()` gives a `MeteredVec` for a list, map, tuple or run, whose charge `list`, `map`, `tuple` and `boxed` take over; `finish(value, bytes_read)` hands every charge to the `Parsed`. `Map` has no growth method outside tests. **`ValueBuilder::finish` is the only way to a `Parsed`** (there is no public constructor; `Parsed::new` and `Parsed::unmetered` are gone, and doctests pin both), so a caller's own value (one to write: the bindings, B's W2 matrix, tests) goes through a builder too, on `Meter::unlimited()` when it is not an input's; `Map::from_entries` builds a map a caller made itself. The types pin that every `Parsed` holds its builder's charge; they cannot pin that every allocation of a value went through the builder, because `Value`'s variants are public data (a value built from a plain `Vec`, or kept after its builder was dropped without `finish`, holds heap no charge covers). That the reader does neither is B's discipline, checked by B's counting-allocator test (7.3). `lists[0]` is the root tree's `NodeList`, and a `ReferencedObject` read through a ref type's tree appends that tree's list **once per distinct tree** (deduplicated by `Arc` pointer, so a list per ref type, not per reference); each `Map` records which list names its keys (`Map::list`, a `ListIx = u32`, tested past `u16`; past `u32` lists `list_index` refuses with `LimitKind::Count`). `bytes_read` is an `i64`: UnityPyBoost's is never negative, the pure-Python reader's is after a negative `TypelessData` length (3.10). `Parsed::field`, `entries` and `get(path)` resolve names. `size_of::<Value>() <= 40` is tested.

### 3.10 Reading

`walk/mod.rs` dispatches (`helpers/TypeTreeHelper.py:123-158`): `byte_size > 0` reads `file[byte_start .. byte_start + byte_size]` (cut at the end of a truncated file) with `boost::read`; `byte_size == 0` reads with `python::read` from `byte_start` over the whole file; then with `check_read`, `bytes_read != byte_size` is `ParseError::CheckRead { expected, parsed }`, which carries the full value (it is what `check_read=False` returns).

**UnityPyBoost's rules** (`walk/boost.rs`, `UnityPyBoost/TypeTreeHelper.cpp`), each a named test:

**The pure-Python reader** (`walk/python.rs`, `TypeTreeHelper.py:182-361`) starts at `byte_start` in the whole file, reads with the stream rules of 3.3 at any position, and **aligns relative to the file**, not the object (`align_stream` rounds the absolute position: an object at byte 1 with `[UInt8 a (aligned), UInt8 c]` reads `c` at 4 and 4 bytes where Boost reads it at 5 and 5 bytes). It differs as CANONICAL_DUMP section 7 lists: aligned primitive arrays are tuples with `UInt16`/`SInt16` signedness swapped; an aligned `SInt8` array raises `TypeError` (`other`) at every length, the empty one included, and an array of aligned `TypelessData` raises `TypeError` once it has an element (an empty one is `[]`); a negative or out-of-range string length reads as `""`; in an array whose aligned element is a vector, a negative inner length reads as `[]`, unless the inner element is an aligned primitive, whose `read_*_array` builds a `struct` format from the count and rejects a negative one (`struct.error`, `other`); arrays of aligned class elements align once and skip the registry check; a `TypelessData` length of -1 reads to the end of the file and other negative lengths follow Python slice semantics (so `bytes_read` can be negative); a read past the end of the file is `other`; and, probed on UnityPy 1.25.2:
- a `pair` with three or more children reads its first two (`:193-196`), where Boost raises;
- an aligned `pair` array reads each child through `FUNCTION_READ_MAP.get(child.m_Type, lambda: read_value(child))` (`:285-293`): a child whose type is in the map (a primitive, a `string`, a `TypelessData`) is read without its own align flag, though a non-empty `string` still aligns itself; any other child (a class, a vector, a `pair`) goes through `read_value` and keeps its flag;
- a `ReferencedObject` reads `ref_object["type"]` before anything else (a missing key is `KeyError`, `other`), and raises "SerializedFile has no ref_types" for an empty or absent list *before* the empty-class skip (no `ref_types` attribute at all is an `AttributeError`, which the dump maps to `ref_type`), where Boost skips `data`;
- a `ReferencedObject` whose `type` has no `class`, `ns` or `asm` key raises `KeyError`, and one whose `type` is not a dict raises `AttributeError` (`:89-97`), both `other`, where Boost reports `ref_type` (R14);
- a string of length 0, or of a negative or out-of-range length, returns `""` before `align_stream` (`streams/EndianBinaryReader.py:266-273`, the memoryview override), and a `string` node has no align flag of its own, so it does not align: `[UInt8 a][string s][UInt8 c]` at offset 0 with `s` empty reads `c` at byte 5 (6 bytes), where Boost aligns and reads it at byte 8 (9 bytes, R6);
- an `Array` node with three or more children reads its elements through `m_Children[1]` (`:216`, `:309`), where Boost raises "Array node must have 2 children" (R9); the writer writes it the same way (`:434`, 3.11);
- an empty array of malformed `pair`s reads as `[]` (the arity check is inside the loop), except an aligned element of fewer than two children, which raises `IndexError` (`other`) at every length, the empty one included (`read_value_array`'s aligned path takes `m_Children[0]` and `[1]` before the loop, `TypeTreeHelper.py:282-283`);
- likewise an array whose aligned element is a vector whose `Array` has fewer than two children raises `IndexError` (`other`) at every length, the empty one included (`subtype = node.m_Children[0].m_Children[1]` before the loop, `:309`), where Boost reads an empty one as `[]` (R11 reads elements one by one); a non-aligned one, or one whose `Array` has three or more children, reads an empty array as `[]`. **The general rule:** `read_value_array` reads an aligned element's `pair` children (`:282-283`) and its vector's `Array` element (`:309`) before its loop, and indexes everywhere else inside it, so a malformed shape of those two kinds fails at length 0 and any other fails only once an element is read; `tools/fixtures/pure_python_rules.py` runs every item of this paragraph that concerns an empty array or a `pair` child against both readers (section 10);
- an aligned `ReferencedObject` array element whose class is empty or whose ref type has no tree raises (`read_value(None, …)`, `ReadDetail::RefTypeNoTree`, kind `other`); everywhere else both readers skip `data`.

**Floats.** `FloatMode::UnityPy` (default) quiets an f32 sNaN as above; `Lossless` keeps the bits. `F64` keeps every bit in both modes.

**Linear dicts.** A class whose children repeat a name (`dup_names`) is the one place a read could go quadratic: `Map::insert` scans, so a hostile tree with *n* children and late repeats would cost *n*² per object. The walker never calls `insert` per child. It keeps a per-class scratch from `slot` to entry position (cleared per class read, so a registry child skipped at run time, R13, cannot misplace a later key): a first sighting pushes, a repeat overwrites in place with `Map::replace_at`. The dict keeps first position and last value, as `PyDict_SetItem`, in time linear in the children read.

**Bounds.** Every list, map, tuple and primitive run a read builds is a `MeteredVec` on `ReadCtx::meter` (the input's), so its capacity, spare or not, is charged before it is allocated; the reader hands each one's charge to the `Parsed` through `ValueBuilder` (3.9), and a refused charge is `ReadDetail::Charge` (kind `other`). To hold no spare capacity, a list first reserves `min(len, remaining / min_size, Limits::max_prealloc)` and then grows by `reserve_exact` in steps of at most `max_prealloc`, never past `len`, and a dict is sized from the compiled tree, its class's distinct child names, so neither holds more than its final length after the read. `max_values_per_object` bounds the work of one read (every `Value` built, the elements of a primitive run included: the pure-Python reader can read the same bytes again after a negative length); nesting (ReferencedObject data re-enters trees) counts against `max_value_depth`; elements with `min_size == 0` count against `max_zero_size_elements`.

### 3.11 Writing

`walk/write.rs` (B) ports UnityPy's `write_typetree` (`TypeTreeHelper.py:161-179`, `:381-458`) under `WriteRules::UnityPy`:
- W1 dispatch on the type name first, then `pair`, `ReferencedObject`, an `Array` first child, then a class;
- W2 **duck typing**: the writer takes any value Python's operations accept, not only the variant the reader makes for the node, which a duplicate-name object exercises (its dict holds one child's value under the other's node). Probed on UnityPy 1.25.2, per node kind: a `bool` node takes any value (`struct.pack('?')` uses truthiness; an empty `Str`, `Bytes`, `List`, `Tuple` or `Dict` is false); an integer node takes `Bool` and `Int`/`UInt` in range (a float, or an out-of-range int, is an error); a `float` or `double` node takes `Bool`, integers and floats (a finite float that overflows `f32` is an error); a `string` node only `Str`; `TypelessData` only `Bytes`; a `pair` node anything with items 0 and 1 (`List`, `Tuple`, `Prims` or `Bytes` of length 2 or more, a `Str` of 2 or more characters), each item written through its child's kind; an array any sized iterable (`List`, `Tuple`, `Prims`, `Bytes` as integers, `Str` as one-character strings, a `Dict` as its keys), each element under the same rules; a class with no children takes any value and writes nothing (its non-dict branch iterates no children); a class with children takes a `Dict` (`value[child.m_Name]`, W6) or any other value that has each child's cleaned name as a Python attribute (`getattr(value, child._clean_name)`, `TypeTreeHelper.py:447-455`: an `int` value satisfies a child named `real`, a `list` one named `count`, whose bound method a `bool` node writes as true), and B's fixtures record which attributes each `Value` variant's Python type has for the names its matrix uses;
- W3 strings always align;
- W4 `TypelessData` writes its length and bytes and aligns only when flagged;
- W5 arrays write the length, then each element, and **each element aligns when its node is flagged** (`:435`), then the vector or `Array` flag aligns once: the writer does not mirror the reader; an `Array` of three or more children writes its elements through `m_Children[1]` (`:434`), as the pure-Python reader reads them;
- W6 a class writes `value[child.m_Name]` for every child: a missing key is `MissingKey`, an extra key is ignored, registry scope as on read;
- W7 `ReferencedObject` data needs non-empty ref types (`:99-100`, where the reader does not raise) and a ref type with a tree: an empty class, or a matched ref type with no tree, fails (`KeyError: 'data'` on the value the reader made, which left `data` out; an `AttributeError` on the `None` node when the value has one).

The writer's output is a `DecodeBuf` on the object's meter (`walk::write`, `WriteError::Charge`), so a write is charged like a read.

`WriteRules::MirrorReader` aligns once after a primitive or pair run and writes an empty-class `ReferencedObject` without `data`, so every value it reads round-trips. It is opt-in (`PARITY.md`, Tier C).

### 3.12 Providers and objects

- **Tree resolution** (`ObjectReader.py:285-307`), `ObjectRef::tree(nodes)` (D): an explicit `nodes=` tree; else the type record's own tree (`TreeSource::Embedded`); else `ctx.providers.lookup(TreeRequest { class_id, version, script: None })` (`TreeSource::Provider(name)`); else `Ok(None)`, which reads as `ParseError::NoTypeTree`.
- **The `MonoBehaviour` script hook** needs an Environment, so it is `Environment::object_tree(obj, nodes)` (D), not `ObjectRef::tree`: when the tree came from the provider chain (not an explicit `nodes=` tree and not the type record's own: UnityPy calls `generate_monobehaviour_node` only inside `if not node:`, `ObjectReader.py:296-304`), its root type is `MonoBehaviour`, and a provider in the chain accepts script requests (`TypeTreeProvider::accepts_scripts`, UnityPy's `env.typetree_generator`), the head is read with that tree (`check_read` off), `m_Script` is dereferenced through the Environment and parsed, and the provider is asked with its `ScriptIdent`. As in UnityPy (`ObjectReader.py:332-346`), only a `ValueError` there falls back to the class tree (a null `m_Script`, a value error in the head read, the provider's miss); a dereference failure (`FileNotFoundError`, `KeyError`, `IndexError`) is the object's error. With no such provider nothing is dereferenced (UnityPy raises its `ValueError` before any deref), so in P1, where no provider accepts scripts, `object_tree` equals `ObjectRef::tree`.
- **`ProviderChain`** (`provider.rs`, scaffold, implemented) asks providers in order, first answer wins, under `(class_id, packed version, script)`: UnityPy's `CLASSES_CACHE` key (`helpers/Tpk.py:16`, `:44`), where rabex keys by class alone and so answers every later version with the first version's tree (`docs/spikes/rabex.md` section 5). It caches **answers only**, as UnityPy does (`get_typetree_node`, `Tpk.py:42-55`, raises on a miss before `CLASSES_CACHE[key] = node` at `:54`), so a miss under an input-chosen key leaves nothing behind. The cache is bounded per chain (`ProviderChain::DEFAULT_CACHE_ENTRIES`, 65,536 entries, and `DEFAULT_CACHE_BYTES`, 64 MiB of slots and keys; `with_cache_bound` sets others): past the bound an answer is returned and not kept. A lookup searches the cache through a borrowed view of the request and copies nothing. Whether an answer is kept is decided from that borrowed view too (already cached, the cache full, the entry's cost over the byte bound), and only an answer that is kept copies the request's strings into its key, so a hit allocates nothing, a key the cache will not keep (too big, or any key once the cache is full) is never copied, a cached key holds no input's buffer, and the copy counts toward the chain's 64 MiB (`provider::tests::a_lookup_copies_nothing_but_the_key_it_keeps`, `a_key_the_cache_will_not_keep_is_never_copied`). An entry counts four buckets of the table (`limits::HASH_TABLE_SHARES`: a doubling table holds up to 16/7 buckets per key at rest and 24/7 while the old and the doubled table are both live) plus its key's heap at `heap_cost` (`the_byte_bound_covers_the_table_at_rest_and_while_it_doubles`). Providers are called with no lock held, so a provider may call the chain.
- **Providers share their trees.** A provider answers every request that maps to one entry of its data with one `Arc<Tree>`, as UnityPy's `NODES_CACHE` holds one node tree per TPK class entry across versions (`generate_node`, `Tpk.py:58-88`). So the trees a chain's cache points at are bounded by the provider's data, not by how many versions an input names, and they belong to the provider, not to an input's meter (3.15's constant).
- **`unityrs-tpk`** (A): `TpkProvider::open(path)` reads a TPK with the fork's parser, picks a class's entry for a version by core's `UnityVersion` ordering (UnityPy's), converts the fork's nodes to `NodeRow`s, compiles each entry once with `Tree::compile` on the provider's own unlimited meter and keeps it (two versions that pick one entry get the same `Arc`), and answers `Ok(None)` for a class it does not have. Its `name()` is `"tpk"`.
- **`ObjectRef`** (D; the handle and its getters are the scaffold's): the file's `Arc` and the row's index (3.1); `raw_data()` (zero-copy, cut at the end of the file), `read_typetree(nodes, check_read)`, `parse_as_dict(check_read)`, `write_typetree(value, nodes, rules)`.

### 3.13 The Environment

`env/` (D) ports `environment.py:27-363`, `classes/PPtr.py:43-90` and `helpers/ResourceReader.py:10-38`.
- **Registry** (`env/registry.rs`): keys are `simplify_name(name)`; dict semantics (a repeated key keeps its first position and takes the new value); every `SerializedFile` and raw entry of a bundle is registered by its entry name **as it is parsed** (`files/File.py:76-90`), and every file loaded at top level by its name (`environment.py:154-157`). **Partial registration:** under `Eager`, a bundle whose entry fails to parse fails `load_file`, which raises before the bundle enters `files`, but the CABs of the entries parsed before it stay registered and resolvable (probed on UnityPy 1.25.2 with a bundle `[good CAB, its .resS, bad CAB]`: `env.files` is empty, `env.cabs` holds the first two). Under `LoadMode::Lazy` a bundle registers every directory entry's name at open, in directory order (a repeated path keeps its first position and its last entry, as the eager dict does), and parses an entry on first `get` (computed with no lock held, then published, 3.16). **What a slot holds:** a file the caller loaded is never evicted, so its slot may hold its handle; a dependency's slot never holds a strong handle on it, only what reopens it (its name, its `Source`, its directory index) and a `Weak` on the handle the dependency LRU keeps, so evicting the dependency frees it (below). Every registration is charged to the meter of the file that registers it: the key (`RawStr::charged`), the slot's `Arc`, three elements of the `order` vector and four buckets of the `slots` hash table: a doubling vector holds up to two elements per key at rest and three while it grows, and a doubling hash table up to 16/7 buckets per key at rest and 24/7 while it grows (`limits::HASH_TABLE_SHARES`, which the provider cache's bound uses too), so the tables' spare capacity and every growth are paid for, and only each table's fixed part (its 16-byte control tail and the allocator's rounding) is left, a constant per registry (3.15).
- **Load modes.** `Eager` is UnityPy (`load_all` at load); `Lazy` is the batch engine's. They give identical results for every read on a scene whose blocks all decode, whose entries all parse and none of which is itself a container. Everywhere else the differences are exactly these, and a test pins each: (a) **failures move**: an entry that fails to parse (or whose AssetBundle read fails) fails the whole bundle at load under `Eager` (with the partial registration above), and under `Lazy` fails only the `get` that parses it, so a sibling stays readable and an entry shadowed by a later one of the same path is never parsed; `BundleFile::load_all` under `Lazy` returns exactly `Eager`'s error; (b) **nested containers**: an entry that is itself a bundle is not a CAB under `Eager`, which registers its entries in place; `Lazy` cannot know that without decoding it, so the entry is registered under its own name until its first `get`, which answers `None` and registers its entries then, at the end of the order; `Eager` answers `None` for that key too, unless an earlier directory entry of the same path was a CAB, which `Eager` keeps under the key; (c) **block failures**: a block that fails to decode, or trips a limit, after the last byte any read needs fails the load under `Eager` (UnityPy decodes every block before any entry, `files/BundleFile.py:173-186`) and nothing under `Lazy`; (d) **overlapping spans**: under `Lazy` each read whose span no cached run covers decodes its whole span again and keeps it (3.6), so a directory of nested or overlapping spans can charge the meter past its limit (`InputMemory`) where `Eager`'s one run fits; read in directory order, a bundle whose entries do not overlap holds at most `Eager`'s run plus, a second time, each block that straddles an entry boundary. (d) is a `Lazy`-only safety divergence in `PARITY.md` (E). Opening a bundle `Lazy` therefore reads its header, blocks-info and directory only (4.1). A test runs every Environment scene in both modes and compares, asserting identity on the well-formed scenes and exactly (a), (b), (c) and (d) on the others; G5 also compares `Eager` with UnityPy on every scene (section 6).
- **`find_file`** (`environment.py:310-354`): `get_cab`, else the `CabResolver` (UnityPy walks `env.path`; the core never opens a path it was not given), loading what it returns as a dependency.
- **`deref`** follows `PPtr.py` in order (`env/pptr.rs` lists the rules): `m_PathID == 0` raises; `m_FileID == 0` is the own file; else `externals[m_FileID - 1]` by `pptr::external_index` (scaffold, implemented, pinned by `tests/fixtures/scaffold/pptr_external.json`): computed in `i64` (`i32::MIN - 1` must not wrap), the guard is only `>= len` (`FileNotFoundError`, `DerefError::FileIdPastEnd`), and then Python indexing, so a negative id counts from the end and one below `-len` is `IndexError` (`DerefError::FileIdBelowStart`). The container preload (`helpers/ContainerHelper.py:43-46`, `except (FileNotFoundError, KeyError): continue`) skips `FileIdPastEnd`, `NotFound` and `MissingObject`, and propagates `FileIdBelowStart` (`IndexError`), `RawTarget` (`AttributeError`), `Null` (never reached: the preload skips null pointers first) and `Load`. **The file's container** is its bundle for a bundle entry, and for a file loaded at top level the Environment that loaded it (`environment.py:154` passes `self` as the parent, `files/File.py:36`): UnityPy's "no container is set" is raised only for a `SerializedFile` built outside any Environment, which `Environment::deref` never sees, so the core has no such refusal (probe: two loose files `a/CAB-A` and `b/CAB-B`, A's external `archive:/CAB-B/CAB-B`, resolve to B's object in UnityPy 1.25.2; the testkit scene `loose_external_pointer` asserts it). The cleaned external path is compared with each key of the container's `files` lower-cased (no basename), then `find_file`; a raw target, or a container under an Environment `files` key, has no objects; a missing path id is a `KeyError`. Each outcome is a `DerefError` variant. `from` need not have been loaded into this Environment (a second handle a caller opened on the same bytes): its bundle siblings come through its `Parent`'s weak bundle handle (3.6), every other CAB from the Environment. **When that bundle has been dropped** (a caller kept an `ObjectRef` and dropped its bundle, which UnityPy cannot do: its `assets_file.parent` is strong), a pointer that needs the container fails with `DerefError::ContainerDropped { name }`; the core does not guess between "no sibling" and `find_file`, which could answer with another file of the same name. A caller that hands out files (the bindings, a batch engine) keeps a strong bundle handle beside each `SerializedFile` it hands out, so it never sees this.
- **Resources**: the four candidates (`basename`, `name.resource`, `name.assets.resS`, `name.resS`), each a slice of the object's path and a static suffix (`resource_candidates(&RawStr) -> [Candidate; 4]`, no copy; the whole name and its lowered key are built, charged to `from`'s meter, only while one lookup runs), `get_cab` each, then load the file's externals and the candidates as dependencies and try again, then `NotFound::Resource`. Note: UnityPy calls `environment.load_file(dependency, True)`, whose second positional parameter is `parent`, not `is_dependency`, so those loads are not marked as dependencies; the port keeps that. The CAB is resolved by that rule, but each candidate's slot is first **located without being parsed** (its source bytes and directory index). When it is an entry of the same input as `from`'s own bundle (the same source bytes and directory index), the entry is read through `from`'s bundle (its `Parent`) and the shared slot is never parsed, so neither resolving nor reading decodes anything through another handle or charges its meter or pool. The bytes are the same entry's either way, so this changes no answer.
- **Container**: `Environment::container()` builds every CAB's preload index first (`environment.py:208-216`) and lists every non-dependency `SerializedFile`'s container rows, CABs in registry order, as an iterator (`ContainerItems`; `Environment::objects` and `Registry::keys` are iterators too), so a listing allocates nothing per record. `container::read_container` reads the first AssetBundle in dict order (`m_Container` pairs in file order, repeated paths kept, and `m_PreloadTable`) into a `Container` built from `MeteredVec`s.
- **Dependencies** (what `find_file` and resource reads load, and what a caller loads with `Environment::load_dependency(source)`, the same load made directly: UnityPy has no such call) each get their own meter under `Reservation::Dependency` and are kept in an LRU bounded by `EnvOptions::dep_cache_bytes`, the sum of their meters; `load_dependency` does not add the file to `files`. Evicting one drops the LRU's handle on it, which returns its runs, its parsed entries and, for a source that can be read again (`Source::Path` re-read, `Source::Fetch` re-fetched), its bytes and their charge, once nothing else holds them; a `Source::Bytes` dependency keeps its bytes, which are the caller's. Its registry slot keeps what reopens it, and the next read opens it again (header and directory again, its decodes charged again) on the same meter, whose decode work it restarts first (`Meter::restart_decode_work`, 3.6): the evicted handle is gone, so no decode of the old open is running, and a dependency evicted and reopened by every job never exhausts its allowance. A dependency read the pool refuses evicts and retries once, then fails with `Error::Budget` naming `Dependency`; the refusal is not cached (3.1), so a later read with room in the pool succeeds. Files the caller loaded are never evicted. `EnvOptions::unitypy()` never evicts.

### 3.14 Errors

`error.rs` (scaffold, frozen) holds one `Error` with structural variants: `Detect`, `OutOfBounds`, `Malformed`, `Unsupported(Unsupported)`, `Decompress`, `Version`, `TypeIndex`, `Tree`, `AssetBundle(Box<ParseError>)`, `Entry { name, source }`, `Limit`, `Budget`, `NotFound`, `Io`. `LimitKind` names one variant per bound (`InputMemory` for the meter, `InputBytes`, `BlockOutput`, `DecodeWork`, `Inflate`, `ContainerDepth`, `TreeDepth`, `ValueDepth`, `ValuesPerObject`, `ZeroSizeElements`) plus `Count`, and a refused charge converts to `Limit` (the input's bound) or `Budget` (the pool's, tagged with its `Reservation`); `OutOfBounds::pos` is the signed reader position (3.3); `DerefError` separates `FileIdPastEnd` from `FileIdBelowStart` and has `ContainerDropped` (3.13). `Error`, `TreeError` and `ParseError` implement `once::CellError`, which says which variants are transient (never kept by a cell) and what heap a kept one owns (3.1). `walk::ParseError` is an object's L2 outcome (`l2_kind()` maps to the dump's kinds); `walk::WriteError` is L3's. All are `Clone + Send + Sync`. A new variant goes through package E (section 7.1); the enums are `#[non_exhaustive]`.

### 3.15 Limits and no panics

- **One rule: everything the core allocates in proportion to an input-chosen size is charged to the input's meter first.** Each input (a top-level file, every bundle nested in it and every file in those) has one `limits::Meter`, made by the load (`Meter::for_input`) and passed to every parse. A charge is made before the allocation it pays for, and a charge that fails allocates nothing. The charge (`limits::Charge`) lives inside what it paid for and returns when that drops, so retained results stay counted: a `Parsed` keeps the charge for its values, a decoded `Bytes` the charge for its buffer. The meter books every charge with the context's `MemoryBudget` as well, so a batch budget sees what every input holds. The sites:

  | what | charged through | test |
  |---|---|---|
  | a path's bytes (`Source::Path`) | `env::read_path`: refused above `max_input_bytes` before a byte is read; one buffer at the stat'd length, charged first and filled, then the end checked with a read into a fixed stack buffer, so a file that ends where its length says costs exactly its buffer, never a growth past it; only a file that outlasts its stat'd length (one growing while read, a pipe, a device) grows the buffer, charged as it grows, stopped at the bound; read, not mapped, because a mapping of a file another process truncates faults (`SIGBUS`) instead of failing, and it needs no new dependency | `env::tests` (a path needs only its own size from the meter and the budget) |

  A charge is `heap_cost(bytes)`, glibc's chunk for the request: the request plus the 8-byte header rounded up to 16 bytes, at least 32; and a chunk of 128 KiB or more is `mmap`ped, its request plus 8 rounded up to a page (`limits::tests::heap_cost_is_glibcs_mmapped_chunk_at_every_residue`). So a charge covers the allocator's rounding too; during a growth the old and the new allocation are both charged until the old one is freed. Charges and permits merge **by meter and by pool**, so an owner keeps one record per meter and per pool however often it grew, and the record is part of the owner's charged struct, not a growth of its own.
- **The bound.** One input holds at most `Limits::max_input_memory` (default 8 GiB) plus a constant: the `Meter` (72 bytes), and per thread reading it, that thread's stack (recursion is bounded by `max_container_depth`, `max_tree_depth` and `max_value_depth`) and detection's scratch (at most 64 KiB, 3.5). Per `FileContext`, not per input, the provider chain's cache holds at most 64 MiB of slots and keys and 65,536 entries (3.12), and providers keep their own data (a TPK's trees, one per class entry); per `Environment`, the registry's two tables' fixed parts (3.13). `tests/memory_model.rs` reproduces it (section 10): a counting allocator counts the heap in glibc chunks (`heap_cost` of each request, the unit the meter charges, so an uncharged allocation cannot hide in another's rounding) and checks that it never holds more than the meter has charged on the paths above, with no slack, each run once with an `Unbounded` budget and once with a `Counting` one (a batch's budget, whose permits are bookkeeping of their own); `heap_cost` is checked against glibc's `malloc_usable_size` at every residue below each page multiple it samples and around the 128 KiB threshold; and the two hostile inputs of round 2's review, scaled to a 64 MiB meter (twelve parses of one 8 MiB table, as overlapping directory entries make; 528 nested spans over a 32-block bundle, as lazy re-decodes make), stop with `LimitKind::InputMemory` after 7 of the 12 parses and 110 of the 528 runs, under both budgets. A caller with bigger inputs raises the limit; a batch engine's budget bounds the sum over inputs (4.1).
- **The other bounds** are on work and nesting. Defaults (scaffold): `max_block_output` 1 GiB (one block's actual output); `max_decode_work` 32 GiB (bytes decoded per open input, not returned while it is open, 3.6); `max_inflate` 4 GiB (streamed, never held); `max_input_bytes` 4 GiB; `max_container_depth` 16; `max_tree_depth` 256; `max_value_depth` 512; `max_values_per_object` 2^26 (work per object read); `max_zero_size_elements` 2^20; `max_prealloc` 2^16 elements. Exceeding one, or the meter, is `Error::Limit`/`ReadDetail::Limit`/`ReadDetail::Charge`, never a crash, and a test trips each (`limits::tests`, `budget::tests`, `env::tests`; packages B and C add one per limit they enforce). `PARITY.md` lists each as a safety divergence where UnityPy would exhaust memory or the stack, and the meter under `Lazy` as 3.13's difference (d).
- **No count sizes an allocation, no arithmetic wraps.** Table growth follows 3.3. Input integers are combined in a wider type (`i64` offsets in `i128`, `i32` ids in `i64`) or with checked operations, because Python's integers never overflow and a wrapped value is a wrong answer in release and a panic in the debug builds the no-panic tests run in.
- `lib.rs` denies `unwrap_used`, `expect_used`, `panic`, `todo`, `unimplemented`, `unreachable` and `indexing_slicing` outside tests. A stub module's `todo!()` is allowed only by its `STUB(X)` line, which the owner deletes with every `todo!()`; G6 (`scripts/stub-check.sh`) fails the gate while any `STUB(` marker, stub allow or `todo!(` in code remains under `crates/` (section 6).
- Every package adds seeded no-panic tests: its builders' output mutated by `testkit::Rng` (bit flips, truncation), 10,000 cases per module in CI, asserting `Result`, never a panic.

### 3.16 Send + Sync and threads

The crate asserts `Send + Sync` at compile time for **every** public struct, enum and trait object (`unityrs-dump` does the same for its own): `const _: () = crate::send_sync::<T>();`, in `lib.rs` or next to the type. A test (`every_public_type_is_asserted`, through `unityrs_testkit::public_types::unasserted`) scans the sources and names each public type by its full module path, so it fails when one is not asserted, even if it shares a name with one that is, and a package that adds a type adds the line beside it without editing the frozen `lib.rs`. The core keeps no global state (no statics with interior mutability), spawns no threads, and never blocks inside a call: `MemoryBudget::try_reserve` refuses instead of waiting (`tests::the_core_starts_no_thread_and_never_waits` scans the sources for thread starts, sleeps, parks, condition variables, barriers and channels). **No lock is held across user code but a budget's, and no value is computed inside its cell.** Locks are `OnceLock`s filled only by `once::get_or_publish` and `get_or_publish_result` (the compute runs with nothing held; the only thing that runs inside the cell is a move), `RwLock`s for the provider cache and the registry, and `Mutex`es for a bundle's runs and the Environment's `files` and LRU. Each is held only to look up or publish, never across a decode, a parse, or a call into user code (a `TypeTreeProvider`, `CabResolver`, `Fetch` or `BlockCodec`), and none is taken while another is held. **The one exception is the budget:** publishing may grow a table (a bundle's runs, the registry) or replace a value, and that growth or release is charged to the meter, which books it with the `MemoryBudget` (`try_reserve`), and a release returns bytes to the `PermitHome` (`release`), with the lock held. Their contract (`budget.rs`) is therefore that they never block, never call the core, and never take a lock a core caller may hold while calling the core (Python's GIL among them: a Python budget is a counter the binding keeps in Rust, never a Python callback); and that one pool is one home, so permits merge by home. So a callback may re-enter the core, even the value it is computing (the inner call computes and publishes, the outer one's value loses), and a thread holding an outside lock, Python's GIL among them, never waits on a computation that needs that lock. The price is duplicate work when two threads ask for one value at once; the loser's value and its charges are dropped. `once::tests` pin both deadlocks round 2 probed (re-entry, and a lock the compute needs held by a waiter), each failing in 10 s instead of hanging, and a source scan (`tests::every_cell_is_filled_through_the_once_helper`) fails on any cell filled outside the helper. A lock is checked by a test of each public path that takes one, re-entering it and holding an outside lock its callback needs (`provider::tests`; C's and D's, 4.1).

### 4.2 Python (P3)

`unityrs-py` maps `Environment`, `BundleFile`, `SerializedFile` and `ObjectRef` to UnityPy's classes one to one; `load()` uses `LoadMode::Eager`, so UnityPy's load errors surface where UnityPy raises them. `Value` converts to Python objects without a typetree: `Str` with `surrogateescape`, `F32` through the double widening, `Tuple` to `tuple`, `Prims::U8` to `list[int]`, `Dict` keys through `Parsed`'s lists. Every binding call into the core releases the GIL, not only reads: a `bundle.files[...]` lookup parses an entry, which may run a codec or a provider, and a Python callback re-acquires the GIL (a budget never does: the bindings' budgets are counters kept in Rust, 3.16). Because the core holds no lock across a callback and computes no value inside its cell (3.16), the GIL cannot invert against a core lock (every type is `Send + Sync`). **`fork()`**: the core holds no threads or global state, but a read in another thread may hold a bundle's run `Mutex`, a registry or provider `RwLock`, or be publishing into a `OnceLock`, and a forked child would inherit that lock held by a thread that does not exist. The rule is therefore the one PyTorch and grpcio state: no core call may be in progress in another thread at `fork()`; the bindings document it, and a `multiprocessing` user picks the `spawn` or `forkserver` start method, or forks before the first read. A child-side reset (an `os.register_at_fork` hook re-creating every lock) was rejected: the locks live inside `Arc`s the core cannot enumerate, and a `OnceLock` caught mid-publish cannot be repaired. **Back-references**: UnityPy's objects point back (`obj.assets_file`, `assets_file.parent`, `parent.environment`); the core's `ObjectRef` and `Parent` carry the file and container handles, and the bindings keep the Python wrappers they built for them (a dict keyed by the core handle) so `obj.assets_file is f` holds; each wrapper of a file keeps a strong handle on its bundle, as UnityPy's `assets_file.parent` does, so `DerefError::ContainerDropped` (3.13) never reaches Python.

## 5. The dump and the CLI

`unityrs-dump` (E) writes `docs/CANONICAL_DUMP.md` format 1 from core's public API.
- **Order** (section 5 of the format): inputs in bytewise order of their relative path; each input depth-first: its `file` record, then a `SerializedFile`'s objects in ascending signed `path_id`, or a container's entries in `files` dict order, recursively. `-j N` dumps inputs in parallel (rayon) and writes them in order, so output does not depend on `N`.
- **A failing entry fails its input**: an input whose entry fails to detect or parse gets one `file` record with `parsed_as` `"error"` and `{"kind":"parse"}`, nothing else. The dump reads each input with `BundleFile::load_all` to get exactly that.
- **JSON** is written by hand, ported from the spike's `json.rs` (string escapes as Python's `json.dumps(ensure_ascii=True)`, the metadata-string rule), never through serde. Values encode from `Value` alone.
- **L3**: each object's value re-saved with `ObjectRef::write_typetree` under `WriteRules::UnityPy` and digested as the format says.
- **Context**: `FileContext::unitypy()` and nothing else: no shim, no fallback version, no override. A TPK path (`--tpk`, the oracle image's UnityPy TPK) feeds `unityrs-tpk` for stripped objects.
- **Output**: gzip level 9, mtime 0, written to `OUT.partial` and renamed when complete; the output path must lie outside the repository (as the oracle's).

**CLI** (`unityrs-cli`, E):
- `unityrs dump PATH... | --index FILE [--kind K] [--sample N] [--name GLOB] -o OUT [--levels L0,L1,L2,L3] [-j N] [--tpk PATH]`, the same selection flags as `tools/parity/unitypy_dump.py`;
- `unityrs values CASES.json`: the spike's value-case protocol (`{"name","endian","nodes","hex"}` in, one JSON line per case out), so `tools/parity/value_cases.py` (moved from the spike and pointed at `unityrs`) drives it.

## 7. Work packages

### 7.1 Rules for every package

- **Branching.** Each package works in its own worktree: `git worktree add .wt/p1-<x> -b p1-<x> p1-core` (x in a-e). Merge order into `p1-core`: **A, B, C, D, E**, each rebased on what merged before it. Every package must pass `cargo fmt --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings` and `cargo test --workspace --locked` at every commit it merges.
- **Ownership.** A package edits only the files it owns (2.2 and below). The scaffold files are frozen: a needed change to a shared signature, an `Error` variant or a `Limits` field is written as a short request in the package's PR description and made by E in one integration commit, which the asking package then rebases on. A package that adds a public type asserts it `Send + Sync` in its own file (`const _: () = crate::send_sync::<T>();`, 3.16), so it never edits `lib.rs` for that.
- **Blocked tests.** A test that cannot pass until another package lands is committed `#[ignore = "STUB(X): <what it waits on>"]`, X being the package it waits on. G6 fails while any remains, so it cannot be forgotten: the package X un-ignores it in its own merge (the merge order puts X after the test's author, or E does it at integration), and that is in X's "Done when".
- **Dependencies.** Core's dependency list is final, its one dev-dependency (`serde_json`, pinned, to replay fixtures) included. Only A changes `Cargo.lock` (new crates `unityrs-rabex`, `unityrs-tpk`), and E (the dump's and CLI's dependency on `unityrs-tpk`). Others resolve lock conflicts by taking the merged base's lock.
- **Tests are synthetic.** Inputs are built in code with the testkit; expected results come from the oracle. A package that records fixtures adds `tools/fixtures/<package>.py` (runs in the oracle image, builds inputs in code, runs UnityPy 1.25.2, writes the inputs as hex and UnityPy's results as small JSON under `crates/unityrs-core/tests/fixtures/<package>/`, one case per line, with a `--check` mode that regenerates and compares); `cargo test` replays them without Python. The scaffold's own fixtures are the model: `tools/fixtures/scaffold.py` writes `tests/fixtures/scaffold/{reader,pptr_external,lz4_blocks}.json` (the reader's position rules, `external_index`, and liblz4's verdict on boundary LZ4 blocks), and `tests/scaffold_fixtures.rs` replays them. No corpus byte, name or path enters a commit.
- **No stubs at merge.** A package deletes its `STUB(X)` allow and every `todo!()` in the files it owns; `scripts/stub-check.sh` lists what remains (G6).
- **Milestones.** Each package pushes its interface milestone first (listed below); other packages may merge that branch into theirs read-only to unblock tests, since files do not overlap.

The base-layer decision is relabelled: yes.** The core supersedes rabex's container, SerializedFile, typetree and serde code, so `DESIGN.md` section 4 now says the core is a port of UnityPy's rules on raw bytes, chosen as an architecture (decision 1: the spike showed rabex fixable), with rabex vendored pristine plus a patch ledger for the TPK reader (P1) and UnityCN and the builders (P3).
- **Q2. The four TPK-derived common strings stay in the generated table**, provenance recorded in `about.hbs` and the generator: they are Unity's own type names, needed to read files that use them, and ship in UnityPy's MIT repository.
- **Q3. `LoadableReference` (offset 1209) reads as `"1209"`**, UnityPy 1.25.2's Tier A answer; naming it is a candidate opt-in for later, not in P1.
- **Q4. `unityrs-rabex` is not published in P1** (`publish = false`): publishing needs a name and a maintenance promise.
- **Q6. UnityPy mode stays the default in P1**; `Lossless`/`MirrorReader` remain opt-in, revisited when the public API is stabilised for the bindings (P3).
- **Q7. UnityWeb, UnityRaw and WebFile wait for P3**, refused in P1 with a named `Unsupported`.
- **Q8. `py_lower`'s Unicode table follows the oracle's Python** (3.11, Unicode 14.0), and moves with it.
- **Q9. The defaults stay** (3.15): `max_input_memory` 8 GiB and `max_input_bytes` 4 GiB. The largest corpus bundle is far below both, so one input fits a 12 GiB process, and a caller with bigger inputs raises them explicitly; a batch bounds the sum over inputs with its budget (4.1). Round 2 replaced the per-path limits (`max_bundle_uncompressed`, `max_metadata_records`, `max_tree_rows`) with the one meter, because a bound per path missed the paths that re-read the same bytes.
- **Q10. Lazy mode's difference on nested containers is accepted** (3.13, (b)): exactness would mean decoding every block before each entry at open and giving up the headers-only registry phase, and nested bundles are not expected in real builds.
- **Trusting declared block sizes as an opt-in: no**, not in P1: UnityPy ignores them for LZMA and treats them as a maximum for LZ4 (3.6), and an opt-in would be a second layout to test.
