**Conventions.**
- *bytes*: an integer count of bytes. *ms*: an integer count of milliseconds.
- *Bytewise order*: the order of the strings' UTF-8 bytes, compared as unsigned bytes, a shorter prefix first.
- *Refused at validation*: the binary exits 78 before any work (section 9).
- `M`, `D` and `I` abbreviate `max_decoded_bytes`, `dep_cache_bytes` and `max_inflight_uncompressed_bytes`.
- A number is read as the nearest IEEE 754 double, correctly rounded with ties to even, as Python's `json` reads it (`9007199254740991.4` reads as 2^53 - 1, `9007199254740991.5` as 2^53), and the rules judge that double; a number past a double's range (`1e400`, a 400-digit integer) is no number the parser reads: it is `syntax`, wherever it is, an unknown member's value included. Every integer field is at most 2^53 - 1, so every JSON parser reads it exactly. A value whose magnitude, so read, passes 2^53 - 1 is out of range (`range`), whatever its token (`-1e300`, `9007199254740991.6`, which reads as 2^53). Otherwise any token other than an integer token, a fraction, an exponent or `-0`, is of the wrong type (`type`): `1.0`, `1e2`, `1e-400` and `9007199254740991.1`, which reads as 2^53 - 1, among them. `spec_version` is read by its token: the integer token `1` is version 1; any other integer token that fits in 64 bits (`2`, `-3`, `18446744073709551615`) is an unknown version (`version`); every other number, a fraction or an exponent token, `-0`, or an integer token too long for 64 bits (`2.0`, `2.0000000000000000001`, `1e-400`, a 21-digit integer), and every other value, is `type`. The engine computes in `u64` with checked arithmetic, and the ranges below keep every sum it forms below 2^63.

## 1. The job spec

A spec is one JSON object, at most 64 MiB (an average of about 670 bytes per input at 100,000 inputs), UTF-8, in a regular file: a `JOB.json` of another type, or a longer one, is refused at validation (`bad_spec`). An unknown field at any level, a duplicate member in any object, a value of the wrong type and a value out of its range are refused at validation. `docs/batch/spec-v1.schema.json` (JSON Schema 2020-12) is written by hand from these tables; it covers each field's type and range, a byte cap only as a code-point bound, an integer as JSON Schema's `integer`, which also holds `1.0`, and the byte caps and the cross-field rules are the parser's alone (`extract.md` section 3, item 4). `unityrs batch --schema` prints the schema of the binary's highest `spec_version` alone, as one JSON document with no progress line (9.1); an earlier version's is its file above.

**Cross-field rules**, each refused at validation:
- `M <= D` and `M + D <= I` (`batch.md` 2.2).
- Every `id` is unique across `inputs` and `dependencies`.
- No two names of one bundle's `headers` are equal compared ASCII case-insensitively (1.2).
- `http.backoff_max_ms >= http.backoff_initial_ms` (1.4).
- Every id in a `deps` list names a bundle of the spec, and no list repeats an id or holds more than `max_view_bundles` ids.
- No view (section 4.2) holds more than `max_view_bundles` bundles, and the views' check stays within its work budget of 2^24 ids (`max_view_bundles` above).
- With a directory sink, `spool.dir` and `sink.root`, compared as paths, component by component (so a trailing or repeated `/` and a `.` component count for nothing), neither equal nor contain one another (preflight compares their real paths again, section 6.2).
- An object store's `endpoint` whose host is an IP address has `path_style` true: `<bucket>.<address>` is not a host (1.6).
- A `bucket` with an uppercase letter or `_` has `path_style` true: as a host name it would be lowercased, reaching another bucket, or refused (1.6).
- `deadline` is set when `sink.kind` is `"object_store"`: it bounds when an attempt's process has ended, from which the caller's wait counts (section 7.2).
- Every `prefer` entry whose `input` is not null names an input.
- Every template parses and passes its literal checks (section 2.1), and every literal key (`prefer`'s keys, `archives`' keys) passes section 2.3's rules but `prefix_conflict` and `archive_conflict`, which phase 6 decides. A non-empty sink prefix passes them without its final `/`.
- `archives`' keys are unique, and none is an ancestor of another (`a` of `a/b.zip`). In one archive, each member `kind` appears once.

### 1.2 Bundle (an item of `inputs` or `dependencies`)

| field | type | required | default | allowed values and meaning |
|---|---|---|---|---|
| `id` | string | yes | | 1-1,024 bytes of UTF-8, with no control character as 2.3's `control_char` counts one (below U+0020, or U+007F) and none of U+0080 to U+009F, the C1 controls, which a key's file system or terminal may also act on (`format`). The bundle's identity (section 4.1) |
| `path` | string | one of `path`, `url` | | an absolute path of a regular file on a local filesystem (network filesystems are out of scope in version 1) |
| `url` | string | one of `path`, `url` | | an `http` or `https` URL with no userinfo. Checked in this order, all before it is parsed: ASCII as written, the string's bytes (`format`); at most 16 KiB as written (`range`); its host as written at most 253 bytes (`range`): the bytes after the scheme's `:` and every `/` or `\` that follows it, up to the next `/`, `\`, `?` or `#`, after the last `@` there and before a port's `:` (a `:` outside brackets, where any `[` opens them and any `]` closes them, as the `url` crate reads a host), tabs and newlines left out. Then, in this order: a URL that does not parse, or that is not `http` or `https` or has userinfo, is `format`; then one over 16 KiB as the `url` crate serializes it, its percent-encoding included, is `range`, so a URL that breaks its form is `format` however long its serialization. So a caller percent-encodes a path and writes a host in punycode (`xn--`) itself: the engine takes neither raw. An `https` server's certificate must chain to a root `webpki-roots` compiles in: version 1 reads no host CA store, so a private CA fails each try (`connect`, its detail `tls`, 1.4) |
| `headers` | object | no | `{}` | only with `url`: a bundle with no `url` that gives the member at all, `{}` included, is refused (`headers_without_url`); at most 32 headers, whose names and literal values total at most 64 KiB. Header name → a string of at most 16 KiB, or `{"env": NAME}`, NAME 1 to 256 bytes (`range`) of `[A-Za-z_][A-Za-z0-9_]*` (`format`), read from the environment at preflight, once per variable however many bundles name it, into one shared value: an unset or empty variable exits 69 (`header_env_missing`), one over 16 KiB exits 69 (`header_env_too_long`). `Host`, `Content-Length`, `Transfer-Encoding`, `Connection`, `Range` and `Accept-Encoding` are refused. Names are HTTP tokens compared ASCII case-insensitively, for that list and for duplicates (1.1); any other name, `Authorization` among them, is sent as given. A value's UTF-8 bytes are only tab, space, visible ASCII and 0x80-0xFF: a literal value outside that set is refused at validation, an env value exits 69 (`header_env_invalid`) |
| `size` | integer | no | | 0 to 2^53-1: the expected byte count |
| `sha256` | string | no | | 64 lowercase hex digits: the expected digest |
| `deps` | array of string | no | `[]` | the ids this bundle needs (E11). A dependency may list its own |

Every bundle is staged into the spool before extraction (`batch.md` 2.5), and every read of it reads the staged copy. A `size` or `sha256` that does not match the staged bytes fails the bundle (`integrity_mismatch`). A bundle over `M` bytes, by a stated size or by its body, fails before its bytes are claimed (`limit(input_bytes, <M>)`), since no meter could read it. A local path that does not exist or cannot be opened fails it (`source_missing`), one that `fstat` shows is not a regular file fails it (`source_not_regular`; the open is non-blocking, so a FIFO cannot hold it), and one written while it is copied fails it (`source_changed`). For local sources, check both supplied size and initial `fstat` size against `M` before claims; claim and copy the initial `fstat` length. Re-stat after copying or early EOF: changed metadata (timestamps at full precision) is `source_changed`, unchanged early EOF is `host_io`; after a complete unchanged copy, check expected size before SHA-256. Every bundle in a view must be an AssetBundle file; a member that is not fails its inputs (`dependency_failed(<id>, not_a_bundle)`).

### 1.4 Http

| field | type | default | allowed values and meaning |
|---|---|---|---|
| `idle_timeout_ms` | integer | 30000 | 1,000 to 600,000: a try fails (`"timeout"`) when no body byte arrives for this long. A try spans its redirect hops, and a retry starts again from the bundle's `url`. This timer and the rate floor run from the try's start, after taking its lookup token and before its first hop's resolve, and count only the final response's body data bytes, never a head, a 1xx or 3xx response, TLS's bytes or chunk framing; they leave out the time the engine spends writing what arrived to the spool (`batch.md` 2.5) |
| `min_rate_bytes` | integer | 1024 | 1 to 2^30: a try also fails (`"timeout"`) when fewer than this many bytes arrive in a period of `idle_timeout_ms`, the periods counted back to back from the try's start. There is no whole-request timeout, so a download slowed by its neighbours takes longer and fails only below this floor. A staged bundle is at most `M` bytes, so with the floor every try ends |
| `connect_timeout_ms` | integer | 10000 | 100 to 60,000: every client's, the store's included (E37): one timer per connection, so per redirect hop, over the name's resolution, the TCP connects to its first 16 addresses at most, one at a time in order, each given the time left divided by the addresses left, and, for `https`, the TLS handshake; the connection is up when the last of these ends |
| `attempts` | integer | 3 | 1 to 10: tries per download, the first included |
| `backoff_initial_ms` | integer | 500 | 0 to 60,000 |
| `backoff_max_ms` | integer | 30000 | at most 600,000, and at least `backoff_initial_ms` (1.1) |
| `retry_on` | array of string | all six | a subset of `"connect"`, `"no_response"`, `"timeout"`, `"truncated"`, `"status_5xx"`, `"status_429"`, none twice (`range`, at the later of the two items): the try classes below that retry |
| `redirects` | string | `"same_origin"` | `"same_origin"` or `"none"` |

- The k-th retry waits `min(backoff_max_ms, backoff_initial_ms x 2^(k-1))`, with no jitter. Of multiple `Retry-After` fields, the largest valid value (nonnegative decimal seconds or an HTTP date) raises that wait, still capped at `backoff_max_ms`. Malformed values are ignored; decimal overflow saturates to the cap and a past date means zero. Dates are not comma-split. Use only the final response of a retryable try; a redirect-only value does not carry to another hop.
- A try's lookup runs on a thread of its own (`batch.md` 2.5): `connect_timeout_ms` ends the try, not the lookup, which only the host resolver's own timeouts bound (`batch.md` A17), and the request's next try waits for it. The engine uses no proxy, and reads no `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY` or `NO_PROXY`.
- Check the cutoff before and after every wait, after lookup-token acquisition, and immediately before a try. No retry starts when its wait would pass the stop cutoff (the deadline less the grace, E7). A request in flight at a stop is abandoned: nothing polls it after the hand-over, and it ends at the process's exit (`batch.md` 2.11).
- `"same_origin"` follows at most 5 redirects whose scheme, host and port equal the request's, with its headers. A redirect anywhere else, past the fifth, with a `Location` over 16 KiB in a head within 1.4's caps, or whose next URL, as the `url` crate serializes it, is over 16 KiB fails the download (`redirect_refused`), as does a joined URL carrying userinfo, refused before connecting. Its detail is `status <N>`, never the Location. Multiple Location fields mean no usable Location, so the final status is not retried. The URL form and size checks apply to every next URL, so a header never reaches another origin. `"none"` fails at the first redirect.
- **A try's class.** A try succeeds on a 200 whose body arrives whole. A try that fails takes the first row that matches; a head both over a cap and malformed, or cut short, takes whichever row `hyper` meets first, a transport outcome (`batch.md` section 1, D's second limit). While tries remain it is retried when its `retry_on` member is listed, and the last try's `detail` is the `bundles` row's (7.3):

  | class | the try | `detail` | `retry_on` member |
  |---|---|---|---|
  | connect | fails before the connection is up: a name that does not resolve, a connection refused or unreachable, `connect_timeout_ms`, or a TLS handshake that fails, a certificate the roots do not chain among them (1.2) | `connect`, or `tls` for a failure rustls reports (a certificate, an alert, a protocol error); a close or reset during the handshake is `connect` | `connect` |
  | head too large | a head, a 1xx's included, that `hyper` refuses for its size (`Error::is_parse_too_large`): a complete head over 128 KiB, or 128 KiB received with the head unfinished; more than 100 fields (`hyper`'s default); a header name of 64 KiB or more; or a `Content-Length` of 2^64-2 or 2^64-1 | `head_too_large`; a store request's is 1.6's `no_response` | none: never retried |
  | no response | sent its request, or part of it, and the connection closed or was reset before a complete response head, or a head, a 1xx's included, was malformed (its status line, a header, a `Content-Length`) | `no_response` | `no_response` |
  | timeout | `idle_timeout_ms` or the rate floor, which run from the try's start, so they cover its connects, when they fire before `connect_timeout_ms`, and the waits for its heads; or a 408 | `timeout`, or `status 408` | `timeout` |
  | truncated | a body that ends before its `Content-Length`, a chunked body that ends without its last chunk or holds a malformed one, a trailer section of 128 KiB or more or of over 100 fields, which a retry repeats, or a reset mid-body | `truncated` | `truncated` |
  | a 5xx, or a 429 | answered with that status | `status <N>` | `status_5xx`, or `status_429` |
  | any other status | any other status the client returns as final: a 4xx; a 2xx but 200; a 101, the one 1xx `hyper` returns (it skips the others, `src/proto/h1/role.rs`); a 3xx the engine does not follow: any but a 301, 302, 303, 307 or 308, and one with no `Location` or one that does not join to a URL; and a redirect the rule above refuses (`redirect_refused`) | `status <N>` | none: never retried |
- Every request sends `User-Agent: unityrs/<version>` and `Accept: */*`; a bundle's `User-Agent` or `Accept` replaces its default, while store requests keep the engine values. Every request sends `Accept-Encoding: identity`, and no body is decompressed. Before any body is read, in this order, the first that fails naming the reason: a `size` above `M` (`limit(input_bytes, <M>)`); a `Content-Length` other than `size` (`integrity_mismatch`); a `Content-Length` above `M` (`limit(input_bytes, <M>)`), each below 2^64-2; 2^64-2 and 2^64-1 are `head_too_large`, and a larger one is malformed (no response). Check supplied size against `M`, then reserve it at each try's start, before networking. Content-Length alone never reserves the body. During streaming, exceeding `M` takes precedence over exceeding expected size; reject before the violating claim or write. Integrity mismatches and input-byte limits are permanent, never transport retries. A try that fails waits for its outstanding write, truncates its file successfully to zero, and only then returns its spool claim before the next try; a failed truncate retains the full claim.

The body timers exclude the spawn-to-completion interval of the stage's own outstanding spool write, preserving the rate-window remainder. Other stages keep running. At an exact expiry/data tie on the injected clock, expiry wins; staging tests must pin the equality boundary.

### 1.6 Sink

One sink per job. Outputs are written to it as loose objects, and each archive (section 1.7) is written to it as one more object.

| `kind` | fields |
|---|---|
| `"directory"` | `root` (required): an absolute path of an existing directory |
| `"object_store"` | `bucket` (string, required: 3 to 255 bytes of ASCII letters, digits, `.`, `-` and `_`); `region` (string, required: 1 to 64 bytes of ASCII letters, digits, `-` and `_`); `prefix` (string, default `""`, else ending in `/`; at most 512 bytes, so the run's fixed keys, at most 128 bytes past it (7.1), pass 2.3's `too_long`); `endpoint` (an `http` or `https` URL with no userinfo, query or fragment, its path empty or `/`, checked as 1.2's `url` is but for its caps: ASCII, at most 1 KiB as written, its host as written at most 253 bytes, before it is parsed; then its form (`format`: the scheme, no userinfo, query or fragment, the path); then at most 1 KiB serialized (`range`); or null, default null: AWS; an `http` endpoint allows plain HTTP to that endpoint only, and an `https` one, AWS's included, is trusted as 1.2's URLs are); `path_style` (boolean, default `false`); `timeout_ms` (integer, default 30000, 1,000 to 300,000, per try, below); `attempts` (integer, default 3, 1 to 10: tries per request, the first included) |

**`endpoint`** is the service's URL without the bucket (`https://s3.example.net:9000`). The engine maps it for each mode: with `path_style` true, requests go to `<endpoint>/<bucket>/<key>`; with `path_style` false, to `<scheme>://<bucket>.<host>[:<port>]/<key>`, which the engine builds from it. With `endpoint` null, AWS's endpoint for `region` in the same mode.

**`timeout_ms`** times a try's whole request, its body's upload and the response's read included, as `object_store`'s own client `timeout` does, so a 16 MiB part must go up within it: set it to at least 16 MiB x (`download_concurrency` + 1) / the uplink's rate: at `download_concurrency` 8, the default 30 s needs about 40 Mbit/s. Where that passes 300,000 ms, lower `download_concurrency`.

Every key is written at the sink's root (directory) or after its prefix (object store). The engine makes every try of a store request itself, waiting between tries as `http`'s backoff rule says (1.4), and the store client retries nothing, so each try is seen and counted (7.3). The engine's own HTTP service records each try's status, `Retry-After` and the S3 error code its body names, at any status (`batch.md` 2.9), and the try is classified by the first row that matches:

| the try | settled | retried, while tries remain |
|---|---|---|
| a failure before the connection was up (1.4), so nothing was sent: a resolve, connect or TLS failure, or `timeout_ms` during them (section 10's `connect` or `tls`) | yes | yes |
| no response otherwise: before a status, a `timeout_ms`, a dropped connection or a head over 1.4's caps; at any point, a try a stop abandoned (`no_response`) | no | yes |
| a 5xx; a 2xx the call still returns as an error (a body holding an `<Error>`, one past the connector's cap, or an `ETag` the engine keeps over 100 bytes, `batch.md` 2.9) | no | yes, `Retry-After` raising the wait as in 1.4 |
| a 2xx | yes | no: success |
| a 408 or a 429 | yes | yes, `Retry-After` raising the wait |
| a 304, 409 or 412, or an `If-Match` write's 404, on a head write | yes | no: read back (7.2) |
| a 404 on a head's read-back | yes | no: no head (7.2) |
| a `NoSuchUpload` on a retried `CompleteMultipartUpload` | yes | no: a HEAD of the key, whose expected ETag means `written` (E37), else `publish_failed` |
| a 4xx whose error code is `ExpiredToken` | yes | no: `credentials_expired` |
| any other 3xx or 4xx | yes | no: `publish_failed` |
| anything else | no | no |

A body that fails, or a `timeout_ms` that fires, once its status arrived leaves the try its status's row, a 2xx's being a 2xx the call returns as an error, with section 10's `truncated`. The table classifies every try of a transfer, a row-file write, a head write, a head's read-back, a phase-7 LIST and the HEAD after `NoSuchUpload`. For a head write or its read-back, a row that gives `credentials_expired` or `publish_failed` gives 7.2's outcome instead: a `running` write exits 69, a final write records 4. A phase-7 LIST that fails degrades as `batch.md` 2.9 says (`resume_list_failed`, `verify_list_failed`), and a HEAD that fails gives `publish_failed`. Preflight's requests and every abort use only the first two columns, with their own outcomes: the bucket proof takes any 2xx as proof, whatever its body (7.2), and an abort's `NoSuchUpload` counts as a successful abort, in the run, in the finisher and at the spool's start (6.2). After a stop, no try is retried by this table; 7.2's rewrites still run (`batch.md` 2.11). A try of an output, archive or row-file request that is not settled is counted in `unsettled_tries` (7.3). Credentials come from the environment only (E37): `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, and `AWS_SESSION_TOKEN` when set and not empty, as AWS's own tools read it. Either of the first two unset or empty exits 69 (`credentials_missing`). Each of the three values is printable ASCII: every byte is a tab (0x09) or in 0x20 to 0x7E, space to `~`, as the store's issued credentials are. An access key id or a secret over 128 bytes, a session token over 16 KiB, any of the three holding any other byte (one that is not ASCII, or a control character), or an `AWS_CREDENTIAL_EXPIRATION` set but not RFC 3339 exits 69 (`credentials_invalid`): the key id and token go into request headers, and the secret only keys the signature. The caller gives credentials valid until the deadline: when `AWS_CREDENTIAL_EXPIRATION` (RFC 3339, as the AWS CLI exports it) is set and comes before the deadline, preflight exits 69 (`credentials_expire`); a request the store refuses with `ExpiredToken` fails with `credentials_expired`, and is not retried.

## 2. Templates and keys

### 2.1 Templates

```
template = 1*( literal / variable )
literal  = 1*( any character but "{" and "}" / "{{" / "}}" )
variable = "{" name "}"
```

`{{` and `}}` write one brace. An unknown variable, or one not allowed for the template's kind, is refused at validation.

| variable | value | allowed in |
|---|---|---|
| `input`, `safe_input` | the input's `id` | every template |
| `type` | the object's class name: `Texture2D` or `Sprite` | `textures`, `sprites`, and archive paths of kind `texture` or `sprite` |
| `name`, `safe_name` | the object's `m_Name` | as `type` |
| `path_id` | the object's path id, signed decimal, no leading zero | every template; an atlas's is the MonoBehaviour's |
| `atlas`, `safe_atlas` | the atlas MonoBehaviour's `m_Name`, as 4.4 step 1 reads it | `sprite_key`, `json_key`, and archive paths of kind `atlas_sprite` or `atlas_json` |
| `sprite`, `safe_sprite` | the `mSprites` element's `name` | `sprite_key`, and archive paths of kind `atlas_sprite` |

A plain variable is written verbatim: a name's stored bytes. Its `safe_` form is `safe()` of the same value (2.2). There is no `{container}` variable in version 1 (E27).

**Literal checks at validation.** What the literals fix is checked on the template: each `/`-separated segment made only of literals passes section 2.3's segment rules (`empty_segment`, `dot_segment`, `segment_too_long`, `reserved_name`); a template that starts with a literal passes `leading_slash` and `reserved_prefix` on it, the key `_unityrs` itself refused when that literal is the whole template; one that ends with a literal passes `trailing_slash`. Everything else is checked on each expansion.

### 2.2 `safe()`

1. Decode the bytes as UTF-8, each invalid byte becoming one code point of its own (UnityPy's `surrogateescape` gives the same count).
2. Replace every code point outside `[A-Za-z0-9._-]` with `_`.
3. Strip every leading and trailing `.` (Python's `str.strip(".")`).
4. An empty result becomes `unnamed`.

### 2.3 Key rules

A key is the template's expansion. It is checked as given, then after the sink's prefix is put before it. The first rule it breaks names the refusal:

| rule | refused when |
|---|---|
| `empty` | the key is empty |
| `not_utf8` | it is not valid UTF-8 |
| `control_char` | it holds a code point below U+0020, or U+007F |
| `leading_slash`, `trailing_slash` | it starts or ends with `/` |
| `empty_segment` | it holds `//` |
| `dot_segment` | a segment is `.` or `..` |
| `segment_too_long` | a segment is over 255 bytes (`NAME_MAX`) |
| `too_long` | the full key is over 1,024 bytes |
| `reserved_prefix` | it is `_unityrs` or starts with `_unityrs/` (section 7) |
| `reserved_name` | a segment starts with `.unityrs-tmp-` (the directory sink's temp files, E62) |
| `prefix_conflict` | it is an ancestor of another key of `P` or of an archive's key (section 4.6), or, for a member path, of another remaining member's path (section 4.7) |
| `archive_conflict` | it equals an archive's key or lies under one (section 4.6) |

An expansion stops at 1,025 bytes (`batch.md` 2.6 step 5), so a key or member path past 1,024 bytes is read no further: it is `too_long` unless a rule before `too_long` in the table breaks within its first 1,025 bytes. A rule that needs the key's end is not applied to such a key (`trailing_slash`, `dot_segment` of its last segment, and `not_utf8` of a code point cut at byte 1,025), and a break past byte 1,025, a `control_char` among them, is not seen: the key is `too_long`. So a key's refusal is the same however much of it an attempt made. The check after the prefix reads the prefix and the key together by the same rule.

A literal key that breaks a rule is refused at validation. An expanded key that does is the output's object-level skip, `unwritable_key(<rule>)`. The rules are the same for every sink, and an archive member path takes every rule but `reserved_prefix`, `reserved_name` and `archive_conflict` (section 4.7), so a key is writable in one sink exactly when it is writable in all of them.

## 3. Selection

What one input exports (E66):
- **Textures**, when `outputs.textures` is set: every Texture2D object of the input's own SerializedFiles. A sheet section 5 cuts is exported too, as the unit's texture (section 4.5).
- **Sprites**, when `outputs.sprites` is set: every Sprite object of the input's own SerializedFiles. The sheet a sprite renders from may be in a dependency (`batch.md` 2.6).
- **Atlases**, when `outputs.atlases` is set: section 5.

The input's **own SerializedFiles** are the SerializedFiles among its bundle's top-level files, as `BundleFile::files()` gives them: UnityPy's `files` dict, where a later directory row of a repeated path replaces an earlier one in its place. A nested container's files are not selected, where UnityPy's `env.objects` and `env.container` reach them; each such container is a `nested_container` diagnostic (7.3). Selection opens each of the input's top-level directory rows, in directory order, one `files()` shadows included; one that fails to open (a WebFile, `unsupported`) fails X as `batch.md` 2.7's bytes row says (`entry_error`, naming the first such row in directory order), so a cut never meets such a row of X. UnityPy parses a WebFile row and goes on.

A texture is exported only in the five formats of E15, and only where UnityPy 1.25.2 neither unswizzles nor byte-swaps it:
- any other format is skipped, `unsupported_format(<name>)`;
- a texture for which UnityPy's `is_switch_swizzled` holds (`helpers/TextureSwizzler.py`: platform Switch, platform blob of at least 12 bytes, more than one GOB per block) is skipped, `unsupported_platform(switch)`;
- an Xbox 360 texture of a format UnityPy byte-swaps (`XBOX_SWAP_FORMATS`; of the five, DXT1 and DXT5) is skipped, `unsupported_platform(xbox360)`. An Xbox 360 RGBA32 or RGB24 texture is exported like any other.

A texture with a side of 0 is skipped, `empty_image`. UnityPy's extractor skips a zero width and raises on a zero height; the oracle records both as `empty_image` (`extract.md` section 5).

**A texture's answer.** Once the texture's object is read (a failure of that read is its skip where `batch.md` 2.7 classifies it as one: 2.6 step 5, 2.7) and it keeps its name (4.4 step 1), its answer is the first of these that applies, in this order, except for a sheet's texture output (section 5), which asks 4 to 10, then the sheet's decode, whose refused charge (12) or panic (13) is the sheet's answer, taken by its texture output and every atlas alike, then 11, then its PNG's own charge (12). `batch.md` 2.7 maps the decoders' errors to them, and `unityrs_texture::plan` gives 5 to 10 from the data's length alone, before anything is allocated:
1. `empty_image`: a side of 0, whatever the format, the platform or the data (`parse_image_data` returns its empty image before it reads any of them, `export/Texture2DConverter.py:265-266`);
2. `unsupported_format(<name>)`;
3. `unsupported_platform(...)`, which so names only a texture of the five formats;
4. the failure of the data's read, by that read's own reason (`outside_view(<cab>)`; for a resource no candidate finds, `outside_view(<path>)`, its `m_StreamData` `path` as read; a budget, a data `limit`), as `batch.md` 2.7 classifies a read;
5. `decode_error`, detail `no_image_data`: empty data, a texture with an empty `image_data` and no `m_StreamData` among them (where UnityPy's `get_image_data` raises, `classes/legacy_patch/Texture2D.py:63-75`), and one whose `m_StreamData` has an empty `path`, which names no resource (UnityPy's `StreamingInfo` is true whatever it holds, so `get_image_data` looks the empty path up, and raises);
6. `decode_error`, detail `negative_size`: a negative side;
7. `limit(texture_pixels, 268435456)`: more pixels than the decoders' bound (9.3), whatever the data's length once it is not empty;
8. `decode_error`, detail `pillow_memory_error`: an RGBA32 or RGB24 texture wider than Pillow's raw decoder's cap, whatever the data's length once it is not empty;
9. `decode_error`, detail `not_enough_data`: data shorter than mip 0. A block format reads the data's length as Pillow's C `int` does, its low 32 bits, signed (`unityrs_texture::bcn_length`, step 6 of `decode`'s order), so data of 2 GiB or more whose low 32 bits are below what mip 0 holds, or negative, is short too;
10. `decode_error`, detail `decompression_bomb`: a block format whose crop Pillow refuses;
11. `decode_error`, detail `pillow_memory_error`, the texture output's own skip: an image wider than Pillow 9.5.0's PNG encoder takes in its mode, `INT_MAX / bits - 7` pixels (`src/encode.c`: 67,108,856 in RGBA, 89,478,478 in RGB), whose PNG cannot be made (the save raises `MemoryError`). Only a block format's image can be: the raw decoder's cap (answer 8) is the same. It answers the texture's PNG, not its image: a plain candidate, whose image is wanted for that PNG alone, is answered from the decode's plan, its width and mode, before the decode, so no image is made that cannot be written; a sheet is decoded whatever its width, its texture output (when planned) is skipped so before its PNG is made, and its atlases cut the image (section 5);
12. the output's charge refused: `budget(input)` or `limit(input_memory, <value>)` (the allocator's refusal is the stop `host_memory`, `batch.md` 2.7);
13. `decoder_panic`: a panic in the decode.

**The values as read.** `m_Width`, `m_Height`, `m_TextureFormat` and `m_StreamData`'s `offset` and `size` are the integers read, of any integer node, signed or not, and each answer uses them as they are: a side of 0 is answer 1 however wide the other; a format outside a 32-bit `int` is answer 2, `unsupported_format(<decimal>)`; a side past a 32-bit `int` is answer 7 (it is more pixels than the bound) and one below it answer 6. The stream's `offset` and `size` matter only when its data is read (answer 4): the data is what the reference reads from the resource, the memoryview reader's `read(size)` at `offset`: a `size` of 0 is no bytes and one of -1 the rest of the resource from `offset`; any other is Python's slice `data[offset:offset + size]`, so a negative index counts from the resource's end and a span past it is short, the integers taken whole, however wide. No bytes is answer 5 (`no_image_data`). On a Switch file, `is_switch_swizzled` reads `m_PlatformBlob` (any list, 4.4 step 2) as bytes: its element count against 12, then `int.from_bytes` of its elements 8 to 12, each an integer in 0 to 255 or a bool (0 or 1); when one of those is not, UnityPy raises there, and the texture's answer 3 is `decode_error`, detail `read` (for a texture of the five formats; another is answer 2 first). On any other platform the blob is not read, whatever it holds.

Else the texture's image is exported. 1 to 3 are selection's skips, which need no pixels (4.4 step 2); 4.4 step 3's key skips (`unwritable_key`, `duplicate_key`) fall between 3 and 4. 4's read is of the data `m_StreamData` names; an inline `image_data` is read with the object. Where `classify` makes a failure the input's (`budget(dependency)`, or `limit(export_work, <value>)`, which the export counts after 11 for a plain candidate; a sheet's decode work is counted before its texture output asks 11) or a stop (`host_memory`, `host_io`, `internal`), that ends the attempt instead of answering the texture (`batch.md` 2.7). A negative side is no skip: its decode fails, `decode_error` with detail `negative_size`, or `no_image_data` for empty data.

## 4. Identity and order

### 4.1 Bundles

- A bundle's identity is its spec `id`.
- A job declares its whole dependency graph. A name in an input's AssetBundle object's `m_Dependencies` is compared, exactly (no case folding, no path or variant rule), with the ids of the bundles of its view. A name that matches none is reported, never fetched or opened: a `diagnostics` row (`undeclared_dependency`, the input, the name) and the run's `undeclared_dependencies` count. A caller who spells ids as `m_Dependencies` spells them gets no such row for a declared bundle.
- The metadata scope is the first AssetBundle in each selected own
  SerializedFile, matching `SerializedFile::container()`. Its dependency lists
  concatenate in own-file/list order; repeated undeclared names remain repeated.
  The attempt opens every own directory row in order before this traversal, so
  an earlier shadowed or unsupported row cannot be bypassed. Reads use checked
  typetrees and cleaned attribute names; no Environment container pass runs.
- Wherever bundles are ordered, it is by bytewise order of their ids.

### 4.2 Views

`view(X)` is the smallest set that holds `X` and the `deps` of every bundle it holds. No `m_Dependencies` list ever adds to it.

### 4.3 Resolution inside an attempt

- The attempt's private Environment registers `view(X)` less `X` in bytewise order of id, then `X` last, always, from the bytes of its own open. Each top-level entry of a registered bundle that is itself a bundle is reached at its registration, which registers its subtree as UnityPy's eager load does (`batch.md` 2.6 step 4). Inside a reached container every row but a bundle is a key, whatever its kind; a bundle there is no key, and its entries are registered (the core's reach, `crates/unityrs-core/src/env/registry/reach.rs`). A WebFile row, top-level or inside a reached container, is a key, and no WebFile's entries are ever registered. Version 1's core refuses to open a WebFile (`Unsupported`), so a lookup its key answers, a pointer's or a resource read's, fails the reading object, `decode_error`, detail `unsupported`, where the registry would answer it with nothing once a WebFile opens (`crates/unityrs-core/src/env/registry/mod.rs`); UnityPy registers a WebFile's entries. So a lookup by name finds every CAB of the view, nested or not, but one whose key a later row takes (a bundle, a WebFile, a raw row or another CAB's; below), and a pointer between two containers of `X`'s bundle, or into a dependency's nested container, resolves as UnityPy resolves it, whatever `X` declares. The attempt inherits the core's `Lazy` differences from UnityPy's eager load (`PARITY.md` section 19.3, (a) to (d)):
  - (a) and (c): an entry that fails to parse, or a block that fails to decode, fails only the reads that meet it (an entry of a member, or a nested one of X; a top-level row of X fails X at selection, section 3; `batch.md` 2.7), where UnityPy's eager load fails the input, except a `Limit` that a bundle's peek meets at an entry's first bytes (`batch.md` 2.6 step 4; its budget never refuses). The peek runs once per run, before any attempt, so such a failure fails every input whose view holds the bundle, before its attempt and the same way whatever runs beside it (`batch.md` 2.3, rule 1): an input's own bundle's as the input's own reason; else a member's as `dependency_failed(<id>, <reason>)`, the least id among the view's peek failures. In a view that did not stage whole, the least-id staging failure is named instead (the input's own first), its record committed when staging ends, before any peek, so it does not depend on whether another view had its members peeked; only an input whose view staged whole waits for the peek pass, and its record is committed when the pass ends. A peek failure leaves its bundle's `bundles` row `staged` (7.3). One level down, a nested container's reach fails the input on a `Limit` or a parse failure (`batch.md` 2.6 step 4). An earlier directory row of a repeated path, shadowed in `files()` (section 3), is never selected, though selection opens it (section 3). Until CR7 (`batch.md` section 6), three gaps remain, each able to decide a record without naming its reason. Two or more levels down, a non-transient `Limit` or a parse failure leaves the container unreached or a plain entry. And at a **dropped container row**, a top-level row of a registered bundle whose registry key (`simplify_name`, the lower-cased basename) a later row of the same bundle takes, an exact repeated path among them, the core's settle swallows a parse failure or a non-transient `Limit` and retries a refusal at the next lookup, its evictions counted; once the row's bundle is evicted, nothing reaches the row, since only a container pass does and the engine runs none. And a top-level container row whose key a nested CAB of such a dropped row takes is reached only by that settle, which swallows a parse failure or a non-transient `Limit` there too (`settle_list`, `env/registry/reach.rs`): the engine's reach by its name answers the nested CAB. ### 4.5 Winners across inputs

E31 to E33 and E61 as written, with these orders and units:
- "first by bytewise input id" everywhere;
- E31 rule 1 applies when the preferred input has a candidate for the key;
- **Units** (E32). A unit is made of outputs the attempt made. When the input made a sheet's texture output (`outputs.textures` set, and the texture neither skipped nor failed), the unit is that texture with every atlas of the input that cuts the sheet (section 5), their crops and their JSONs, and its **unit key** is the texture's key. Otherwise (a sheet's texture skipped for its key, `duplicate_key` or `unwritable_key`, among them) each atlas whose JSON was made is a unit of its own, its crops and its JSON, keyed by the JSON's key; an atlas with neither has no unit, and its crops are plain candidates. A texture no atlas cuts (section 5's sheets) is a plain candidate. The attempt exports a sheet's texture before its atlases, and an atlas's JSON before its crops (4.4), so a unit's key is fixed before its crops are recorded. A unit key is always the key of an output of the unit. A unit's **keys** are its unit key and its members' keys. Its `prefer` entry is its unit key's (an entry for another key of a unit is not consulted), and E31 rule 2 compares that output's MD5. Step 1 decides among units only: an entry naming an input whose candidate for the unit key is plain is not honoured, and that candidate loses in step 3 (rule `unit`).
- The steps, in order (`batch.md` 2.9):
  1. Each unit key's winning unit is decided by E31 and E61 among the units with that unit key. A unit that loses is **ineligible**: none of its keys is ever published from it. A unit key that E61 withholds withholds every unit with that key, and every key of each of them is reserved in step 2 as a winning unit's are.
  2. Every key of every winning unit is **reserved**. Of the unit keys that claim a key, the first in bytewise order of unit key keeps it, and every other's winning unit is withheld whole (`unit_conflict`). A key stays reserved even when every unit claiming it is withheld; this step is not repeated. A reserved key's `outputs` row (7.3) is its keeper's winning unit's candidate; when the keeper's unit key is withheld by E61 and the input its rules chose holds no candidate for the key, the row is the first candidate, by bytewise input, of that unit key's units that hold one. A unit key E61 withholds stays `withheld` where it also loses a claim here: its keys' reason, and its units' candidates' rule, is `withheld`, not `unit_conflict`. A member key is a flip when its keeper unit key was decided by rule 3 in step 1, whether or not E61 then withholds it, and that unit key's candidates for the key do not all share one MD5.
  3. A plain candidate for a reserved key loses (rule `unit`). A key whose only candidates are ineligible units' is not published: it is `withheld`, reason `unit_lost`, its row the first of them by bytewise input, with no flip; E61 is not consulted for such a key. Every other key is decided by E31 and E61 among its plain candidates; an ineligible unit's candidate for it loses.
  4. Section 4.6 runs once on the keys steps 1 to 3 would publish.
- So phase 6 never publishes a unit in part: a unit is published whole or withheld whole. An attempt-time skip of one of its outputs (`unwritable_key`, `duplicate_key`) removes that output only.

### 4.6 Prefix conflicts

Let `P` be the keys section 4.5's steps 1 to 3 would publish: withheld keys, `unit_conflict` keys and losers are not in `P`.
- A key `K` of `P` that is an ancestor of another key of `P` or of an archive's key (one starts with `K/`) is `unwritable_key(prefix_conflict)`; the keys and archives beneath it stay.
- Any other key of `P` that equals an archive's key or lies under one is `unwritable_key(archive_conflict)`; the archive stays.
- A unit with a key refused here is withheld whole: its other keys are `unit_conflict`.
- The check runs once, on `P` as steps 1 to 3 left it, and is not repeated after a unit is withheld. It runs on `P`'s keys and the archives' keys in **`/`-first order** (bytewise, except that at the first byte where two strings differ a `/` is less than any other byte), in which every key's descendants follow it, so its result does not depend on the order of publishing (`batch.md` 2.9). It is the same in every sink. What remains is the set of **winners**.

### 4.7 Archive members

For each archive and each of its `members` entries, every winner of that kind is a member, at the path the entry's template gives for it (expanded by the attempt that made the candidate, `batch.md` 2.8). Then, per archive:
- a path that breaks a rule of section 2.3 but `prefix_conflict` (below) is left out first (`unwritable_path(<rule>)`) and takes no part in the rules below;
- the rest are ordered by path in `/`-first order (4.6), so the members under one directory are contiguous;
- of several members with one path, the one whose key is first in bytewise order is kept, and the others are left out (`duplicate_member`);
- a path that is an ancestor of another remaining member's path is left out (`prefix_conflict`).

Membership depends only on the winners, never on how their loose PUTs end, so an archive's bytes are a function of the committed records. With `publish_incomplete: false` and a failed input, nothing is published, and every archive with a member is `withheld` (`publish_incomplete`). Here "with a member" means at least one structurally included survivor after these rules. An archive with only left-out expansions stays `empty`, preserving its `left_out` count. Member rows use archive-key byte order, then displayed path in `/`-first order, then loose key and input; invalid paths enter only this display sort.

## 5. The NGUI cutter

The MonoScript's read is part of the `m_Script` read: its failure, a value with no string `m_ClassName` among them, is that read's (4.4 step 2's rule); and
2. its typetree has a field `mSprites` that UnityPy reads as a list of sprites. This is decided from the typetree's nodes alone, as `read_value` dispatches (`helpers/TypeTreeHelper.py:182-263`), before any value is read: the root's last child named `mSprites` (a typetree's dict keeps the last of each name) is a vector node: its type is none that `FUNCTION_READ_MAP` reads (as `string`, whose first child is `Array` too, is), nor `pair` or `ReferencedObject`, and its first child is `Array`; and its element, the `Array` node's second child, is a struct: of none of those types (so not a `map`'s `pair`) and no vector, whose last children named `x`, `y`, `width` and `height` are each of an integer type and whose last child named `name` is a `string`. The integer types are `FUNCTION_READ_MAP`'s (`helpers/TypeTreeHelper.py:29-52`) less `float`, `double`, `bool`, `string` and `TypelessData`.

A MonoBehaviour that meets 1 but not 2 is skipped, `ngui_layout_unsupported`: NGUI 2's `sprites` layout is not in version 1, nor an `mSprites` of any other shape, a rectangle of `float` or `bool` fields among them. One with no typetree is skipped, `no_typetree`; version 1 has no fallback for a stripped atlas. A MonoBehaviour whose `m_Script` dereferences to an object that is no MonoScript is not an atlas, and is not counted. One whose `m_Script` read fails with an error `batch.md` 2.7 makes an object's skip is not an atlas, and the input's record counts it (`unresolved_scripts`); when that error is of the budget class (exit 5), it is also recorded as a skip of the MonoBehaviour, output `atlas`, with its reason (whichever object's read it failed on, the MonoScript's or the head's), so the records and the exit code show that a budget decided. Any other error (a `Budget(Dependency)`, a run-level class) goes as 2.7 says: it fails the input or stops the run.

**Skipped atlases.** An atlas's `m_Name` is its `m_Name` as 4.4 step 1 reads it, from its head. An atlas with an empty `m_Name` is skipped, `unnamed_atlas`. An atlas whose `m_Name` ends with a string of `skip_name_suffixes` is skipped, `reference_atlas`. An atlas past these skips is read whole (its typetree's value, with `check_read`, 4.4 step 2); a failure of that read skips it by the read's own reason, as `batch.md` 2.7 classifies it (`decode_error` with its code, a data `limit`, a budget), at the plan, before its sheet is looked for (4.4 step 2's order).

**The sheet** (E21, scope `own_files_by_name`; `follow_pptr` is not in version 1).
1. The material's main-texture name: dereference the atlas's `material` field, then, in its `m_SavedProperties.m_TexEnvs` (the Material read whole with `check_read`, 4.4 step 2; a list of pairs, each a pair (or a two-element list)), the first pair whose first is `_MainTex`, or a struct whose `name` is (UnityPy 1.25.2 types it either way, `classes/generated.py:11477`); dereference that pair's `m_Texture` and read its `m_Name` as 4.4 step 1 reads it. An atlas with no `material` field gives no name. The field is NGUI 3's `material`, as measured on a corpus of two builds of one game: every NGUI 3 atlas there has it (in one build's 1,506, set to a material in the atlas's own file on 737 and null on the 769 reference atlases; the other's agree). An error on this path that `batch.md` 2.7 makes an object's skip gives no name, and the next step runs, recorded as above when it is of the budget class: a null pointer, an `m_FileID` past the externals or before them (its index `m_FileID - 1`, a negative index counting from their end, so `-1` names the next-to-last, as UnityPy's `PPtr.deref` indexes them, `classes/PPtr.py:56-60`), a missing object, a raw or bundle row of the reading file's own bundle, or a raw row the registry answers (`bad_pointer`), and a bundle the registry answers or a CAB outside the view (`outside_view`, 4.3) among them; a WebFile row the lookup meets, of the reading file's own bundle as anywhere (`decode_error`, detail `unsupported`, 4.3), gives no name too. Any other error goes as 2.7 says, as above.
2. Among the input's own Texture2D objects in object order, the first whose `m_Name`, read as 4.4 step 1 reads it, equals that name exactly (bytes, case-sensitive). When there is none, or no name, the first whose `m_Name` equals the atlas's `m_Name`. The match is on the name alone: when that texture's object read then fails, the failure is the sheet's answer, and skips the atlas with the read's reason; no later texture of that name is tried.
3. No match skips the atlas, `sheet_not_found`.

A sheet whose answer is an object's skip (any of section 3's answers for a texture but its image and answer 11, its PNG's, where `batch.md` 2.7's `classify` makes it the texture's skip: a selection skip, its object read's or its data's failure, `decode_error`, `limit(texture_pixels, 268435456)`, a refusal of the sheet's decode (its pixel buffer, `budget(input)` or `limit(input_memory, <value>)`), `decoder_panic`) skips each atlas that cuts it, crops and JSON, with the sheet's reason; so does a sprite whose sheet does. A failure `classify` makes the input's (`budget(dependency)`) or a stop (`host_memory`) stays what it is: it ends the attempt, and is no skip of the atlases and sprites. The texture's own PNG, charged after the decode, is the texture's output alone: its refused charge skips that output, and so does the PNG encoder's refusal of the sheet's width (section 3's answer 11, decided before that PNG is made); either way the atlases cut the decoded sheet, and with no texture output planned (textures off, or its key dropped) the sheet's width answers nothing.

A texture is a **sheet**, and so a member of its atlases' unit, when at least one atlas of the input selects it by steps 1 and 2 and is not skipped at the plan (4.4 steps 1 and 2); every other texture section 3 selects is a plain candidate, exported after the sheets (4.4). A sheet's skip at the export is recorded as one `skips` row for the texture when its output kept its key after 4.4 step 3, then one per atlas with an output still planned after step 3 (output `atlas`, its crops and JSON together), in export order.

The sheet is decoded as a texture (E15), into the image UnityPy's `Texture2D.image` gives (`classes/legacy_patch/Texture2D.py:8-11`): rows top to bottom. Its data is its `image_data` when that is not empty; else the resource its `m_StreamData` names, read by 4.3's own-chain procedure, the reading file's own containers first and then the view, with UnityPy's candidate names (`helpers/ResourceReader.py:10-33`). With no `m_StreamData`, or one whose `path` is empty, the data is empty (section 3's answer 5). With `outputs.textures` set, the atlases of one input that cut one sheet are one unit with it; without it, each atlas is its own unit (section 4.5).

Every failure this section meets is a reason of 9.3, as `batch.md` 2.7's `classify` makes it: a read's error by its code (7.3's `detail`), a pointer's by its `DerefError` (`bad_pointer` or `outside_view(<cab>)`), a texture's data and decode by section 3's answers.

**Crops.** For each element of `mSprites`, in array order:
- its rectangle is `(x, y, x + width, y + height)` on that image, origin at its top-left, the element's `x`, `y`, `width` and `height` as the integers read, the edges computed exactly (each value fits 64 bits, so their sums fit 128). Borders, paddings and mirror flags are not applied;
- a `width` or `height` of 0 or less skips that sprite, `empty_rect`;
- a crop Pillow 9.5.0 refuses skips that sprite at the plan, from the rectangle alone: `decode_error`, detail `decompression_bomb`, when `width x height` (after `empty_rect`, an exact unsigned 128-bit product) is over 178,956,970 pixels (twice `Image.MAX_IMAGE_PIXELS`, `Image._crop`'s check, made first); else detail `crop_overflow` when an edge is outside a C `int` (`x` or `y` below -2^31, `x + width` or `y + height` above 2^31 - 1), whose box Pillow's C crop refuses;
- a crop wider than Pillow 9.5.0's PNG encoder takes in the sheet's mode (`INT_MAX / bits - 7` pixels, `src/encode.c`: 67,108,856 in RGBA, 89,478,478 in RGB), whose save raises `MemoryError`, skips that sprite at the plan too, `decode_error`, detail `pillow_memory_error`, after the two checks above, so no crop is made that cannot be written;
- a crop is charged before it is allocated (E59), at its size and the sheet's mode; a refused charge skips that sprite, `budget(input)` or `limit(input_memory, <value>)`, as section 3's answer 12 does a texture;
- a rectangle past the image's edge is padded with zero pixels, as Pillow 9.5.0's `Image.crop` pads (E23). The crop keeps the sheet's mode.

**The JSON** (E24): CPython 3.11's `json.dumps(value, indent=2)` of an object with these keys, in this order:

| key | value |
|---|---|
| `name` | the atlas's `m_Name`, as 4.4 step 1 reads it |
| `texture_width`, `texture_height` | the sheet image's size |
| `pixel_size` | the typetree's `mPixelSize` as read, or `null` when absent |
| `settings` | the typetree's `mSettings` as read, or `null` when absent |
| `sprite_count` | the length of `mSprites` |
| `sprites` | each element of `mSprites`, as read, in array order |

"As read" means UnityPy 1.25.2's `read_typetree()` value, written as `json.dumps` writes it: a typetree dict as an object in its field order, a pair as a 2-element array, an f32 widened exactly to the double, a string as UnityPy decodes it (`surrogateescape`, so an invalid byte is written `\udcXX`). A value `json.dumps` cannot write (bytes) skips the JSON, `json_unwritable`, and keeps the crops (E25). It is found at the export, so the JSON keeps the key 4.4 step 3 planned for it. The field names are the typetree's, not renamed. The sheet's key is the outputs row's `unit` (section 7.3).

## 6. The spool

**A cgroup v2 memory limit** that holds a run is provisioned at `(1.5 x memory_bound + 10 MiB x (2 x download_concurrency + 1) + 3 MiB x (download_concurrency + 1)) / (1 - vm.dirty_ratio / 100)`, or, when `vm.dirty_bytes` is set, at `1.5 x memory_bound + 10 MiB x (2 x download_concurrency + 1) + 3 MiB x (download_concurrency + 1) + vm.dirty_bytes`, `memory_bound` being `--check`'s (section 10), which is **provisional** until `extract.md` X12 measures its constants (section 10's `detail`), so this limit is an estimate until then too; a `vm.dirty_ratio` of 100 needs `vm.dirty_bytes`. The terms are glibc's slack, the live sockets' buffers, glibc's uncounted lookup heap and the spool's dirty pages (`batch.md` 5.6 derives them). The heap's term is glibc's `files dns` path's: a host whose NSS uses another module (systemd's `resolve`) may need more, and its caller raises the cgroup. The rule does not cover a cgroup v1 limit, which preflight still checks against the bound (`batch.md` 2.7).

Claims use the increase in a file's cumulative length rounded up to the
preflight `st_blksize`, not the sum of separately rounded writes. Zero-length
files claim zero bytes; claims do not preallocate or change content length.
The reserve check uses caller-available `statvfs` bytes; equality succeeds.
`ENOSPC` and `EDQUOT` at create, write, flush or delete are `spool_full`, with
that exact detail; other I/O is `host_io`. A directory owner retains all claims
through partial writes, failure, rename and drop. Only successful explicit
deletion releases them; a failed or partial deletion retains the whole claim.
For an owned staging file, a retry also releases its claim after successful
truncate-to-zero, once every outstanding write completes; a failed truncate
retains the full claim. Drop alone never releases it.
A sealed artifact has completed writes and closed files, with no per-output
fsync or crash-recovery promise.
Cooperative directory removal uses no-follow directory descriptors and checks
stop initially and every 1,000 entries. A stop during partial deletion keeps
the whole claim and leaves cleanup to the next start.

### 6.1 Layout

| path | holds |
|---|---|
| `<dir>/.unityrs-spool` | the marker: an empty file the engine writes when it first uses an empty directory |
| `<dir>/lock` | the spool's lock: `flock(LOCK_EX \| LOCK_NB)` for the process's life (E63). Created if absent, never deleted |
| `<dir>/runs/<run_id>/journal.tmp` | a removal's rewrite of the journal, renamed over it (next row) |
| `<dir>/runs/<run_id>/journal` | multipart upload ids, one per line as a JSON array `[endpoint, bucket, key, upload_id]`. Every append and every removal opens the journal by path, under the journal's mutex. Before an append, a journal whose last byte is not `\n` gets one. A line is appended and `fdatasync`ed after the create (the append that creates the journal is followed by an `fsync` of `runs/<run_id>/`), and removed only after a successful complete or abort (E64): the journal is streamed line by line, one line held, into `journal.tmp` without it, which is `fdatasync`ed and renamed over it, and `runs/<run_id>/` is `fsync`ed before the mutex is released. So it holds the uploads in flight and those whose abort failed; a removal a crash loses costs only an extra abort (6.2 step 4); a reader skips a line that is empty, over 16 KiB (which no line at 1.6's and 2.3's caps reaches, escaped, with an upload id under 1 KiB, `batch.md` 2.9), or that does not parse, a torn last line among them |
| `<dir>/runs/<run_id>/in/` | staged bundles, read-only: `i<n>` for the n-th of `inputs`, `d<n>` for the n-th of `dependencies` (`batch.md` 2.5); and, read-only, `pi<n>` or `pd<n>`, the peek file of a bundle one of whose top-level entries is a container: a bit per top-level row in directory order, set for a container, row `i` at byte `i / 8`, bit `i % 8`, the least significant first, its padding bits zero, CR7's layout (`batch.md` 2.6 step 4, section 6) |
| `<dir>/runs/<run_id>/attempts/<input>/` | one attempt's outputs and `records.ndjson` |
| `<dir>/runs/<run_id>/fail/<input>/` | a failure record's `records.ndjson`, written on the controller's blocking pool; the controller renames the directory to `done/<input>/` (`batch.md` 2.4). The finisher reads none, and one a stop left unrenamed is removed by the next start's cleanup (6.2 step 5) |
| `<dir>/runs/<run_id>/done/<input>/` | a committed attempt, or a committed failure record |
| `<dir>/runs/<run_id>/winners/` | phase 6's sorted runs, the winners file, the archive member lists and the sorted row files |
| `<dir>/runs/<run_id>/winners/outcomes`, `archive_outcomes` | phase 7's results: one byte per winner at its index in the winners file, and one 128-byte record per archive (that byte, size, MD5, ETag), made at phase 7's start (`batch.md` 2.9); a missing or short file reads as 0 past its end. The byte: 0 `not_written`, 1 `written`, 2 `present`, 3 `failed` (`publish_failed`), 4 `failed` (`publish_mismatch`), 5 `failed` (`credentials_expired`), 6 `failed` (`archive_too_large`, an archive's only) |

`<input>` and `<n>` are positions from 0, in decimal, so an id never becomes a path.

An archive outcome record uses these byte offsets (inclusive):

| bytes | encoding |
|---|---|
| 0 | outcome code above |
| 1 | ETag length, 0 to 100 |
| 2–9 | little-endian `u64` size |
| 10–25 | binary MD5 |
| 26–125 | ETag bytes without quotes, zero-padded |
| 126–127 | reserved zero bytes |

For `written` and `present`, metadata is written first and the status byte
last, with checked offsets; a whole-record positional write is not assumed
atomic. A missing winner byte is 0; a missing or partial 128-byte archive
record is 0, not a partially advertised success. Other invalid codes are
corrupt internal artifacts. Updates to an already claimed extent add no
second claim. An acknowledged archive's success metadata is immutable within
this attempt: another success update is refused as an internal artifact error.
Verification failure changes only the status byte, leaving the original metadata
intact even if that status write fails. Directory archive ETags are null.

### 6.2 Start

The engine owns only what it created. Preflight starts the spool in this order, after reading the credentials. A failure in steps 1 to 3 exits 69 with nothing deleted, and any call on `dir` in steps 1 to 3 and 6 that fails with an error no step names is `spool_unusable` (9.3); step 4 never fails the start; an I/O error in step 5 is `host_io` (74), through the finisher, with no head (7.4); a failure in step 6 exits 69 after step 5's deletions, which removed only the engine's own files:
1. **Dedicated.** `dir`'s entries must be none, or only `.unityrs-spool`, `lock` and `runs`, the marker among them, with `lock` a regular file and `runs` a directory, by `lstat` (neither a symlink). Otherwise `spool_not_dedicated`. A `dir` whose `statfs` type is tmpfs or ramfs is `spool_in_memory`: its bytes would be memory outside the bound (`batch.md` 5.4).
2. **Apart from the sink.** With a directory sink, the real paths of `dir` and `root` neither equal nor contain one another. Otherwise `spool_overlaps_sink`; a `root` whose real path cannot be taken, a missing one among them, is `sink_root_unusable` (7.2).
3. **The lock.** `lock` is opened (created if absent) and locked; busy is `spool_locked`. The lock is held until `_exit` and the file is never deleted, so a second process always meets the same inode. An empty `dir` gets its marker before `lock` is created, so an interrupted first use can leave a lone marker, a valid empty dedicated spool; a lone `lock` is still refused. The engine canonicalizes `dir` before opening it with no-follow directory flags, then, after locking, compares the canonical path's no-follow `st_dev`/`st_ino` with the held directory and refuses a mismatch before cleanup. Later startup operations use the held directory.
4. **Old journals.** Every `runs/*/journal` is read, streamed through a fixed buffer, holding only the ids of the aborts in flight; each upload id whose endpoint and bucket are this sink's is aborted, at most `download_concurrency` at once, each with the sink's `timeout_ms` and `attempts`. `NoSuchUpload` counts as aborted (1.6): the upload completed before its id was removed, or the lifecycle rule took it. Any other failure, a 403 among them, leaves the id to the bucket's lifecycle rule (E64) and counts in the warning `abort_failed`, so no journal can stop a later start. An id of another endpoint or bucket is left to that bucket's lifecycle rule.
5. **Cleanup.** Everything under `runs/` is deleted, through directory handles opened with `O_NOFOLLOW`, so no symlink is followed out of the spool; this `run_id`'s earlier attempts and other run ids' alike, the `attempts/` and `fail/` directories a stop left among them: the lock proves no live process uses them.
6. **Free space.** `statvfs` of `dir` must show at least `reserve_bytes` free. Otherwise `spool_no_space`.

Nothing in the spool is reused between attempts: every attempt stages and decodes again (E44). After the final manifest, and after a stop, the spool is left as it is; the next start clears it.

## 7. The manifest

### 7.1 Location

| sink | the head | the row files |
|---|---|---|
| directory | `<root>/_unityrs/<run_id>/manifest.json` | `<root>/_unityrs/<run_id>/<attempt>/<file>.<k>.ndjson` |
| object store | `<prefix>_unityrs/<run_id>/manifest.json` | `<prefix>_unityrs/<run_id>/<attempt>/<file>.<k>.ndjson` |

No output key may start with `_unityrs/` (2.3). The row files hold the attempt number, so an earlier attempt never overwrites a later one's rows. Each row file is written in chunks `k` = 0, 1, ..., each at most 16 MiB and cut at a line's end, so each is one single-part PUT; a reader concatenates them in order. The head names each file's chunk count, not its keys, so it stays under 64 KiB whatever the rows' size.

### 7.2 Fencing, verification and the caller's duties

- **Preflight**, for an object store, first proves the bucket: a LIST of the prefix at `max_keys` 1 whose response is a 2xx, whatever its body holds, which is read under the LIST cap and dropped, never scanned or parsed (`batch.md` 2.9); a 404 exits 69 (`bucket_missing`), any other failure `sink_unreachable`. Then, for either sink (a directory under its lock, below), it reads the head; a 404, or no file, is no head. A head over 1 MiB, or one that is not a manifest, exits 69 (`manifest_unreadable`); a sink that cannot be reached exits 69 (`sink_unreachable`). A head of this `run_id` whose `attempt` is at or above this one's exits 7 (`superseded`; `batch.md` 2.11's precedence), and nothing is written but, in a directory, the `_unityrs` lock and `<run_id>` directory preflight made. Every head read, preflight's and every read-back, reads at most 1 MiB + 1 byte, so a longer head is never read whole (`batch.md` 2.9).
- **Object store, `"conditional"`.** The store client is configured with `S3ConditionalPut::ETagMatch`. The `running` write is `If-None-Match: *` (`PutMode::Create`) when no head exists, else `If-Match` (`PutMode::Update`) on the ETag preflight read. The final write is `If-Match` on the `running` write's ETag, or, in 7.4's second row, the precondition of the `running` write's last try (`batch.md` 2.11). A `running` write that fails other than by a failed precondition exits 69 (`sink_unreachable`), with nothing written but possibly the `running` head, which its own fence covers (9.1).
- **A failed precondition** is `object_store`'s `Precondition` or `AlreadyExists`: a 412, a `Create`'s 304 or 409, an `Update`'s 409, or an `Update`'s 404, which `object_store` reports as `Precondition` (`src/aws/mod.rs`). Each is read back with a GET. A head with this `attempt` and this write's `write_seq` is this write, whose response was lost: success. Only a head of a higher `attempt` is `superseded`: the attempt writes nothing more and exits 7 (`batch.md` 2.11's precedence). A writer never overwrites a head it cannot read: one over 1 MiB, or not a manifest, makes the `running` write exit 69 (`manifest_unreadable`) and the final write record 4, the head left as it was. Any other head is retried with `If-Match` on its ETag: at the final write, this attempt's own `running` head; at either write, a lower attempt's, an earlier attempt's late write that landed after preflight's read (after its 69, the caller retried at once, 9.1). No head at all (a concurrent write's 409, or a head removed) is retried with `If-None-Match: *`. Those retries are at most 4 per write; a fifth failed precondition exits 69 at the `running` write (`previous_attempt_live`), and at the final write leaves the stored head as it was, recording 4 (`publish_failed`). Only the finisher writes after `running` (`batch.md` 2.11), so no two writes of one attempt share a `write_seq`.
- **Object store, `"none"`.** Plain PUTs.
- **Directory.** `<root>/_unityrs/lock`, one lock for the whole root, whatever the `run_id`: `flock(LOCK_EX | LOCK_NB)` held for the process's life, busy exits 69 (`output_locked`); any call on the root at preflight that fails with an error no rule names (its open as a directory, `realpath`, the `_unityrs` and `<run_id>` creates, the head's read, `openat2` with an errno but `ENOSYS` and `EPERM`) exits 69 (`sink_root_unusable`). So one process at a time writes a root. Two keys that differ in any byte are two outputs, so a directory sink must be case-sensitive and normalization-preserving: on a sink that folds them, two outputs whose keys differ only by letter case, or only by Unicode normalization, would be one file, the second write replacing the first while the head lists both. After the head's fence, before the `running` head, preflight probes this in the root itself and in `<root>/_unityrs/<run_id>` (a directory's folding is its own: a root that folds can hold an `_unityrs` that does not): in each it creates two pairs of empty files, `.unityrs-tmp-probe-a` and `.unityrs-tmp-probe-A`, then `.unityrs-tmp-probe-` and U+00E9 against `.unityrs-tmp-probe-e` and U+0301, each create exclusive (`O_CREAT | O_EXCL`) after an `unlinkat` of both names (`ENOENT` ignored, so a killed attempt's probes fail nothing), and removes both, the second even when the first's removal fails. Their names are reserved (2.3's `reserved_name`), so no output key meets them. A pair whose second create fails with `EEXIST`, or opens the first's inode, exits 69 (`sink_root_unusable`, its detail `case_insensitive` or `normalization_insensitive`). A directory below the root that folds names of its own (ext4's per-directory casefold attribute, set before the run) is unsupported: the probe does not see it, and its outputs may fold unseen. When preflight creates `_unityrs` or `<run_id>`, it `fsync`s the directory containing each new entry before any head can be acknowledged. Each head write is a temp file, `fsync`, a rename over the head, and an `fsync` of the directory, made on the writing thread itself. Immediately before each create (directories and metadata included) and commit rename, the parent is re-resolved from the root under no-symlink, beneath-root resolution (or the fallback walk), and its `st_dev`/`st_ino` must match the held parent. Concurrent external renames inside the owned root are detected at these points only.
- **Verification** (object store). After its last transfer, phase 7 LISTs the prefix and checks every key and archive it marks `written` or `present` against the ETag it expects (`batch.md` 2.9). One that is missing or differs is `failed` (`publish_mismatch`). A key whose ETag is not an MD5 (`etag_not_md5`, SSE-KMS or SSE-C) is checked by its size alone and counted in `verified_by_size`: for it, the store held an object of this attempt's size, not necessarily its bytes. The head's `verified` is true when the pass ran to its end; false when a LIST failed or came out of order (warning `verify_list_failed`) or a stop interrupted it (no warning); and null for a directory sink, where the root's lock leaves no other writer, and when nothing was published (`publish_incomplete: false`).
- **What no client can fence.** A store may commit a request it has received long after the client gave up on it, and after the client's process has ended: S3 documents that a `CompleteMultipartUpload` can take several minutes. So the engine bounds only its own writes, and the caller owns the rest.
- **The caller's duties** (object store):
  1. At most one process of a `run_id` runs at a time, two of one attempt number included (an orchestrator's single-flight claim per run does this), nothing but that run's attempts writes its keys, and two `run_id`s never share keys. `"conditional"` is set only for a store that enforces `If-Match` and `If-None-Match` on a PUT.
  2. Before it starts attempt `n + 1`, the caller waits `W` past the end of attempt `n`'s process, or past its `deadline` when it cannot see that end: the engine resets every connection it still has before each exit, at `T_hard` at the latest, before the deadline (`batch.md` 2.11), so none sends after it, even while a file call holds the process (`batch.md` A11), unless the process is stopped or frozen across `T_hard` (by the caller, job control or the kernel's freezer), when its sockets send until it resumes or ends, or the caller or the kernel kills it (the OOM killer, a fault, a signal whose default action ends it) while a file call holds a thread: then each socket is reset only by its zero linger, at the last thread's exit. `W` is the store's longest time to commit a request it has received: every engine socket has zero linger from before its connect, so any close, at exit or a kill included, resets it and discards what TCP still holds (`batch.md` 2.5). Segments already below TCP are covered by the store's figure. The engine uses no proxy (1.4), but a transparent proxy or a balancer in front of the store may hold a request after the engine's reset, so a caller with one adds its delay to `W`. For AWS S3 this contract states 15 minutes. There is no wait when attempt `n` ran with `"conditional"` fencing and its final head has a null `stop_reason` and `unsettled_tries` 0: every try of every output, archive and row-file request was settled by 1.6's table, and every try of a head write is fenced (above), so none can land after the head. Nor is there a wait after an exit 69, which leaves at most a fenced `running` head. With `"none"` the caller always waits, after a 69 too.

The head is the record of the run. For every key the final head lists as `written` or `present`, the store held this attempt's bytes when verification listed it (with `verified` true; for a key counted in `verified_by_size`, an object of their size), and holds them still if the caller kept its duties. With `verified` false or null, the first half is not checked. A key the head does not list so is not part of the run's output, whatever the store holds.

The identity envelope used to recognize an existing head consists of
`manifest_version` (a positive unsigned integer), `run_id` (a string equal to
this run's id), `attempt` (an integer from 1 to 2^31-1), `write_seq` (an unsigned
64-bit integer), `binary_version` (a string), `spec_version` (a positive
unsigned integer), and `spec_sha256` (64 lowercase hexadecimal digits).
These seven fields must each occur once and have their stated type. A future
`manifest_version` is accepted by this envelope; unknown fields are skipped
with bounded storage while their JSON syntax is checked. A mismatched
`run_id` at this run's head path is `manifest_unreadable(not_a_manifest)`,
never permission to overwrite. Recognition allocates no JSON tree; the caller
supplies the bounded read buffer.

UnityCN uses this existing error-code vocabulary: a missing key or an invalid
key length is `unsupported`, preserving the earlier encrypted-input refusal;
a signature mismatch (including a wrong key) or a short AES vector is
`malformed`, because the supplied header cannot be decoded as valid input.
A walk past UnityPyBoost's bounded virtual trailing byte is `unsupported`.
These are per-input refusals: an open reports `container_error` with that
code; an entry uses `entry_error`; an object read uses `decode_error`.

- **`detail`** on a `bundles` row: for `download_failed` and `redirect_refused`, the last try's (1.4's try table); for `integrity_mismatch`, `size` or `sha256`, the first check that failed, the size's coming before the SHA-256's; on a bundle that is the stop's culprit, the one whose peek's run failure set the stop's reason (`batch.md` 2.11), that reason, `internal`, `host_io`, `host_memory` or `spool_full`; else null. A texture decode's error (`unityrs_texture::DecodeError`, E15) has codes of its own, each a case where UnityPy raises too, in section 3's order of a texture's answers: `no_image_data` (empty data), `negative_size`, `pillow_memory_error` (Pillow's raw decoder's width cap, answer 8), `not_enough_data` and `decompression_bomb` (the check of UnityPy's crop); its `TooLarge` is no `decode_error` but the data limit `limit(texture_pixels, 268435456)` (9.3), its `Charge` the limit or budget refusal it holds (an allocator's refusal, a `ChargeError::Budget` too, is the stop `host_memory`, not the object's skip: `batch.md` 2.7), and a panic `decoder_panic`. Apart from the decode's codes, a texture output whose image is wider than Pillow's PNG encoder takes is `pillow_memory_error` too (section 3's answer 11): no `DecodeError`, but the cutter's check of the output's width and mode before its PNG is made, a skip of that output alone. A sprite's crop that Pillow refuses (section 5) has three codes, `decompression_bomb` and `crop_overflow` for the crop and `pillow_memory_error` for its PNG encoder's width cap. A Sprite's render (`unityrs_texture::sprite::SpriteError`, E17) has the crop's three codes and three more: `decompression_bomb` and `crop_overflow` (a box edge outside a C `int` or a C `long`) for its crop, `pillow_memory_error` for an image Pillow refuses to make (wider than 536,870,910 pixels) and for its PNG encoder's cap, `read` for a field of another shape, `unsupported` for a mesh part version 1 leaves to a later phase, and `render` for every other exception UnityPy 1.25.2's `SpriteHelper` raises (a NaN or infinite rectangle, an edge before its opposite, a rotation of 5 to 15, an alpha texture of another size, an atlas without the Sprite's entry, a mesh it cannot mask or draw); its `TooLarge` (a canvas past the renderer's bound) is the data limit `limit(texture_pixels, 268435456)`, a tight Sprite's mesh in a file with no version `version`, a mesh's resource read the core's code (as an error's, above), an `m_SpriteAtlas` that does not resolve its `DerefError`'s class (`batch.md` 2.7: `bad_pointer`, `outside_view(<name>)` or a `decode_error`), its `Charge` the refusal it holds and a panic `decoder_panic`, as a texture decode's. So a code the core or the decoders add or rename reaches a manifest only with a new `manifest_version`, this list and `classify` changing with it. On an `inputs` row: for `container_error`, the error's code; for `entry_error`, the code, a space and the entry's path in its container's directory, the innermost container's for a nested entry, cut (below) so the whole is at most 1,024 bytes; for a transport reason or `integrity_mismatch`, the bundle's `detail`; under `dependency_failed`, the member's, by its inner reason; for `stopped`, null but on the stop's culprit, the input whose attempt's run failure set the stop's reason (`batch.md` 2.11), where it is that reason, `internal`, `host_io`, `host_memory` or `spool_full`; when the culprit is a bundle (a peek's stop, which comes before any input is dispatched or marked), no row is `stopped`, and the bundle's row names the reason; else null. On a `skips` row: for `decode_error`, the error's code; for `decoder_panic`, the panic's payload, cut to its first 1,024 bytes at a code point boundary (`cut` then true), or `non-string panic payload` (`batch.md` 2.11); else null. A status is the server's answer, as the transport reason it qualifies is (`batch.md` section 1, D's second limit); a code is a function of the bytes.
- **`pixels_differ`** is true only when both the candidate's and the representative's visible hashes are present and differ. The representative's own flag is false, including for withheld or unwritable keys.
- **Archive eligibility precedence.** No included members means `empty`, even when publication is globally blocked. Otherwise global blocking means `withheld` (`publish_incomplete`), before the size check. An otherwise eligible archive above `10,000 × 16 MiB` is `failed` (`archive_too_large`); equality succeeds. Refusal precedes payload reads and scratch/temp creation, preserves member rows, and leaves digest/size fields null. A stream summary is internal: only acknowledged `present`, or authorized rename followed by the outcome write, permits successful public metadata.
- **Archive member row order** is archive-key bytes, then displayed path in `/`-first order (4.6), then loose-key bytes, then input bytes. Invalid paths take part only in that display sort; they never enter membership selection.
- **A flip** is a rule-3 decision (E31) among candidates whose MD5s are not all equal.
- **A candidate's `rule`** (`collisions`). A unit's candidate carries the rule that decided its unit key in 4.5's step 1 (`prefer_input`, `prefer_md5` or `first_input`), a losing unit's too, the rule that beat it; but `unit_conflict` on the winning unit step 2 withheld, and `withheld` on every unit of a unit key E61 withholds. A unit key E61 withholds stays `withheld` where it also loses a claim in step 2: its keys' reason, and its units' candidates' rule, is `withheld`, not `unit_conflict`. A plain candidate carries `unit` for a reserved key, else the rule that decided the key (`withheld` when E61 withholds it).
  After step 4, a winning unit withheld by propagation carries `unit_conflict`; losing instances keep their step-1 rule, and E61 units keep `withheld`. A directly refused plain candidate keeps its step-3 collision rule. Direct refusals retain their specific `unwritable_key` reason; propagation withholds the unit's other keys without promoting any loser or repeating the prefix pass.
- **Diagnostics.** `same_named_cab`: a registry key (`simplify_name`, 4.3) that two or more bundles of the input's view hold in their top-level directories, one row per key, `bundle` the top-level holder 4.3 ranks highest (`X` when it holds the key, else the greatest id) and `name` the full directory path of that bundle's last top-level row with that key. `undeclared_dependency`: `bundle` null, `name` the `m_Dependencies` name (4.1). `nested_container`: an entry of the input's own bundle that is itself a bundle, met while selecting, `bundle` the input, `name` the entry's path.

A reason is a code of section 9.3. A string taken from the bytes is cut to its first 1,024 bytes, at a code point boundary (an invalid byte counting as one code point, 2.2), and its row's `cut` is then true. A string that is not valid UTF-8 (a name, a CAB, an entry path, a reason's argument) is written with each invalid byte replaced by U+FFFD, so every line is UTF-8 JSON that any parser reads; its original bytes are not recoverable from the manifest, and two stored paths that agree after cutting and that replacement are not told apart. A row holds at most four bounded strings (an id, a key or path, a cut string). The 1,024-byte source cut can expand to 3,072 UTF-8 bytes after repair; it is never reapplied to repaired text. Escaping takes at most six bytes per original source byte, so every final line remains at most 32 KiB (`batch.md` 2.8). Apart from the figures the normalised comparison leaves out (timings, peaks, the host's, `extract.md` section 5), a manifest is a function of the run's records and outcomes; byte identity with another implementation is not a goal.

The local library controller (provisional until B7/B9) commits attempts in
controller receipt order and barrier failures in bytewise input-id order;
manifest ordering remains the row ordering above. Every barrier marks all
failed holders before its first failure write. Failure writes use vacated
admission room, preserve the attempt's figures except zero skips and unresolved
scripts, and add only their own flush to `spooled_part`. Commit stores the
pending input, loads canonical `Control`, hands over uncommitted if stopped,
then renames, emits the typed rename observation, clears the input bit and
clears the pending slot. A rename error retains that slot, with fixed input
and errno facts for B9's reconciliation. `ReadyForWinners` means extraction
artifacts are committed; `HandOver` freezes received facts and leaves queued
ends uncounted. Neither boundary writes a final manifest or publishes.

The sealed library API is `unityrs_batch::attempt::run_attempt(AttemptArgs) ->
AttemptEnd` (provisional until B5–B7). It borrows prepared paths, export options,
peek metadata and a directory owner; only `Done` is eligible for the controller's
later commit. `Failed`, `Stopped` and `RunFailure` retain partial owned artifacts
and discard pending records without flushing. After dropping charged locals it
checks zero Input/Dependency use and allocator refusals; a leak is `internal`
and keeps the slot reserved, an allocator refusal is `host_memory`, under 9.1's
precedence. The end uses fixed reason/detail codes, a view-member index and
bounded entry text; it owns no extraction buffers or permits. A successful
summary's `ms` is sampled at the final seal boundary and reused by the end.

no run id, input position or spool path. Names shared with manifest rows have
the same meaning and types as above. Summary integer tokens occupy 20-byte
slots, padded before the decimal digits with JSON whitespace, so time and
filesystem claim figures cannot change the encoded length or the actual-byte
flush work. The additional fields are:

| `candidate` | `key`, `unit`, `input`, `serialized_file`, `kind`, signed `path_id`, `md5`, integer `crc32`, nullable `visible_hash` and `mode`, `size`, `etag` (null up to and including 16 MiB; multipart above it), `file` (`o<plan_index>`, a stable planning ordinal, with gaps allowed), `cut` |
| `member` | integer `archive` (spec archive index), `path`, `key`, `input`, `md5`, nullable `reason` (an invalid expansion's `unwritable_path`), `cut`; one line per expansion |
| `skip` | the `skips` row's fields |
| `diagnostic` | the `diagnostics` row's fields |
| `input_summary` | terminal: `id`, `status`, `reason`, `detail`, `input_peak`, `dependency_peak`, `evictions`, `export_work`, `decode_work_peak`, `ms`, `skips`, `unresolved_scripts`, `spooled_part`, `claimed_bytes`, `cut` |

A successful summary includes its own final record flush in `export_work`,
`spooled_part` and `claimed_bytes`, matching the attempt end message. A failure

keep their inherited `cut`; they are not cut a second time after replacement.
Every line, including its newline, is at most 32 KiB. Serialization streams
escaping into the charged 64 KiB buffer, flushing only full buffers and the
final partial buffer; failure discards pending bytes without another flush.

Export work counts each actual records flush or output file independently at
`max(4096, ceil(size / 4096) * 4096)`, regardless of `st_blksize`, and pixel
bytes unrounded. A member adds the largest final `archive_members` row encoding
(including newline, the archive key, `cut`, and all included/left-out reason
forms). Its compact artifact row is not the member's work unit. The spooled
part has those file/flush and member units plus the failure-record flush,
without pixels. Disk claims continue to use section 6's cumulative rule.

Counts derived from a row file are zero when that file's `rows` entry is
null. A final directory `syncfs` failure nulls every row entry and zeros all
row-derived counts. Received run figures remain independent of publication
success: the three diagnostic figures in `run` count logical received records,
not successfully published diagnostic lines. A committed pre-dispatch failure
has no attempt-end receipt; its failure-record flush is nevertheless included
in `spooled_parts`, taken from its validated committed summary. Text is cut once by source-byte
length, preserving inherited `cut`; repaired UTF-8 text is never cut again.
The final line-bound tests must include invalid-byte-heavy source strings.
The row assembler takes one frozen snapshot instant for dispatched `not_run`
elapsed times; queued, never-dispatched inputs keep null reason and time.
A family is acknowledged only after its last complete-line chunk. A failed later
chunk nulls the entire family, including earlier physically written chunks.

The probe holds the writer's lock for that instant, so a writer starting then exits 69 (`output_locked`), and its caller retries.

In the first two rows, a read-back (7.2) is not a try of the `running` write. ## 8. Zip bytes

An archive is a function of its members' bytes, paths and order:
- every member stored (method 0), in member order (section 4.7), CRC-32 from the spool's record;
- local and central headers: version needed 20, or 45 in a header that carries a zip64 extra field (so an entry whose offset alone overflowed says 45 in its central header and 20 in its local one), version made by 20, general-purpose flags `0x0800` (UTF-8 names) and no data descriptor, DOS time `0x0000` and date `0x0021` (1980-01-01 00:00), no extra field but zip64's, internal and external attributes 0, no comment;
- **zip64** only where the classic fields overflow (APPNOTE 4.5.3). In a central header, each of the uncompressed size, the compressed size and the local-header offset that is at least `0xFFFFFFFF` is set to `0xFFFFFFFF`, and a zip64 extra field (id `0x0001`) holds exactly those fields, 8 bytes each, in that order. A local header carries a zip64 extra, holding both sizes with both classic size fields set to `0xFFFFFFFF`, only when a size overflowed; an offset alone gives the local header none. An archive whose member count is at least `0xFFFF`, or whose central directory's size or offset is at least `0xFFFFFFFF`, ends with a zip64 end of central directory record (version made by and needed 45, no extensible data), its locator (disk 0, total disks 1), and the classic end record with each overflowed field set to its maximum;
- the central directory is spooled while the members stream and written after them (`batch.md` 2.9).

The emitter validates archive key/index, included count, exact final layout and each payload's extent. During the payload read it recomputes CRC-32 and MD5 against sealed metadata; headers retain the recorded CRC. Short/trailing payloads or metadata mismatches stop `internal`, with no input culprit. Read I/O remains `host_io`.

Whole MD5, current-part MD5 and MD5 over binary completed-part digests are incremental fixed state, with no part-digest vector. All emitted bytes, including central replay and end records, enter these hashes once. Through exactly 16 MiB the ETag is the whole MD5; strictly above it the ETag is the combined digest and part count, with no empty final part. Thus bytes, MD5 and ETag are independent of stream chunk boundaries (E43). An archive over 10,000 such parts (156.25 GiB) is not written (`archive_too_large`).

The `zip_offset` test hook (`batch.md` 2.11) is the first local header's logical position, default zero, behind test hooks. A checked layout seed starts there; the emitter returns only the tail. Logical size includes the prefix; emitted size and test hashes exclude it. Production hashes always start at zero. CPython 3.11's `zipfile` reads every member through a seekable virtual prefix reporting the complete logical length; presenting only a small tail with inflated offsets is invalid. The emitted tail also equals independent `struct`-encoded expectations. Huge member-size and central-size boundaries use header/arithmetic tests, without claiming huge payload round trips.

B8a supplies this library stream. B8b publishes it to a directory sink through B7b's publication and enables archives in B7c's `unityrs batch` subset: each archive streams straight to its sibling temp and commits as a loose output does, and resume compares the destination's whole-file MD5 with a fresh expected-hash pass. Cooperative stream stop checks do not claim B9's process-level grace/finisher guarantees or B11's store transport, retry and journal behavior.

- **Precedence**, when several apply: 78, 69, 70, 74, 7, 6, 5, 4, 3, 0. A failure in `batch.md` 2.11's step 1 comes before validation, so its 69 stands whatever the spec holds. A stop's code is its reason's (section 9.3); a more severe stop that comes before the finisher takes the reason replaces it (`batch.md` 2.11).
  Taking captures an immutable reason/detail/culprit tuple. Later requests still
  reduce the live stop word for hard-exit fallback and arm its time budget;
  they never change the captured manifest. Equal severity retains the first
  entire tuple, including `host_io` versus `host_memory`.
- Codes 1, 2 and 64 to 68 are never used by the engine's surfaces, `unityrs batch ...` and `unityrs --version`. The binary's other commands, `dump` and `values`, which are not the engine's, keep their status 2 for a bad command line, as an unknown top-level command does (`unityrs: error: ...` on stderr, the usage before it). A process killed by a signal shows `128 + N`: `SIGKILL`, which a caller sends no sooner than `shutdown_grace_ms` after its stop signal (1.1); a `SIGXCPU` past `RLIMIT_CPU`; every `SIGABRT` (134), raised by the engine (`batch.md` A13's allocator, a panic while panicking) or sent by the caller, after the engine resets its connections (`batch.md` 2.11); a stack overflow, which ends with 134 when the alternate signal stack holds the nested SIGABRT frame, else with SIGSEGV's 139 (unverified); a signal before `batch.md` 2.11's step 1 blocks the five it handles (the four that stop the run, SIGTERM, SIGINT, SIGHUP and the parent-death signal, and `SIGABRT`); and any signal whose default action ends the process but those four, SIGXFSZ, which it ignores (`batch.md` 2.11), and SIGPIPE, which Rust's runtime ignores. One of the five sent between steps 1 and 4 stays pending and meets its handler at step 4, unless a 78 or 69 ends the process first; the engine's own abort there ends with 134 (glibc's `abort` unblocks `SIGABRT`). As a PID namespace's init (`batch.md` 2.11 step 4), the kernel drops each signal sent to the engine whose action is the default (a blocked one is kept until step 4), but a `SIGKILL` from outside the namespace or from the kernel (137), which ends it, and a `SIGSTOP` from outside, which stops it (the kernel's documented rule for init, unverified against its source here): the engine's own abort before step 4 then ends with SIGSEGV's 139 (glibc on x86-64; unverified elsewhere), and from step 4 every `SIGABRT` ends it with exit status 134 after the resets, not by a signal. The caller retries a `128 + N` with `attempt + 1` after 7.2's wait, counted from the process's end; a 134 with no `SIGABRT` it sent is usually `batch.md` A13's allocator, and the run needs more memory; a 137 the caller did not send is usually the memory cgroup's OOM killer: raise the limit by section 6's rule before the retry. A second signal (SIGTERM, SIGINT or SIGHUP) exits at once, and the hard exit at `T_hard` exits, with the final code once it is stored, else with the stop's code (`batch.md` 2.11), and a final head write in flight may still land. Only SIGTERM, SIGINT and SIGHUP count toward a second signal (the parent's death does not), so a stop for any other reason, followed by one of them, still ends through the finisher.
- `unityrs batch --check JOB.json` exits 0 for a valid spec and 78 otherwise. `unityrs --version` and `unityrs batch --schema` print on stdout and exit 0; each exits 74 when that write fails, with nothing on stderr, or 69 at step 1. On signal-setup failure, each stream that `fstat` reports as a character device is left unwritten so job control cannot stop the exit, including when a denied ioctl prevents terminal detection. Pipes, FIFOs, sockets and regular files keep section 10's shared budget and its regular-file writeback exception.

## 10. The progress stream

NDJSON on stdout (E4), in the stream's own format version `p`: 1 in this release, raised when a binary adds a field or a value of a closed set (`type`, `phase`, `status`, `reason`, a `detail`'s form), whatever the `spec_version`, as `manifest_version` is (7.3). Each line is one JSON object and a whole snapshot, never a delta: a reader needs only the last line it read. Every line has every field below. A reader ignores a field it does not know, reads a value of a closed set it does not know as "other", and reads a line of a higher `p` by the fields it knows.

B7 owns the normal-run one-slot mailbox, writer, bounded acknowledgment and
truthful live samples, including atomic budget telemetry. An unavailable
sample is not represented by fabricated zero usage. B9 owns the service's
lifetime and stop behavior.

- The first line is written when the threads start (`batch.md` 2.11 step 7), and then a line at least every 2 s while stdout is a pipe, a FIFO, a socket or a terminal that the caller keeps reading (a line a full pipe holds back is the caller's own backlog); to a regular file or a block device the host's writeback can hold a write for minutes (measured, `batch.md` A11), so the `exit` line may be missing there, the exit status authoritative, and no deadline waits on it (`batch.md` 2.11). The deadline holds only for a stdout and a stderr of the engine's own: a regular file another process also writes can hold the engine's write on that file's lock while the other writer is throttled, a wait `_exit` cannot end, so the process can outlive its deadline (`batch.md` 2.11, *What cannot be bounded*). A caller that needs the deadline gives the engine a pipe, or a file no other process writes, for each, and sources no other process is writing: on XFS a buffered read takes the file's `IOLOCK_SHARED`, which a throttled writer's `IOLOCK_EXCL` holds. The lines come from a one-slot mailbox (`extract.md` item 5). No field holds a URL, a header value or a credential (E42). A reader ignores a last line with no `\n`: an `_exit` can cut the line being written.
- A run that ends before the progress thread exists (a spec refused at validation, a 69 before that thread's spawn), and `--check` either way, write one line: the `exit` line, with `seq` 0. Without a deadline the main thread writes it, and then its stderr line, within one budget of 1 s for the two, counted from the first write: on a pipe, a FIFO or a terminal through a non-blocking description of its own, tried again while it is full, and on a socket, or when stdout cannot be opened again (`EACCES`, a pipe another uid created), through its writer thread, waited on for what is left of the budget; a line, or its rest, is dropped when the budget is spent, so another writer of the same pipe holds the two no longer (`batch.md` 2.11): a failure before validation accepts a spec, a spec accepted with `deadline: null`, a 78, since a refused spec has no deadline even when its `JOB.json` names one, and `--check`, which sets no deadline and does no work. With the deadline of a spec validation accepted (a 69 after validation, before that thread's spawn), the line, whatever stdout is, goes through the main thread's writer thread, which it waits on for at most `min(1 s, the time left - 500 ms)`, so the line may be missing, and when that wait is not positive (the deadline less than 500 ms away, or past) no line is promised: the exit status is the record (`batch.md` 2.11). For a failure at its step 1, before validation, `phase` is `validate`; on signal-setup failure any stream that is a terminal is left unwritten (9.1). A main-thread panic writes none (70). A 78's stderr line is `unityrs batch: bad_spec <detail>`, the `exit` line's detail, then, for `usage`, the command's usage lines; for `unityrs --version` with an argument it is `unityrs: bad_spec usage`, then `usage: unityrs --version`. **B7c executes the supported local normal run.** B7 execution is a temporary normal-run subset: every declared source is local (unused dependencies included), the sink is a directory, and no deadline, stdin watch or `parent_pid` is requested. Unavailable capabilities are typed library refusals before host checks or mutation; the CLI maps them to 78 `usage` and names this subset. Full validation and `--check` continue to accept the whole v1 schema. This is an explicit temporary exception, with no new closed reason or status. B8b adds directory archives to the subset (section 8). A non-normal controller or publication hand-over preserves artifacts and the existing head, reports the actual failure and skips the normal finisher. B9 replaces that behavior with 7.4's finishing and the mandatory lifetime guarantees; B7 claims neither full lifetime behavior nor complete X10 acceptance.
- **`bad_spec`'s detail** is `<rule> <JSON pointer>`: the rule broken, then the RFC 6901 pointer of the value refused, empty for the document itself, when the detail is the rule alone, with no space, and, for `missing`, the pointer the absent member would have; only the pointer is cut to fit, and a cut pointer ends in `~`, which no whole one does (RFC 6901 writes `~` as `~0`). A bad command line of `unityrs batch ...` or `unityrs --version` (an unknown option, an argument missing or extra) is `usage`, the rule alone; the binary's other commands and an unknown top-level command keep their status 2 (9.1). The parser reports the first error in this order. First the document's own rules: `unreadable` (a `JOB.json` missing, or one that cannot be opened or read), `not_regular`, `too_large`, `not_utf8`, `syntax` (text that is not one JSON value, a value nested 128 levels deep or more, the document's object or array the first level, or a number past a double's range, the conventions). A document that is not an object is `type`, the rule alone. Then `spec_version` (`duplicate_member`, `missing`, `type` or `version`, an unknown version). Then each other value in document order (an absent member at its object's end, where the first required member the object lacks, in its table's order, is named), by the first it breaks of `duplicate_member`, `unknown_field`, `missing`, `type`, `range` (a length, a count, or a string outside its field's values among them), `format` (a pattern, a URL's form, a date, a digest) and `refused_header` (1.2). A value's own rules come before those of what it holds: an array's count before its items, a `headers` object's count and byte total (`range`, at `headers`) before its members. A count is known only at its value's end, so a count out of bounds replaces whatever its items broke; an object's own `missing` is its last rule, after its members', since an absent member is told only at the object's end. After the first error the parser reads the rest of the document for `syntax` and for these own rules of the values that hold the error, and builds nothing more. A URL is `format` when it is not ASCII, `range` when it or its host as written passes its cap, both before it is parsed (1.2), then `format` when it does not parse or has not its form (an endpoint's path, query and fragment included), and only then `range` when its serialization passes its cap. A header's own rules come before its value's members: a refused name whose value is an object is `refused_header`, `{}` included, before the object's missing `env`. A sink whose `kind` is absent or names no kind has each other member checked against either kind's table. Then the cross-field rules, in this order, each with its pointer: 1.1's, in its list's order, `budgets`, `/max_decoded_bytes`; `duplicate_id`, the second occurrence's `id` in document order; `duplicate_header`, the second of the two names, under its bundle's `headers`; `backoff`, `/http/backoff_max_ms`; `deps`, the `deps` list; `view_size`, the first input, in document order, whose view passes `max_view_bundles` or at which the views' running work passes 2^24 ids (1.1), the check stopping there; `spool_in_sink`, `/spool/dir`; `path_style`, `/sink/endpoint` for an address, `/sink/bucket` for a bucket's name; `deadline_required`, `/deadline`; `unknown_input`, the `prefer` entry's `input`; `template`, the template; `key(<rule>)`, the literal key, its rule 2.3's: the sink's `prefix` first, `/sink/prefix`, wherever it stands in the document, since every other key is checked with it, then the other keys in document order; `archive_key`, the later of the two keys; `archive_kind`, the later member's `kind`; then `source`, a bundle with both or neither of `path` and `url`, the bundle (1.2); `headers_without_url`, the bundle's `headers` (1.2); `outputs_empty`, `/outputs`, and `prefer_empty`, a Prefer whose fields are both null, the entry (1.5). The detail holds nothing else: never the parser's message, which may quote a value (E42).
- With `detail` so bounded, every `exit` line is under `PIPE_BUF` (4,096 bytes).
- `unityrs --version` prints one line on stdout, not NDJSON: `unityrs <crate version> spec <highest spec_version>`.
