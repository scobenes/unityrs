# The parity oracle's Python stack (docs/DESIGN.md section 3), for CPython 3.11
# on manylinux x86_64:
#
#     python -m pip install --require-hashes -r tools/parity/requirements-oracle.txt
#
# Each package, dependencies included, is pinned to one wheel: the one the
# oracle image (unityrs-oracle:upy1.25.2-2026-10-28) holds. oracle_records.json
# pins each wheel's files (the digest of its RECORD, written from the wheels by
# `oracle_env.py --pin-records`); installed from these pins, or in the image,
# every file hashes as that RECORD says. The UnityPy wheel carries UnityPyBoost
# (UnityPyBoost.cpython-311-x86_64-linux-gnu.so); without it, or with another
# build of it, unitypy_dump.py refuses to run. Pillow 9.5.0 has two cp311
# manylinux wheels, and the pin is the manylinux_2_28 one the image holds. No
# sdist is allowed, since a local build would not be the image's binary.
#
# numpy is no dependency of UnityPy, but UnityPy imports it when it is there
# (export/SpriteHelper.py solves a sprite's affine transform with numpy, and
# with a pure-Python solver otherwise, and the two render different pixels),
# and the image holds it. So it is pinned too: the oracle is the image's stack,
# numpy included. The image holds other packages too; of those, UnityPy
# imports only pycryptodome's Crypto (UnityCN decryption), and only once a
# decryption key is set, which the oracle never does.
#
# The pinned set is the whole oracle: tools/parity/oracle_env.py checks that an
# interpreter holds each pin's wheel, its version and every file (--exact: and
# nothing else, as in CI's venv), and unitypy_dump.py refuses to run when one
# differs.
# Re-pinning is in tools/parity/README.md.
